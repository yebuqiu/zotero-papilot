01 / 概述

项目定位：账号体系的「出门通道」

Papilot 的账号、会员、官方 AI 网关都跑在自己机器的 Node 后台里。后台要能服务任意网络下的 Zotero 客户端，就必须有一个稳定的公网入口——这正是公网通道唯一负责的事。

通道本身不处理业务：它不解析账号、不缓存请求、不修改报文，只做一件事—— 把 Cloudflare 边缘收到的 HTTPS 请求原样转发到本机 127.0.0.1:8000， 再把响应原样送回去。业务逻辑全部留在账号后台，通道因此可以长期不动。

之所以用隧道而不是「公网 IP + 反向代理」，是因为家用宽带与移动办公场景通常拿不到固定公网 IP， 也未必愿意开入站端口。隧道的连接方向是由本机主动向边缘发起， 于是 NAT、运营商封禁、动态 IP 都不再是问题；域名与证书由 Cloudflare 边缘托管， 大陆访问走境外边缘节点，也无需 ICP 备案。

i

判断该不该动这条通道，只需看一个信号：/api/health 能不能从公网取回 {"ok":true}。 能，就别碰；不能，按 L1–L6 自底向上定位，不要一上来就重启。

它解决什么，以及它不是什么

没有它的时候

  • 后台只活在 127.0.0.1，出了这台机器就登不上账号
  • 换到没有公网 IP 的网络，插件立刻「连不上服务器」
  • 自建反代要开入站端口、配 DDNS、续证书、还要担心运营商封禁
  • 把端口绑到 0.0.0.0 硬顶，等于把管理面直接挂到公网上

有了它之后

  • 任何网络下都能用同一个账号体系，地址固定不变
  • 零入站端口、零端口映射，NAT 后照样可用
  • 域名解析与 HTTPS 证书由边缘自动签发、自动续期
  • 回源始终是本机回环，公网无法绕过边缘直连后台
!

边界要说清：它不是通用内网穿透工具，也不是 VPN。除账号后台的 8000 端口外，它不转发本机任何其他服务； 管理面（/admin）仍只允许本机访问，请勿为了「远程管理」把 admin 也挂到公网域名下。

02 / 特性

九项设计取舍，决定了它为什么「好养」

这条通道最早依赖用户目录与外部保险库，项目搬进移动硬盘后整链失效、公网 530。 重构后的每一条特性，都是对那次故障的直接回答。

01项目内自包含

cloudflared.exe、令牌、运行器、日志全部收在 runtime/cloudflared/。 所有脚本按自身位置反推路径，不写死盘符与用户目录——移动硬盘换机、换盘符，双击即用。

02幂等启停

start 先查边缘是否已就绪，就绪则直接返回 0 不做改动； stop 本来未运行也返回 0。重复点按钮不会产生第二个进程。

03连接参数自动兜底

按 http2+IPv4 → http2+IPv6 → quic+IPv4 依次尝试，每组等 30 秒。 换网络后不必手改参数，restart 会自动挑一组能通的。

04绝不误伤别的隧道

识别进程不看进程名，而是看命令行里是否带本隧道的指标端口 20250。 同机并存其他 cloudflared 隧道时，停止操作只结束自己那一个。

05健康看连接，不看端口

判据是 /ready 返回的 readyConnections 是否大于 0。 端口被占用、进程活着但没连上边缘的「假活」状态无处遁形。

06令牌不进命令行

通过 --token-file token.txt 传递，任务管理器里看不到令牌内容； 令牌文件被 .gitignore 排除，刷新时自动备份旧值并校验格式。

07六层分层诊断

一条命令按 L1→L6 自底向上检查，直接指出"是后台没起、隧道没连、还是本地代理抢答了握手"， 退出码 0/1 可接监控，-Json 可被程序消费。

08守护会自愈，但不瞎重启

守卫先做边缘 TLS 预检：边缘根本不可达时不重启（重启也白搭，只会每分钟 churn 一个进程）， 而是写下 ALERT 并交给路由自愈去修根本问题。

09多入口同一判据

根目录 bat、命令行、控制台 GUI、开机自启，四条入口读的是同一个 /ready， 不存在"控制台说停了、命令行说在跑"的分裂结论。

03 / 原理

请求链路：四段，全程不碰入站端口

客户端发出的是普通 HTTPS 请求；到达本机后，它只是"恰好"从一条加密隧道里出来。 链路上没有一段需要你开放防火墙。

01Zotero 客户端
插件内置固定地址，发起 HTTPS 请求到 pp.xinglintools.top
02Cloudflare 边缘
终止 TLS、按 CNAME 找到隧道 papilot，并挑选一个已就绪的 connector
03隧道连接
cloudflared 主动连到边缘 :7844，把请求从这条长连接里取回
04账号后台
Node 服务在 127.0.0.1:8000 处理业务并原路返回
↳ 为什么第 3 段是"取出"而不是"推进"：连接由本机发起并保持，边缘只是把请求写进这条已存在的会话。 所以本机在 NAT 后面、IP 每天都在变，都不影响可达性。

三段式守护：各自管一件事

守护脚本 scripts/guard-papilot.ps1 每分钟运行一次，三段顺序固定，健康时全部静默不写日志。

P1账号后台

用 /api/health 判断，而不是 TCP 端口。端口在听但事件循环被堵死时， 只有 health 能看出问题；连续 2 次失败才重启，且杀进程前必须确认命令行含 account-server.js——8000 被别的程序占用时只记日志不动手。

P2隧道连接

未就绪时先看两道闸：进程存活不足 90 秒属于"正在连边"，放过； 边缘 :7844 的 TLS 都握不上手，则重启无意义，只写 ALERT。 两道都过才替换进程。

P3出口路由

检查是否有 TUN 代理用 0.0.0.0/1 半路由劫持了流量， 并把边缘网段 198.41.128.0/17 钉到物理网关（metric 1）。 比 /1 更具体，因此只放行边缘、其余照旧走代理。

三个状态，三种处置

看到状态灯时先对号入座，再决定要不要动手。

就绪 · 运行中（隧道已连接）
readyConnections > 0，公网请求可正常回源。此时唯一正确的操作是什么都不做。
进程在，但未连上边缘
readyConnections = 0，公网必然 530。刚启动时等 10–30 秒属正常； 持续如此就跑分层诊断，重点看 L4 是否被本地代理抢答。
未运行
没有持有 20250 的 cloudflared 进程。若是主动停止（存在 runtime/cloudflared/stopped.flag），守护会尊重这个决定、不自动拉起。
04 / 场景

什么时候用得上它

凡是"后台在自己机器上、用户在世界某处"的组合，都落在它的射程内。

A个人跨网络使用

白天在校园网、晚上在咖啡馆、回家换宽带。插件里那个固定域名始终有效， 账号、会员状态、AI 用量记录只有一份，不会因为换网络而分叉。

B移动硬盘随插随用

项目与运行时全在盘里。插到另一台电脑，启动后台再启动通道，同一套账号体系立刻接上—— 那台电脑不需要装 Node、不需要装 cloudflared、不需要管理员权限。

C无公网 IP 的家用宽带

没有固定 IP、无法做端口映射、也拿不到 ICP 备案的域名。 走隧道后这些前置条件全部消失，只保留一个 Cloudflare 托管的子域。

D小范围共享与发放

给同事、学生、小团队成员开账号或发激活码。入口是标准 HTTPS， 对方无需任何额外配置，也不必知道后台跑在哪台机器上。

E官方 AI 网关的对外出口

登录用户的 /v1 请求经此通道到达本机网关，密钥留在服务端， 客户端永远看不到上游 Key；余额与限流也在这一侧统一裁决。

F本机调试与真机验证

需要验证"公网真实链路"而非 localhost 时，通道是最接近生产的环境： 同样的 TLS、同样的边缘转发、同样的延迟特征，一条 restart 就能切状态。

05 / 上手

四步上线，全程零安装

前提只有一个：项目目录（或整块移动硬盘）原样在手，且 runtime/cloudflared/ 下的 cloudflared.exe 与 token.txt 都在。

确认随身三件套在场

打开 runtime/cloudflared/：隧道客户端、令牌文件、运行器缺一不可。 目录里另有 logs/（首次运行自动创建）。

Explorer
runtime\cloudflared\
├─ cloudflared.exe                      # ~55 MB，随盘携带，不入库
├─ token.txt                            # 运行凭证，敏感，不入库
├─ cloudflared-run-papilot.bat          # 单次运行器（可传协议 / edge 版本）
├─ cloudflared-run-papilot-hidden.vbs   # 无窗启动，供自启 / 守护用
└─ logs\cf-run-papilot.log              # 超过 20 MB 自动轮换

启动账号后台（回源先活）

双击根目录 启动Papilot后台.bat，在控制台点「启动后台」。 它会拉起 8000 端口的 Node 服务；隧道是"把请求送过去"，回源没起就只会得到 502。

启动公网通道

双击根目录 启动公网隧道.bat，或控制台「公网通道」组点「启动通道」。 脚本会自动依次尝试三组连接参数，直到边缘连接建立。首连通常 10–30 秒， 移动硬盘冷启动可能更慢，状态灯变绿前不要重复点击。

PowerShell
# 等价的命令行方式（四选一）
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\tunnel\tunnel.ps1 start
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\tunnel\tunnel.ps1 status
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\tunnel\tunnel.ps1 stop
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\tunnel\tunnel.ps1 restart

从公网验证一次

浏览器打开健康检查地址，返回 {"ok":true,…} 即全线贯通。 status 也会顺带跑一次公网自检并打印 HTTP 状态码。

Shell
curl https://pp.xinglintools.top/api/health
# → {"ok":true,"version":"…","uptime":…}
i

换到新电脑时不用重装任何东西。插盘 → 启动后台 → 启动通道 → 验证， 四步与首次完全一致。若 token.txt 丢失或已轮换，见 配置说明 · 令牌轮换。

07 / 运维

公网打不开时，按这个顺序查

最贵的错误是"先重启"。重启会覆盖现场，让根因再也看不出来。 先分层定位，再决定动作。

PowerShell
# 一条命令回答"为什么是 530"
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\diag\probe-tunnel.ps1

# 机器可读，便于接入监控或告警
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\diag\probe-tunnel.ps1 -Json

# 退出码：0 = 公网端点健康；1 = L1..L5 中至少一层失败

六层各看什么

层检查对象失败意味着
L1本机后台 :8000/api/health回源没起或已经卡死，先解决后台（公网此刻必然 502/530）
L2持有 20250 的 cloudflared 进程隧道根本没启动，或被人为停下
L3边缘就绪 /ready 的 readyConnections进程在但没连上边缘——公网 530 的直接原因
L4主机 → 边缘 :7844 的 TCP + TLS出口链路问题。这一层最能区分"本地代理劫持"与"隧道自身故障"
L5公网端点 /api/health链路整体不通，回看前四层
L6出口路径是否被 TUN 半路由接管存在劫持风险，边缘流量可能正走机场节点

最关键的一条判据

TCP 在 <5 ms 就"连上"，随后 TLS EOF

说明本地有个 TUN / 代理抢答了握手——真正的边缘还在境外，你连到的只是代理。 这种情况下重启隧道一万次也没用。
典型场景：Clash 类工具的 TUN 模式吞掉 198.41.128.0/17:7844， 而订阅里恰好缺这条网段的直连规则，流量落进兜底的机场节点。

TLS 能完成，但 L3 仍为 0

出口是通的，问题在隧道自身：令牌失效、隧道在云端被删、或 cloudflared 侧异常。 先看 runtime/cloudflared/logs/cf-run-papilot.log 尾部， 再核对令牌是否需要重签。

应急修复：绕开 TUN 劫持

给边缘网段补一条比 /1 更具体的直连路由。需要管理员权限。 守护脚本的 pass 3 会在下一分钟内自动做同样的事，因此手动操作只是应急。

PowerShell · 管理员
# 1) 找到物理网卡的网关与接口索引（默认路由里 metric 最小的那条）
Get-NetRoute -DestinationPrefix '0.0.0.0/0' | Sort-Object RouteMetric | Select-Object -First 1

# 2) 把 Cloudflare 边缘段钉到物理网关（/17 比 TUN 的 /1 更具体）
New-NetRoute -DestinationPrefix '198.41.128.0/17' `
  -InterfaceIndex <物理网卡 index> -NextHop <物理网关> -RouteMetric 1

# 3) 重启通道，让它重新握手
powershell -File scripts\tunnel\tunnel.ps1 restart

常见问题

按"现象 → 先看什么 → 该做什么"组织，尽量让每条都能独立解决。

公网打开是 530，怎么办？

530 的含义是 Cloudflare 找不到健康的 connector，也就是隧道侧的连接没建立起来。按顺序看：

  • 隧道进程在不在：tunnel.ps1 status 第一行；
  • 边缘连没连上：同一输出的 readyConnections 是否为 0；
  • 边缘本身可不可达：跑 probe-tunnel.ps1 看 L4。

如果只是刚开机，等 10–30 秒再看——移动硬盘冷启动叠加杀软扫描，首连比 SSD 上慢很多。 若持续 530，先修 L4（多为本地代理劫持），再谈重启。

公网是 502，跟 530 有什么区别？

502 说明隧道这条链已经通了——Cloudflare 找到了 connector，也把请求送到了本机， 但回源 127.0.0.1:8000 没有应答。问题在账号后台，不在通道。

去控制台点「启动后台」，或用 probe-tunnel.ps1 确认 L1 是否 PASS。

状态显示"进程在"但公网还是不通，为什么？

因为"进程在"和"健康"是两件事。readyConnections = 0 时，进程活着却在边缘挂不上号， 公网必然不可达——这正是这套系统不用端口判断健康的原因。

常见成因有两个：刚启动还没连上（等 30 秒）；出口被本地代理抢答（跑基线诊断看 L4）。 守护脚本同样会先做边缘 TLS 预检，边缘不可达时它故意不重启，避免每分钟 churn 一个进程。

换了个网络就连不上，必须改参数吗？

不用。跑一次 tunnel.ps1 restart 即可：它会按 http2+IPv4 → http2+IPv6 → quic+IPv4 的顺序重试，每组 30 秒。 某些 ISP 只放通 IPv6，或 UDP 被限速，这条兜底链就是为这些情况准备的。

插件提示"连不上账号服务器"，先查通道还是先查后台？

先分叉，别猜。三个地址依次验证：

  • http://127.0.0.1:8000/api/health —— 后台本身活不活（L1）；
  • http://127.0.0.1:20250/ready —— 隧道连没连上边缘（L3）；
  • https://pp.xinglintools.top/api/health —— 整条链路（L5）。

哪个断就修哪个；三个都通而插件仍报错，问题在客户端侧（地址配置、网络策略、证书时间）。

token.txt 丢了 / 我怀疑泄露了，怎么处理？

丢失就重新生成：refresh-token.ps1 会从保险库提取、校验格式、覆盖写入，并把旧文件备份成 token.txt.bak-时间戳。_brain 不在同级目录时用 -BrainDir 指定。

怀疑泄露则顺序反过来：先去 Cloudflare 控制台重签令牌（旧令牌立即作废），再更新保险库、 再跑脚本。只换本地文件不重签，等于什么都没做。

会不会影响机器上别的 cloudflared 隧道？

不会。识别进程的依据是命令行里是否包含 20250，而不是进程名。 停止操作只结束匹配到的那个；同机其他隧道（例如更新通道用的那条）不受影响。

相应地，不要随手改指标端口——它是这个"只杀自己"能力的唯一依据，改了就失去保护。

为什么开机后要等一会儿才通？

冷启动有三段延迟叠加：移动硬盘首次读盘、杀毒软件实时扫描 cloudflared.exe、 边缘握手本身。从进程 spawn 到 8000 应答十几秒属正常，脚本已经把等待放宽到 25–30 秒。

控制台状态灯也做了专门处理：探测只用 1 秒超时、隔几次才真探一次，避免"边缘卡住时 UI 跟着卡死"。

两块移动硬盘都插着，双击提示"已在运行"？

这不是故障。控制台用单实例互斥量，两块盘上的项目副本共用同一个名字， 因此一块盘开着控制台时，从另一块盘启动会被正确拒绝——避免两份副本同时操作同一套服务与数据。

需要切换时先关掉当前控制台。注意两份副本的代码可能各自演化，同步请按文件清单复制，不要整目录镜像。

需要备案吗？需要自己的证书吗？

都不需要。走 Cloudflare Tunnel 不使用境内服务器的入站端口，因此不涉及备案； HTTPS 由 Cloudflare 边缘自动签发与续期，本机到边缘那一段本身就在隧道加密之内， 127.0.0.1:8000 上不需要任何证书。

若未来改为"公网 IP + nginx 直连"，则需自行处理证书、trust proxy 与管理面鉴权——这条通道的很多便利会同时消失。

控制台显示"未运行"，命令行却说在跑？

理论上不该出现：两条入口读的是同一个 /ready。真出现时按这个顺序查：

  • 控制台状态灯有缓存（隔拍刷新），等一个刷新周期再看；
  • 安全软件是否拦截了 cloudflared.exe 的指标端口监听；
  • 用 tunnel.ps1 status 取一次权威结果，以它为准。
