# B2 / B3 并行编排方案（2026-10-20）

> 目标：让「窗口组件统一（B2）」与「首次使用向导（B3）」同时推进，而不互相踩文件、
> 不把版本号/守卫/产物写乱，并且任何一条线失败都能单独回滚。
>
> 机器可校验的真源：`docs/parallel/tasks.json`（任务 / 依赖 / 文件归属 / 波次）

> 契约：`docs/parallel/ui-kit-contract.md`（B2.0）、`docs/parallel/wizard-spec.md`（B3.0）

## 一、并发调度：按依赖分波，同波次才并行

| 波次 | 并行任务 | 为什么能并行 |
|---|---|---|
| 1 | **B2.0** 组件契约 ｜ **B3.0** 向导交互稿 | 一个写 `ui-kit.css` + 类名快照，一个只写设计文档，文件零交集 |
| 2 | **B2.1** skill-store 迁移 ｜ **B3.1** 向导窗口 ｜ **B3.2** 首启触发 | B2.1 改 `skill-store.*`；B3.1 全是新文件；B3.2 改 `main.js/menus.js`，三者不重叠 |
| 3 | **B2.2** review-workbench ｜ **B2.3** chat-window + workbench ｜ **B3.3** 推荐配置卡 | 四个窗口各改各的；B3.3 只碰 `prefs.xhtml` + 新脚本 |
| 4 | **INTEGRATE**（串行） | 版本号 / pref 默认值 / 守卫 / 产物 / 清单只能有一个写者 |

**调度规则（写进校验器，违反即拒绝开工）**
1. 一个任务只属于一个波次，波次 = **最长依赖路径 + 1**（不能用「我觉得可以一起做」覆盖）。
2. 同一波次内，任意两任务的 `files` **不得相交**（支持 glob 与 `dist/*` 前缀判定）。
3. `exclusiveFiles`（`manifest.json` / `prefs.js` / `papilot-update.json` / `scripts/check-wiring.py` / `dist/*`）
   **只允许 INTEGRATE 写**；其他任务碰一下就报错。
4. 任务 `status` 从 `pending → in_progress → completed`；`--ready` 只列「依赖全部 completed」的任务。

**物理隔离**：每条并行线在自己的 git worktree 里干活，互不共享工作区：

```bash
git worktree add ../pp-b2 -b feat/b2-ui-kit      # B2 线
git worktree add ../pp-b3 -b feat/b3-wizard      # B3 线
# 各自 cd 进去开发、跑 python scripts/preflight.py --fast
# 完成后由集成者在主树按 wave 顺序合并：B2.1 → B3.1/3.2/3.3 → B2.2/2.3 → INTEGRATE
```

> 记忆里的教训：worktree 里构建/门禁必须用**该 worktree 自己的** `ROOT`（`build-xpi.py` 已按脚本位置推导，
> 不会误打包主树）。反向教训也有一条：非本人文件的 mtime 还在变，就不要在主树构建发布。

## 二、依赖管理：契约先行，不靠口头约定

```
B2.0 ─┬─→ B2.1 ─┬─→ B2.2 ─┐
      │         └─→ B2.3 ─┤
      ├─→ B3.1 ─→ B3.3 ───┼─→ INTEGRATE
B3.0 ─┴─→ B3.1            │
      └─→ B3.2 ───────────┘
```

三条硬依赖，其余都是「同一波次里并行」：

1. **B2.0 是所有 UI 任务的前置**：`ui-kit.css` 的类名是消费方的 API。B3.1 只等**契约**（B2.0），
   不等窗口迁移（B2.1–2.3）—— 这是 B2/B3 能真正并行的关键切口。
2. **B2.1 是 B2.2/B2.3 的前置**：它同时是「样板 + 人工目视闸门」。样板没过评审，后两个窗口不许开工，
   否则同一套错误会复制三遍。
3. **INTEGRATE 依赖全部完成**：版本号、`prefs.js` 默认值、`check-wiring` 守卫、产物与清单必须一次成型，
   否则会出现「两个版本号、两份 xpi、清单指错」。

依赖的验收不是「代码写完」，而是每个任务自己的 `exit` 条件（见 tasks.json）：测试绿 + 人工目视
（B2 系列）/ 三步可走通 + 降级齐备（B3 系列）。

## 四、异常处理

| 异常 | 处置 | 回滚粒度 |
|---|---|---|
| 同波次文件冲突（登记表写错） | `parallel-plan.py --check` 直接非零退出，**不开工** | 无（未开工） |
| 合并冲突（两人改了同一函数） | 后合并方 rebase 到先合并方；冲突只允许改自己的部分，不许「顺手重排」 | 单任务 commit |
| 窗口迁移视觉不通过 | 只 `git revert` 该窗口的 commit，其他窗口不回滚 | 1 个窗口 |
| 契约不够用（需要新类） | 开 B2.0 增量：先改契约 + 快照测试，再让消费方用；**不许消费方就地写 inline** | 契约 commit |
| 依赖方要等 | 不阻塞：B3.1 基于契约开发，用 stub 数据；等 B2.1 完成后再联调一次 | — |
| 任务超时（> 1 天未完成） | 降级：B2 只做 1 个窗口、B3 只做前两步；剩下的进下一波 | — |
| 门禁红 | 先看是不是**自己**引入的；不是就记一条 issue 继续（并发期他人改动会造成红） | — |
| CI 红 | 只允许「同一提交重跑」或「补一个只改自己文件的修复」；不许 `--no-verify` 绕过 | 单提交 |
| 版本号被两条线各改一次 | 只有 INTEGRATE 能改；两条线一律不动 `manifest.json` | — |

**提交纪律**（沿用项目既有约定）：显式 `git add` 列路径、禁 `git add -A`、提交身份 noreply、
一个任务一个 commit、commit message 写「已目视：<窗口> 明/暗」。

## 五、预期并行效果

| 指标 | 串行（单线依次做） | 并行（本方案） | 说明 |
|---|---|---|---|
| 总工期 | 5.0 人日 | **3.0 人日**（约 −40%） | 波次内取最慢任务：0.5 + 1.0 + 1.0 + 0.5 |
| B2 四窗口 | 2.0 人日 | 1.5 人日 | 样板 0.5d 后，三个窗口并行 1.0d |
| B3 向导 | 2.5 人日 | 2.0 人日 | 设计→实现仍串行，但实现期与 B2 重叠 |
| 人工评审 | 集中 4 次 | 分散 4 次（可与其他线重叠） | **真正的瓶颈**，见下 |
| 返工半径 | 一处错可能四窗口一起错 | 一处错最多一个窗口 | 样板先行 + 单窗口 commit |

**收益主要来自三件事**（不是「电脑更快」）：
1. 契约先行让 B3 不必等 B2 完工；
2. 文件零交集让两条线可以真的同时改；
3. 单窗口 commit 让评审不通过的代价从「重做一遍」降到「撤一个 commit」。

**已知瓶颈（不会因为并行而消失）**
- **人工目视**：B2 每个窗口必须人看明/暗各一眼（我无法看图）。4 个窗口 ≈ 40 分钟有效等待，
  但可以与其他线的编码重叠 —— 这是并行收益的上限所在。
- **B3 的设计决策**（三步是否够、要不要引导付费）：属于产品判断，不能并行化。
- **单次门禁 ≈ 150s**：每条线各自跑，CI 只在合并后跑一次，不构成瓶颈。

## 六、使用限制

1. **不做自动合并**：`parallel-plan.py` 只校验「能不能并行」，不做 cherry-pick / 冲突自动解决。
   合并仍由集成者按波次手工执行。
2. **文件集靠人维护**：`tasks.json` 的 `files` 是声明，不是从 diff 反推。任务开工后新增文件
   必须同步登记，否则校验器看不到冲突（这是这套方案的**主要失效模式**）。
3. **不支持跨 worktree 的实时协作**：同一文件仍是「先到先得」，两个人同时改同一窗口 =
   冲突留到合并时解决。所以「同波次零交集」是硬约束，不是建议。
4. **不覆盖并发会话的边界**：另一会话的 `cred-vault` 改动不在本登记表内；B3.2 已被标阻塞，
   若强行开工，冲突由开工方负责。
5. **版本发布仍是一次性的**：同一时间只能有一个版本在发（Zotero 只认更高版本号，同号后发不触发更新）。
6. **估算误差**：`est` 是人日经验值，不含评审往返；实际以 `status` 与 commit 记录为准。
7. **向导只在真实首启/升级路径生效**：测试环境需手动清 `wizardDone`，否则看不到弹窗。

## 七、实测记录（方案不是纸上推演）

**隔离验证**（本方案的核心承诺：一条线的红不该传染另一条线）：
在同一分钟，主工作区因为**另一会话未提交的 1.9.1 服务端改动**有 10 个套件红
（`文档版本` / `运维三件套` / `管理审计` / `优惠券` / `登录设备` / `套餐AI` / `网关计量` / `余额域` /
`在线支付` / `接线扫描 3 条`），而把本批提交 `d330ca1` 单独检出到 worktree 后：

```
git worktree add H:/project/pp-verify-d330ca1 d330ca1 --detach
python scripts/preflight.py --fast
→ 共 89 项，通过 88，跳过 1，失败 0
```

结论：**「用 worktree 隔离 + 在提交上验证」能让红绿归因干净**。主树红 ≠ 你的改动有问题，
但必须用这种方式自证，否则合并时会替别人背锅。

**守卫抓到的真实漂移**：并行期间另一会话新增了 `vault.xhtml`（密钥保险箱窗口），
`test/ui-tokens.test.js` 立刻把它纳入检查并报「未引入统一令牌」——守卫按预期工作；
随后它自己也加了 `@import`。同时修掉一个误判：只引入词汇表、**不声明任何本地令牌**的窗口
不该被判失败（不存在覆盖关系）。
