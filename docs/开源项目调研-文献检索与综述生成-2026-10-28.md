# 开源项目调研 · 文献检索与综述生成

- 日期：2026-10-28
- 目的：为 [文献检索与综述生成设计方案](文献检索与综述生成-设计方案-2026-10-28.md) 提供可借鉴的工程机制
- 方法：检索 GitHub 与论文页，读 README / 仓库结构 / 关键模块命名；**未逐个 clone 跑通**，故只评价"机制是否可迁移"，不评价"当前版本是否可用"
- 前提约束：Papilot 是零依赖 Zotero 插件（无 npm、无 Python 运行时），**任何项目都只能借鉴设计，不能引入其运行时**

---

## 0. 结论先行

| 结论 | 说明 |
|---|---|
| 值得借鉴的是**流程骨架**，不是代码 | 综述生成的开源实现几乎都依赖 Python + 向量库 + 多家 LLM SDK，与插件形态不兼容 |
| 最该抄的一条：**"先检索建库、再大纲、再分节写"** | STORM / AutoSurvey / SurveyX 三家独立收敛到同一结构，说明这是被验证过的分解方式 |
| 第二该抄：**引用要落到片段级** | paper-qa 的 `(Paper pages 1-2)` 与 RefChecker 的三元组校验，正好补上 `citeToLink()` 只有编号的短板 |
| 第三该抄：**筛选要人机协同** | ASReview 的"AI 排序 + 人做 oracle"是唯一在系统评价场景被大规模验证的形态 |
| 明确不借鉴 | 向量库/嵌入检索、网络百科式检索、多智能体对话、本地论文库（体积与依赖都不合适） |

## 2. 逐项分析

### 2.1 STORM（斯坦福 OVAL）

**它怎么做**：把"写一篇带引用的长文"拆成两段——
*pre-writing*（检索资料 + 生成大纲）与 *writing*（按大纲写正文 + 挂引用）。
前期核心不是"让模型提问"，而是**Perspective-Guided Question Asking**：先看同类主题的既有文章，
归纳出若干"视角"，再用这些视角驱动提问；配合**模拟对话**（写作者 ↔ 领域专家）迭代补全信息。

**可借鉴**

| 机制 | 映射到本方案 |
|---|---|
| 两阶段 + 大纲作为显式中间产物 | §3 流水线的 S1–S4 与 S5 分界；大纲落盘、可编辑（`outline[]`） |
| 多视角提问扩展检索维度 | `topic` 模式拆概念时，除同义词外补"方法视角/人群视角/结局视角"，生成额外概念组 |
| 引用随写作同步收集 | 本方案更进一步：`[[E:id]]` 在生成时就绑定，而非事后匹配 |
| 大纲先于正文 | 已有 `ReviewWorkbench.generateOutline()` 同构，改造成本低 |

**不采纳**：DSPy 框架与多智能体模拟对话（调用量翻数倍、不可控）；联网百科检索（与 PubMed 场景不符）。

### 2.2 AutoSurvey（NeurIPS 2024）

**它怎么做**：先在大规模摘要库中召回一批文献用于**生成大纲**（`--outline_reference_num`，默认上千），
再为每个小节召回一小批用于**写作**（`--rag_num`，默认 60），按 `--subsection_len` 控制每节长度；
最后用专门指标评估引用与内容质量。

**可借鉴**

| 机制 | 映射到本方案 |
|---|---|
| **两个召回池分离**：大纲看广度，写作看精度 | 已按此拆成两个配置项：`writing.outlinePool`（宽，按概念覆盖）与 `writing.maxEvidencePerSection`（窄，按分数） |
| 分节长度显式预算 | `writing.outline.sections[].budget` |
| 评测驱动迭代 | §15.2 的 40 句标注集与"绑定准确率"指标 |
| 参数化一切（模型、节数、长度、召回量） | §11 配置表的设计依据 |

**不采纳**：本地 53 万篇摘要 + 嵌入索引（插件不能带几百 MB 数据与向量库）；GPU 依赖。

### 2.3 SurveyX

**它怎么做**：准备阶段做**在线文献检索 + 过滤**，再用 **AttributeTree** 把每篇论文按类型
（方法/基准/综述/理论）抽成层级属性树；生成阶段先出大纲再写正文，最后有 **re-polishing** 重润色；
论文里给出了内容质量与**引用质量**的量化提升。

**可借鉴**

| 机制 | 映射到本方案 |
|---|---|
| 按论文类型走不同抽取模板 | `EvidenceCard.design` 决定抽取字段集：RCT 抓样本/干预/终点；综述抓覆盖范围与结论；模型研究抓数据集/指标 |
| 属性树（层级化而非平铺） | 证据卡保留 `outcomes[]` 与 `limitations[]` 两级，而不是一段自由文本 |
| re-polishing（成稿后再过一遍） | P2 的 writer-critic：只对"争议与不足"节做二次打磨，成本可控 |
| 引用质量作为独立指标 | `AuditReport.coverage` 与"仅摘要支撑占比" |

**不采纳**：端到端生成 LaTeX/图表（超出插件定位）；其商业版闭源部分。

### 2.4 paper-qa（PaperQA2）

**它怎么做**：对一摞 PDF 做元数据补全（Semantic Scholar / Crossref / Unpaywall 多源冗余 + **撤稿检查**），
解析入全文索引，检索后用 LLM 做重排与上下文摘要（RCS），最终回答**带页码级引用**，
例如 `(Qian2011Neural pages 1-2)`；支持 agentic 多轮检索。

**可借鉴**

| 机制 | 映射到本方案 |
|---|---|
| 引用落到"文档 + 页/段" | `EvidenceCard.quotes[].loc`（`abstract` / `fulltext:p3` / `section:results`），笔记里可显示"原文：…（第 3 页）" |
| 元数据多源冗余 | S2 合并规则里"摘要取最长、被引取最大、撤稿宁严勿松" |
| **撤稿检查前置** | 硬筛选第一道就排除 `isRetracted`，并在审计里报告"剔除了 N 篇撤稿" |
| 上下文摘要（RCS）而非直接塞原文 | 证据卡本质就是"受控的上下文摘要"，比原样截断摘要更省 token |
| 查询迭代细化 | P2：首轮命中过少时自动放宽概念组并提示用户 |

**不采纳**：向量库（numpy/tantivy）+ LiteLLM + 每次问答多模型调用（成本与依赖都不合适）。

### 2.5 RefChecker（Amazon Science）

**它怎么做**：把模型回答拆成**claim 三元组**（subject, predicate, object），
逐条与参考文本比对，输出 `Entailment / Neutral / Contradiction`，并能**定位证据片段**；
论文报告其在细粒度幻觉检测上显著优于句级/段级判定。

**可借鉴**

| 机制 | 映射到本方案 |
|---|---|
| 断言级（而非段落级）核对 | §10 的 V3：逐句比对数字与结论，而不是"整段看起来对不对" |
| 三分类而非二分类 | 校验结果分"有支撑 / 无信息 / 相矛盾"，`Neutral` 不当作错误（避免误报） |
| 证据定位 | quote 子串定位 + 句子高亮跳转 |
| 抽取器与判定器解耦 | 抽取（S4）与校验（S6）分开，可各自替换模型或换规则 |

**不采纳**：训练/调用 RoBERTa NLI 模型（插件无法承载模型权重）。本方案用
"子串比对 + 数字集合比对 + 可选 LLM 二分类"实现同等目的的低配版。

### 2.6 ASReview

**它怎么做**：把标题/摘要筛选建模为**主动学习排序**——模型每轮给出"最可能相关"的下一批，
人只做纳入/排除（人是 oracle），循环收敛；提供模拟模式评估"能省多少阅读量"；
全过程日志可复现。

**可借鉴**

| 机制 | 映射到本方案 |
|---|---|
| 排序优先、人做决定 | §7 闸 4 的硬约束：AI 只改排序与预填，`decision.by` 必须是 human |
| 每轮只审一小批 | 待定区按分数降序，一次呈现 20 条 |
| 决策日志可复现 | `screening{}` 记录 `by/at/score/reasons`，导出 CSV |
| 冷启动用先验样本 | P2：让用户先标 5 纳入 + 5 排除作为种子 |

**不采纳**：其 Python 模型栈；本方案 P2 用纯 JS 手写 TF-IDF + 线性 SVM（几百行可覆盖）。

### 2.7 paper-search-mcp

**它怎么做**：为 arXiv / PubMed / bioRxiv / medRxiv / Semantic Scholar / Crossref / OpenAlex 等
各写一个适配器，统一返回 `Paper` 对象；所有检索工具共享 `max_results`、`date_from/date_to`、
`abstract_limit`（默认 200 字符，0 省略，-1 全量）等参数，并做跨源去重与 PDF 回退链。

**可借鉴**

| 机制 | 映射到本方案 |
|---|---|
| 统一返回结构 + 统一参数面 | 已有 `SubSources` 的 `entries` 结构就是同一思路；补 `abstract_limit` 式 token 预算参数（`writing`/`extraction` 各一档） |
| 日期区间作为通用参数 | `query.filters.dateFrom/dateTo` 逐源翻译 |
| 平台能力差异显式声明 | `SubSources.LIST[].caps` 已是此设计，本方案扩为 `supports: {mesh, cursor, retraction}` |
| PDF 回退链 | 本地 PDF → OA 链接 → 摘要，对应 `sourceLevel` 三级 |

**不采纳**：Sci-Hub 可选源（合规风险）；MCP 服务形态（插件内直接实现更轻）。

### 2.8 / 2.9 pyalex、pymed（细节参照）

- **pyalex**：`filter` 的拼装约定（`filter=publication_year:>2015,is_retracted:false`）、
  `cursor=*` 翻页、`mailto` 进礼貌池。可直接照抄到 `SubSources._openalex` 的参数构造。
- **pymed**：`esearch` → `efetch` 两段式、XML 字段映射（`ArticleTitle`、`AbstractText` 多段拼接、
  `AuthorList` 集体作者处理）、请求间隔。用于校验本方案 PubMed 解析的边界情况
  （多段摘要、集体作者、非英文标题 `VernacularTitle`）。

### 2.10 zotero/translators（字段映射权威）

PubMed / Crossref / DOI 的元数据到 Zotero 字段的映射，官方 translator 是事实标准。
本方案不复制代码，只在写 `ref-import` 的字段映射时对照，避免自造字段名（如把 `journalAbbreviation`
写成 `journalAbbr`）。**许可与条款以仓库为准，仅作参照。**

## 3. 组合建议：借哪几块、放在哪

| 本方案模块 | 主要借鉴 | 具体动作 |
|---|---|---|
| S1 检索 | paper-search-mcp、pyalex、pymed | 统一参数面 + 逐源分页 + 日期翻译 + 字段边界用例 |
| S2 去重 | paper-qa（元数据冗余/撤稿） | 合并优先级表 + 撤稿宁严勿松 |
| S3 筛选 | ASReview | 排序优先、人做 oracle、决策留痕；P2 上主动学习 |
| S4 证据 | SurveyX（AttributeTree）、paper-qa（片段定位） | 按设计类型分模板 + quote 必填 + 子串校验 |
| S5 写作 | STORM（两阶段）、AutoSurvey（双池/预算） | 大纲先行 + 大纲池/写作池分离 + 每节字数预算 |
| S6 校验 | RefChecker（三元组/三分类）、SurveyX（引用质量指标） | 逐句数字比对 + 三分类 + 覆盖率 |

**一条反向结论**：这些项目都在"生成"上投入很重，在"检索可复现"上投入很轻
（多数不保存检索式与命中计数）。本方案的差异化恰恰在这里——**把方法学留痕做成第一等公民**，
这既是 Zotero 场景的真实需求（写方法学部分要用），也是与通用 AI 写作工具的分界线。

## 4. 明确不引入的东西（防跑偏）

| 不引入 | 理由 |
|---|---|
| 向量数据库 / 嵌入模型 | 插件体积、首次索引耗时、离线不可用；P2 用本地 BM25 替代 |
| LangChain / DSPy / LiteLLM 等框架 | 与零依赖约束冲突，且抽象层会掩盖可控性 |
| 多智能体对话式研究 | 调用成本高、过程不可解释，写综述不需要"圆桌讨论" |
| 论文全文库/摘要库随包分发 | 体积与版权双重问题 |
| 端到端生成 PDF/LaTeX 投稿包 | 超出定位；导出 Markdown/docx/BibTeX 已够用 |
| Sci-Hub 类下载 | 合规风险 |
