# 产品命名评估：PaperPilot 重名现状与改名建议

> 评估日期：2026-10-19 · 数据来源：GitHub Search API（`api.github.com/search/repositories`）、npm registry、PyPI JSON API、RDAP（Verisign / Google Registry）、公开检索
> 代码侧事实来自本仓库实测：`manifest.json`、`prefs.js`、`chrome/content/**`、`paperpilot-update.json`

---

## 一、结论（先给答案）

1. **需要改名**，但只改「用户看得见的那一层」：英文名换掉，`文献副驾` 中文名保留。
2. **不要动内部标识**：`addon id`、`extensions.zotero.paperpilot.*` 这 196 条 pref、本地缓存文件名——改这些等于换一个插件，老用户会失去自动升级、设置和历史数据。
3. **推荐 Papilot**（paper + pilot 压合，最贴合「副驾」语义，包名全可用），**备选 CiteWing**（唯一性最好，但语义偏「引用」）。
4. **不建议 LitPilot**：2026 年已有一篇同名学术论文平台（Taylor & Francis），而你的用户正是写论文的人，搜索结果会被它压死。
5. 执行窗口放在下一个小版本，旧仓库保留一个升级清单文件即可平滑过渡，不需要通知用户重装。

## 三、重名带来的实际代价（按对本项目的影响排序）

1. **搜不到（最致命）**。潜在用户搜索“paperpilot zotero”时，首屏是 5 个同名插件 + 2 个 174★/41★ 的中文同名项目。你的 README、安装教程、公众号文章都拿不到自然流量，因为你叫什么名字、别人也叫什么名字。
2. **装错、认错**。Zotero 插件靠 `.xpi` 手动安装，用户从群聊/文章里拿到一个叫 "PaperPilot" 的包，无法判断是哪一个。一旦装错版本，用户的第一反应是“你的插件有问题”。
3. **工单与口碑错投**。用户在 GitHub 搜到同名仓库提 issue，会提到别人那里；反过来，别人的问题也可能提到你这里。你现在的仓库 star 是 0，同名噪音会让你的项目永远没有“品牌沉淀”。
4. **升级链路的信任问题**。同名不同源的插件各自有 `update_url`，用户无法辨别哪个是“正版”。这既是用户风险，也是你的风险——真出问题时要自证身份。
5. **商标与在先使用**。`Zotero` 是 Corporation for Digital Scholarship 的注册商标，官方规则明确“不得以可能引起 Zotero 用户混淆的方式用于非关联产品”。反过来说：一个已经有 5 个在先同名项目的名字，**谁都无法独占**。未来想注册商标、想给会员体系做正式商业化叙事时，这个名字会先卡住你。
6. **商业化与客服成本**。会员页、收款备注、退款核销、客服话术都要反复解释“我们和那个 PaperPilot 不是同一个”。

## 五、逐个点评

**Papilot（推荐）**
`paper + pilot` 压合成一个 7 字母造词，字面就能读成「纸上的驾驶员」，与现有中文名「文献副驾」严丝合缝。全站 12 个同名里只有 1 个（`hany01rye/papilot`，0★，arXiv 翻译台）沾同域，其余都是无关项目；npm、PyPI、`.dev`、`.app` 全部可用。代价：GitHub 用户名被占（用组织名 `papilot-app` 即可）、`papilot.com` 2007 年就被注册、`papi` 在英文口语里是亲昵称呼，气质略俏皮。

**CiteWing（备选）**
`cite + wing(wingman)`，零同名、包名与账号全可用，唯一性是所有候选里最好的。代价有三：`.com` 在 2026-10-05 刚被注册（可能有人起步，需复查）；`cite` 把产品锁在“引用”上，而你的核心是翻译 / 阅读 / 问答 / PDF 对照；「僚机」这个说法在中文里需要额外解释一次。

**LitPilot（不建议）**
看着最顺，但正好撞在目标用户的信息入口上：2026 年 Taylor & Francis 有一篇《LitPilot: A Human-Centered Platform for Transparent and Interactive Systematic Literature Reviews》，GitHub 还有两个 11★/4★ 的同域文献综述工具。学术人群搜“LitPilot”先看到论文，这个坑比 PaperPilot 更难填。

**Bibliopilot（不推荐）**
零冲突，但 11 个字母，写进 `manifest.json` 的 addon 名、窗口标题、公众号标题都太长，不符合插件名的长度惯例。

## 六、推荐方案

### 6.1 定名

**英文主名：`Papilot`；中文主名继续用 `文献副驾`。**

展示写法：

- Zotero 插件列表 / 窗口标题：`Papilot 文献副驾`
- 仓库：`papilot-zotero`（GitHub / Gitee 同名）
- README 首行：`Papilot（文献副驾）— Zotero 的 AI 文献副驾`

理由三条：

1. **品牌故事不用重讲**。你现有的 UI、菜单、文档里“副驾”的隐喻全部成立，改名只是把 `Paper` 压成 `Pa`，不需要把整套文案重写一遍。
2. **唯一性足够**。GitHub 同名 12 个，但同域只有 1 个 0★ 项目；搜「Papilot Zotero」只有你。相比 PaperPilot 的 5 个同场景同名插件，这是降维。
3. **包名资产全可用**。npm / PyPI / `.dev` / `.app` 全部空着，未来做 CLI、MCP server、文档站都不用再改名。

### 6.2 定名前必须做的事

- **商标快检**：CNIPA 第 9 类（软件）、第 42 类（SaaS）各查一次 `Papilot`；USPTO 顺带查一次。只是快检，不是检索报告。
- **占位**：先建 GitHub 组织 `papilot-app` + 两个新仓库（空仓库即可），再动代码。名字是最便宜、最不可逆的资产。
- **复查 CiteWing**（若你更想要零冲突）：过两周再看 `citewing.com` 是否上线真实产品，再决定。
- `papilot.com` **不建议回购**，除非报价极低——`.dev` 足够。

## 七、迁移方案（关键：升级链路不能断）

### 7.1 三层改动边界

| 层 | 内容 | 处理 |
|---|---|---|
| **不动** | `applications.zotero.id = paperpilot@dev.local` | 保持。这是插件的真实身份，改了等于新插件，老用户失去自动升级 |
| **不动** | `extensions.zotero.paperpilot.*`（196 条 pref） | 保持。改前缀要写迁移代码，收益为零（用户看不见） |
| **不动** | `DataDirectory/paperpilot-*.json` 缓存、CSS 前缀 `pp-`、`Zotero.PaperPilot` 命名空间 | 保持。纯内部标识，改动只会引入回归 |
| **要动** | `manifest.json` 的 `name`、README/docs、菜单与窗口标题、`Zotero` 面板里的品牌文案 | 文案层替换，用户可见 |
| **要动** | GitHub / Gitee 仓库名、Release 资产名、`update.json` 里的 `update_link` 路径 | 发布层 |
| **过渡** | `paperpilot-update.json` 文件名 | **保持文件名不变**（老安装在读它），内容更新 |

### 7.2 升级链路为什么不会断

老用户机器里冻着两样东西：`addon id`（`paperpilot@dev.local`）和 `update_url`（`gitee.com/.../paper-pilot/raw/main/paperpilot-update.json`）。

只要 **id 不变 + 那个旧 URL 仍然能取到一份合法清单**，新版本就会被当成“同一插件的更新”装进去——用户无感。所以：

1. 新版本 manifest 里 `name` 改 `Papilot 文献副驾`，`id` 继续 `paperpilot@dev.local`，`update_url` **顺手改成自己域名的稳定路径**（如 `https://zotero.gujinbencao.com/papilot/update.json`）。以后无论仓库怎么改名，升级链路都不再受影响。
2. `paperpilot-update.json` 继续维护：新版本条目 `update_link` 指向新路径的 xpi，文件名和 `addons` 下的 key 都不动。
3. **Gitee 旧仓库不要删**。最省事的做法：旧仓库停止开发，只保留 `paperpilot-update.json` 一份文件（内容指向新链接），成本≈0，可以长期保留。
4. 文案过渡两个版本：插件列表显示 `Papilot 文献副驾（原 PaperPilot）`，设置面板顶部写一行同名说明。老用户看到“原 PaperPilot”就知道没装错东西。

### 7.3 替换规模与执行顺序

实测规模：`PaperPilot|paperpilot` 在源码/文档中出现 **1861 处**，其中 `chrome/` 1076 处、`docs/` 207 处、`server/` 83 处。

执行顺序（每步可独立回滚）：

1. 建新仓库占名（GitHub / Gitee）。
2. 开分支做机械替换，**带排除清单**：`paperpilot@dev.local`、`extensions.zotero.paperpilot`、`paperpilot-update.json`、`paperpilot-*.json`、`pp-`、`Zotero.PaperPilot` 一律不替换。
3. 人工复核 5 处高风险点：`update_url`、`paperpilot-update.json` 的 key、服务端返回给客户端的文案、支付/会员页抬头、`community-packs` 里的包名引用。
4. 跑门禁：`python scripts/preflight.py --fast` → 全量 `python scripts/preflight.py` → `python scripts/check-wiring.py`（改文案会碰到 XML 实体解析、锚点目录这类静态检查）。
5. `python scripts/build-xpi.py 0.55.0`，解包核对**包内 `manifest.json` 的 name / version / id 与条目数**。
6. **真机双步验证**：先用 0.54.1 装一次并改几个设置 → 再用新包覆盖安装 → 确认 Zotero 插件列表里是**更新了同一条**（不是多出一条）、设置项仍在、账号仍是登录态。
7. 服务端（83 处文案、管理页标题、邮件/回执）另起一个批次，不要和插件发版混在同一轮。

### 7.4 节奏建议

选一个功能空窗的下个小版本（如 0.55.0）单独做改名，别和功能改动混在一个 release——出问题时无法判断是改名引起的还是功能引起的。

## 八、如果坚持不改名（保守方案及其天花板）

最低限度的止损动作：

- 把中文名提到主位，英文名加限定写成 `PaperPilot for Zotero`；
- README 顶部加一段消歧声明（“本项目与 … 无关”）；
- GitHub 仓库描述里塞满差异化关键词（划词翻译 / PDF 对照 / 术语表 / MCP）。

天花板很明确：**你永远无法在“paperpilot”这个词上做品牌沉淀**。5 个同名 Zotero 插件里任何一个做起来，用户记住的都是“那个 PaperPilot”，而不会是你。以现在 star 为 0、同名前缀已被 174★ 项目占住的状况，改名越早越便宜。
