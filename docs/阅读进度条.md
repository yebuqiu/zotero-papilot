# 阅读进度条（0.46.0 · 进度条 2.0）

> 为主界面文献列表的每个条目可视化「这篇我读到哪了」。本文档回答五个问题：
> 进度怎么显示、数据从哪来/存哪去、怎么开关与换样式、大库性能怎么样、配套功能做了哪些取舍。

## 1. 显示形态：进度画在「标题」列背景（对齐 zotero-style 的挂法）

**主形态不需要任何列**——进度直接画在每条文献的标题背后，装完插件即见。

挂法与 [zotero-style](https://github.com/MuiseDestiny/zotero-style) 的
`renderTitleColumn` 完全同源：它 hook 原生「标题」列的单元格渲染（先调原生拿到
cellSpan，再把进度层以 `zIndex:-1` 绝对定位铺进 `.cell-text` 背景，标题容器
`position:relative + zIndex:1` 浮在上层）。我们不依赖 ztoolkit，直接包装
`ItemTree.prototype._renderCell` 的 title 分支——`itemsView` 是该类实例，原型一次
补丁覆盖主列表与 feed 树；wrapper 带识别标记（`_ppProgressRow`）且装饰受开关门控，
卸载时仅在「自己仍是最外层」时还原原型（被别家插件再包一层时只停装饰不撕包）。

两种行内样式（设置 → 条目数据列 → 阅读进度）：

- **heat（默认 · 高能进度条，zotero-style 同款）**：标题背后**每页一格**，
  格子透明度 = 该页累计阅读时长（饱和线 = 均值 +（最大−均值）×0.5，且不低于
  1.5 分钟/页）——哪几页读得久一眼可见。还没有每页数据（老数据/刚装）时自动回退
  为整体填充，读完一页立刻「转正」为逐页热图。
- **fill（整体填充）**：标题背景按进度百分比铺半透明色（已读绿、其余主题强调色）。

悬停标题可看「读到第 X/Y 页（N%）· 累计约 M 分钟」。

**可选列（排序位）**：「阅读进度」数据列仍会注册，但遵循 Zotero 原生行为——
**默认隐藏**，不勾选不出现；只想按进度排序的用户可以右键表头勾选它。列内进度条
样式可配（bar/gradient/percent），但日常查看完全不需要它。

| 方案 | 评估 |
|---|---|
| **标题内嵌（已选）** | zotero-style 实证过的挂点；零用户操作；标题是每行必渲染的格子，热图铺满列宽 |
| 行级底部进度线（覆盖整行） | 同样要包 `_renderCell`/`_renderItem`，但盖住多列信息且遮挡列分隔视觉 |
| 独立列为主显示 | 需要用户手动勾选（本版用户的原话：不要另外设栏目）；列降级为可选排序位 |

## 2. 数据机制：三源融合的「最远到过的页」

进度语义 = **读到哪一页 ÷ 总页数**。三个信号源融合成单一 maxPage，只进不退（重读不倒退）：

| 源 | 机制 | 存储 | 同步 |
|---|---|---|---|
| **A. Zotero 原生上次位置** | 阅读器关页时 Zotero 自己持久化（`attachment.getAttachmentLastPageIndex()`，0 基） | Zotero 库内（SyncedSettings） | **随库同步** |
| **B. 心跳捕获** | `ReadingStats` 每 60s 解析焦点阅读器（0.46.0 起焦点解析抽出为 `activeReader()` 单一真源），经 `PdfText.viewerOf` 取 pdf.js 的 `currentPageNumber/pagesCount`；取不到时回落 A | 本模块 pref | 否 |
| **C. 标注位置** | Notifier 监听标注 `add`，解析 `annotationPosition.pageIndex`（0 基，兜底页标签数字） | 并入 B 的记录（标注本体在库内） | 标注随库同步 |

**存储**：pref `readingProgress`，JSON `{schema, items:{<条目key>:{p:最远页, t:总页数, a:更新ms, d:{<页>:分钟}}}}`，
LRU 上限 3000 条；`d` = 每页累计分钟（高能进度条的燃料，心跳每分钟给当前页 +1），
每条目上限 128 页（超出淘汰读得最少的页）。与 `readingStats` 同一套存储纪律：
只在本机 pref、不上传、不联网。原生位置（A）与标注（C）本身在 Zotero 库里，
换设备登录即自带——我们只存增量，不重复造同步。

**口径可配**（`progressBasis`）：

- `auto`（默认）：有位置用位置，没有按时长折算（分钟 ÷ 页数 × 1.5 分钟/页，即 0.42.0 的算法作兜底）；
- `position`：只看位置（更严格，重读无效）；
- `time`：只看时长（完全回到 0.42.0 行为）。

**总页数**：心跳捕获的 `pagesCount` 优先，其次 `Zotero.Fulltext.getPages`（异步取一次后缓存），
都没有 → 30 页启发值（标记估算）。

**回填**：没有位置记录的条目 → 首次渲染时异步回填一次（`getBestAttachment`
→ 原生位置 + 标注页取 max），落库后 800ms 去抖重绘。**不要求先有心跳时长**——
用户可能从未触发过心跳，但 Zotero 原生「上次读到」早已持久化，打开列表就该看到；
去重 + 一回填终身有效，什么都没有的条目不写 store（不伪造覆盖）。

## 3. 开关与配置

| pref | 默认 | 说明 |
|---|---|---|
| `progressRowEnabled` | true | **行内显示总开关**（标题背景；即时生效，关=只停装饰不动原型） |
| `progressRowStyle` | heat | heat（高能进度条，每页一格）/ fill（整体填充） |
| `progressBasis` | auto | auto / position / time |
| `progressAutoFinish` | true | 进度反向驱动阅读状态 |
| `progressAutoFinishPct` | 95 | 自动「已读」阈值（80–100） |
| `progressColumnEnabled` | true | **可选列**注册开关（排序位；列可见性仍由表头右键控制） |
| `progressBarStyle` | bar | 列内样式：bar / gradient / percent |
| `progressColorByState` | true | 列内进度条按阅读状态着色 |
| `readingProgress` | "" | 位置数据存储（§2 的 JSON，含每页时长 d） |

设置面板在「条目数据列 → 阅读进度」两卡片（行内显示 + 可选列）；样式/口径/着色/行内开关
改动即时重绘（`refreshColumns` + `redraw` 双通道，沿分区列的修复口径）。

## 4. 性能分析（大量条目渲染）

itemTree 是 **virtualized-table**：`dataProvider`/`renderCell` 只对可视行调用（一屏 ~40 行）。
在此前提下分层预算：

| 路径 | 成本 | 控制 |
|---|---|---|
| 行渲染 | 每行 O(1)：两次 Map 查（时长聚合、位置快照）+ 纯算术 | 时长按 `readingStats` **raw pref 串缓存**成聚合 Map；位置走 `readingProgress` 快照（同法），pref 没变不重复 JSON.parse |
| 页数获取 | 异步一次，`itemID→pages` 内存缓存 | 缓存 miss 才查 `Fulltext.getPages`；心跳捕获的总页数直接持久化 |
| 排序（点列头） | 全量 dataProvider，每行仍 O(1) | 万级条目 <100ms；排序键是**零填充百分数字符串**（`"042"`），Zotero 的字符串序即数值序 |
| 心跳 | 每 60s 一次焦点解析 | 无阅读器焦点时近零开销；与 ReadingStats 共用一次 `activeReader()` 结果 |
| 存储 | 每分钟至多一次 JSON 落盘 | LRU 3000 条封顶；位置没推进不写盘（`changed` 才 save） |
| 列关闭时 | 零渲染成本 | 列注销/隐藏后 renderCell 不被调用；心跳仅服务状态自动化 |

已知边界：重绘节流 800ms（页数/回填到达后合并刷新）；排序时 `String(dataProvider 返回值)`
依赖对象 `toString()`——这是 Zotero 官方比较路径，不是依赖实现细节。

## 5. 配套功能与取舍

**做了**：

1. **进度 ⇄ 状态双向联动**（`progressAutoFinish`）：有进度且状态「未读」→ 自动「在读」
   （比 0.11.0 的 tab 事件路径更稳，部分版本 tab 事件不可用）；**位置**进度 ≥ 阈值（默认 95%）且
   页数真实（非启发）→ 自动「已读」。时长口径**不**触发「已读」——反复精读前几页也会攒够时长，
   误标代价高。着色又反过来读状态（绿=已读），闭环成立。
2. **列头原生排序**：零额外 UI。`toString` 零填充方案同时修复了旧版排序完全无效
   （对象被 String 成 `[object Object]`）的问题；空行 `""` 自动沉底。
3. **分类统计联动**：分类右键 →「条目统计」尾部新增阅读情况摘要（已读/在读/未读分布 + 有位置进度的条目数）。
4. **右键重置**：阅读状态子菜单尾部「重置阅读进度」——清位置记录 + 原生「上次读到」归零
   （下次从第 1 页开始）；**标注不动**（用户资产）。

**没做（理由）**：

- **已访问页集合（覆盖率口径）**：跳读的文献永远显示低进度，与直觉相反；存储体积是单值的几十倍。
- **进度写回 Zotero 字段（extra）**：污染元数据、同步冲突面大；本机 pref + 原生位置已同步已够用。
- **按进度筛选的保存搜索**：需动态 search 定义，复杂度高；「排序 + 状态标签」已覆盖主要场景。
- **Hub/工作台进度看板**：本轮收敛范围，ReadingStats 热力图 + 分类统计已提供阅读面观察。
- **原型补丁的替代方案（如只监听 DOM 变更再注入）**：MutationObserver 逐行扫描比「在渲染函数
  出口处装饰一次」更贵也更脆；标题列渲染出口是 zotero-style 多年实证的稳定锚点，且我们
  的 wrapper 带 `_ppProgressRow` 标记 + 开关门控 + 最外层校验还原，与别的插件包一层可共存。

## 6. 已知边界

- EPUB/快照：原生位置是 cfi/百分比而非页码，不参与位置融合——EPUB 走时长口径。
- 关闭阅读统计（`readingStatsEnabled`）后心跳仍在采集位置（进度列独立工作），但时长兜底会失去数据源。
- 同步过来的新「上次位置」在下次打开该文献（或任何一次位置采集）时才会吸收进本机记录。
