## 1. P0 · 计量在空转（最该先修的一条）

**事实**（`server/data/pricing.json`）：

```json
{ "models": {}, "fallback": { "inPer1k": 0, "outPer1k": 0 } }
```

**连锁后果**：

1. `pricing.js priceFor()` 对每个模型都走 `fallback`，`known:false`、单价 0 →
   `cost.micro = (inTok*0 + outTok*0) * 1000 = 0`。
2. 实测用户 `usage.costMicro: {"2026-10-14": 0}` —— **token 数真实记录，成本恒为 0**。
3. `account-server.js:1258 balance.consume(user, cost.micro, …)` 扣的是 0 →
   **余额只发不扣**（`planMicro` 已累计 ¥40，`paidMicro` 0）。
4. 即便把 `balance.enforce` 改成 `true`，也只能拦住"从未充值/无订阅额度"的用户；
   **无法真正按用量扣费**，因为消耗量恒为 0。

**结论**：`06-套餐AI分级` 里写的「订阅去无限化」目前**尚未真正发生**——不是被 enforce=false 关着，是单价没填、计价链条的输入端为空。

**修法（顺序不能颠倒）**：

1. 先填单价表：按**上游真实成本 × markup** 折算成"元/千 token"的对外单价，逐模型录入
   （会员管理 → 成本与用量 → 单价表；`PUT /api/admin/pricing`）。至少覆盖当前在用的
   `deepseek-v4-pro / deepseek-v4-flash / glm-5.3 / glm-5.3-flash / hunyuan-2.0-thinking / minimax-m3 / auto映射的真名`。
2. 让成本看板（`GET /api/admin/usage-summary`）**跑够 1~2 周真实数据**，拿到人均 token/月。
3. 用真实人均成本反推 `monthlyGrantMicro`（见 §2 公式）与 `dailyLimit`。
4. 最后才翻 `balance.enforce = true`。

> ⚠️ 单价是"元/千 token"的**对外售价**，不是上游成本价——额度按它计，毛利就藏在 markup 里。
> 这一步同时决定了 §2 的账能不能算平。

## 2. P0 · 定价与额度倒挂（结构性问题）

**现状数字**（`membership.json priceItems` × `plans.Pro.monthlyGrantMicro=20000000`）：

| 周期 | 实收 | 发放额度（月×¥20） | 用户拿到的额度 / 实收 | 折合月单价 |
|---|---|---|---|---|
| 按月 | ¥9.9 | ¥20 | **2.02×** | ¥9.9 |
| 按季 | ¥19.9 | ¥60 | **3.01×** | ¥6.63 |
| 按年 | ¥69 | ¥240 | **3.48×** | ¥5.75 |

**两个问题叠在一起**：

- **单期就倒挂**：付 ¥9.9 拿 ¥20 的服务，除非对外单价的 markup ≥ 2.0 倍，否则每卖一单亏钱。
- **期限越长越亏**：年付的倒挂倍数（3.48×）反而最高，而它又是最"划算"、最畅销的档位 →
  **卖得越好，亏得越多**。年付要保本，需要 **3.48 倍 markup**，这对可被用户直接购买上游 API 的 LLM 转售来说过高。

**建议（二选一，都可后台改）**：

- **方案 A（推荐，诚信且可算）**：额度按"对外零售单价"计，把 `monthlyGrantMicro` 降到
  **月费 ×(1 − 目标毛利率) 以下**，并让各周期比例**基本持平**。例：月 ¥9.9 → 月额度 **¥6**；
  季 ¥19.9 → 季额度 ¥20；年 ¥69 → 年额度 ¥76（即各约 **0.6~1.1×**，不再倒挂）。
- **方案 B（改价）**：保留 ¥20 月额度，把月费提到 **¥19.9~¥29**，让"额度/月费 ≈ 0.7~1.0"。

**统一公式**：`monthlyGrantMicro ≤ 月费 × (1 − 目标毛利率) ÷ markup`，其中 markup = 对外单价 / 上游成本。
**校准前不要凭感觉填数**——这正是 §1 要先做计量数据的原因。

> 免费额度/赠送同理：注册赠送 ¥6/30 天是"按成本计"还是"按零售价计"要一句话定死，否则后台数字没法对账。

**✅ 已执行（2026-10-14）**：采用 **markup = 2.5×**，`plans.Pro.monthlyGrantMicro` 由 ¥20 → **¥10**。
按已填单价重算三档毛利（假定额度被用满）：

| 周期 | 实收 | 额度 | 额度/实收 | 运营成本（额度÷2.5） | 毛利率 |
|---|---|---|---|---|---|
| 按月 | ¥9.9 | ¥10 | 1.01× | ¥4.0 | **59.6%** |
| 按季 | ¥19.9 | ¥30 | 1.51× | ¥12.0 | **39.7%** |
| 按年 | ¥69 | ¥120 | 1.74× | ¥48.0 | **30.4%** |

三档全部为正，且「期限越长越亏」被反转。**注意**：额度是**上限**而非预期用量，实际利用率远低于 100%，
所以真实毛利会更高——这也是后续可以按数据**上调**额度或**下调**年费的地方。
markup 2.5 是可调参数：改它只需重算单价表（`PUT /api/admin/pricing` 的 `set`），不需改代码。

## 3. P1 · Free 的价值主张被自己掐死

**事实**：`channels.json.highTierModels` 现在包含 `deepseek-v4-flash / glm-5.3-flash / minimax-m3`
（外加一批未上线模型）→ **Free 用户可用的官方模型实际只剩 `auto`**。

**商业含义**：免费用户拿 auto 问一个论文问题，效果往往不足以形成"这个 AI 有用"的第一印象 →
**转化漏斗的第一环（体验）断了**。同时 `plans.Free.features` 还写着"注册赠送 ¥6 额度（限基础模型）"，
而"基础模型"已等于 auto —— 用户会觉得"送了额度却几乎没模型可用"。

**建议**：**用"额度/次数"限制 Free，而不是用"模型白名单"限制**。

- 至少把 **1 个 flash 档**（如 `glm-5.3-flash` 或 `deepseek-v4-flash`）放回免费，让免费用户
  真正体验到 AI 的价值；
- 成本仍由**每日次数 / 每月赠送额度**控制（这两个阀门已经存在且可控）；
- 模型级断崖式封锁 → 对"只想试试"的用户是劝退，对成本控制并不比额度更有效（反正额度才是真阀门）。

## 4. P1 · 价值感知缺失：用户看不见"钱在花"

**现状**：功能全免费，Pro 只卖 AI；但用户在界面上看不到"这次问答花了多少、这个月还剩多少"。
额度是个**不可感知的抽象数字**，用户没有"快用完了"的紧迫感，也就没有升级动力。

**建议**：把成本变成**可感知的稀缺资源**。

- 插件端每次问答后显示：`本次消耗 ¥0.0031 · 本月剩余 ¥18.42`
  （`/api/auth/me` 已有 `cost` 块与余额三档，补"每次请求"粒度即可）；
- 余额/额度低于 20% 时在会员卡转警示色 + 一句"按当前用量约可用 N 天"；
- 这是**唯一能自然产生转化时刻**的地方——到期提醒是行政通知，额度见底才是需求驱动。

## 5. P2 · 产品结构单一

- **只有 Free / Pro 两档**，Pro 是唯一付费档且门槛 ¥9.9。缺少**轻量档**（如 ¥3.9/月，
  只给长上下文基础模型）来承接"想付费但不需要最强模型"的人。
- **充值余额（¥10 / ¥30→¥33 / ¥100→¥115）已存在，但没被产品化** —— 它其实是**非订阅用户的
  唯一付费入口**（`paidMicro` 永不过期、可用于高级模型）。建议包装成"**额度包**"：
  "¥10 = 约 800 次深度问答，永不过期"，并让它与订阅解耦（不买会员也能买包）。
  `docs/账号与会员体系-优化建议.md` #12 已列此项（额度包），至今未做——建议提到 P1。
- 三档化（Team/机构版）暂不急，但**席位共享**是高校/课题组的真实需求，可作为远期方向。

## 6. P2 · 试用与生命周期运营

- **试用按自然日**：`trialOf()` 从 `user.createdAt` 起算 7 天。用户注册后一周没打开 Zotero，
  试用就悄悄作废了 → 建议改为**按活跃度起算**（首次调用 AI 起算 N 天，或"首个 N 次全模型"），
  保证"试用永远发生在用户真正在用的那一刻"。
- **优惠券引擎闲置**：`coupon.js` 已建好（折扣上限 99%、名额占用/释放、与激活码硬隔离），
  但没有任何**生命周期触达**在用它。低成本高杠杆的三张券：
  1. **试用到期券**：试用结束当天推"7 折升级券，3 天有效"；
  2. **续费券**：到期前 7 天推"85 折续费券"；
  3. **充值返券**：首充 ¥30 返 ¥5 额度包。
  这些**零开发增量**（后台配券即可），却能显著抬高试用→付费、到期→续费的转化。

## 7. 认知层：谁才是 Pro 的客户

必须承认一个事实：**自定义 Key 通道可以完整绕过官方网关**（且这是刻意设计——限制它只会拦住
老实用户、毁掉"可接入自己接口"的卖点）。

推论：**Pro 的真实目标客群 = 不会配 API Key / 不想折腾的小白与省事型用户**，
而不是能自己买 API 的技术用户。这直接决定两件事：

1. **定价与文案要面向"省事"而非"模型更强"**：用户不为 token 便宜买单，为"不用自己配 Key、
   开箱能用、额度管够"买单。把 Pro 翻译成"写综述时一键用最强推理模型，不用管 API"。
2. **官方网关要做自带 Key 拿不到的增值**（否则技术用户永远不付费）：论文专用提示词模板、
   术语库联动、长上下文、高峰优先（`GATEWAY_MAX` 目前对所有套餐一样，可按套餐分级）、
   流式稳定性保证。**增值在"服务"层，不在"模型"层。**

## 9. 落地顺序（建议 + 进度）

1. **填单价表** ✅ 2026-10-14 → 2. **看板跑 1~2 周** ⏳ 进行中（已开始计价，等真实数据）
→ 3. **重设 monthlyGrantMicro 消除倒挂** ✅ 2026-10-14（¥20→¥10）→ 4. **Free 放回 1 个 flash 档** ✅ 2026-10-14
→ 5. **插件端显示每次消耗** ✅ 2026-10-14（0.40.0 已实现并构建，待发布）→ 6. **配生命周期券** ⏳ 待做
→ 7. **翻 enforce** ✅ 2026-10-17（与「取消次数上限、Pro ¥20/月」同批，服务端 1.8.0）

### 5 的实现要点（0.40.0 / 服务端 1.7.1）
- 服务端：`/api/auth/me` 的 `cost` 块新增 **`last`** = 最近一次扣费 `{at,micro,text,reason}`（取自余额流水，
  客户端契约**仍不带流水**，只放行这一条）。
- 插件：`AIClient` 官方通道调用成功后，`runSend` 异步回报 `ui.onCost`，
  悬浮窗与独立窗口各渲染一行「本次消耗 ¥x · 剩余额度 ¥y」。
- 三条边界：**仅官方通道**（自带 Key 不计量，显示 ¥0 是误导）；**`at` 未变则跳过**
  （本次未计费时不拿旧流水冒充）；**全程静默**（取不到就不显示，不影响回答）。
- 刷新用 `Account.refreshCost()`：**不落盘、不重绘**（每次调用都跑，不能带来会话写盘）。

**第 2 步之后要做的复核**：拿看板的真实人均成本回填本表——若实际利用率证明 ¥20 偏保守，
可按 §2 公式上调；若 Free 成本超预期，调 `balance.signupGrantMicro` / `signupValidDays`
（1.8.0 起已没有 `dailyLimit` 这个成本口）。

**改动位置**：单价表 `pricing.json→models`（`PUT /api/admin/pricing`）；额度 `plans[].monthlyGrantMicro`；
Free 模型范围 `channels.json→highTierModels`；试用 `membership.json→ai.trialDays`
及 `account-server.js trialOf()`；券 `coupon.js` / 管理页优惠券页签；每次消耗展示 `chrome/content/prefs-account.js`
+ `/api/auth/me` 的 `cost` 块。

## 10. 值得保留的设计（不要再改回去）

- **功能永久免费、算力按量付费**的定位 —— 让装机量与口碑不受付费墙伤害，正确。
- **`auto` 恒免费、越权明确 403 不静默降级、自带 Key 永不限制** —— 三条边界都对，有断言守着。
- **过期不踢下线、只收模型** —— 对留存友好，避免"偷偷降级"的恶感。
- **永久档停售** —— 永久 = 一次性收入 + 无限期成本，在 LLM 成本结构下风险高，停得对
  （`优化建议.md` 里的 ¥298 重定价方案在停售状态下暂不适用）。
