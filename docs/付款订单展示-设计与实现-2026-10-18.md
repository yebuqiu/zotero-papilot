# 付款订单展示能力 · 设计与实现（会员购买 / AI 额度充值）

> 版本：插件 0.49.0 起（服务端契约 1.6.0+，无服务端改动）
> 关联模块：`chrome/content/prefs-account.js`（OrderDlg 组件 + 两条购买流接线）、
> `chrome/content/prefs.xhtml`（挂载点与重开入口）、`chrome/content/prefs.css`（弹窗样式）、
> `test/membership-panel.test.js`（K 段）、`scripts/check-wiring.py`（§43 守卫）。

## 1. 背景与目标

Papilot 的两种购买都在**设置面板 → 账户卡片**内完成，下单后订单信息只落在一段
内联文字区（`pp-mb-pay-info` / `pp-bal-pay-info`）。实际使用中用户容易：

- 漏看**精确金额里的对账尾数**（如 ¥10.42 按 ¥10.00 转账）→ 自动对账匹配不上；
- 在长面板里根本没注意到订单已生成，误以为下单失败。

**目标**：下单验证通过（服务端返回合法 pending 订单）后，**自动弹出一张付款单**，
把「买的是什么 / 多少钱 / 订单号 / 什么状态 / 怎么付 / 二维码」一屏摆清；
订单状态随既有轮询实时更新；订单与会员/余额体系的履约链路不变。

## 2. 展示位置与触发条件

### 2.1 两条购买流（唯一入口：设置面板「账户」卡片）

| 购买流 | 位置 | 下单按钮 | 订单对象 | 履约结果 |
|---|---|---|---|---|
| **会员购买** | 账户卡片 → 会员区「升级/续费专业版」展开下单面板 | `pp-mb-create`「生成订单」 | `mbOrder`（kind=`plan`） | 核销后**开通/续期会员**（`refreshMembership`） |
| **AI 额度充值（模型购买）** | 账户卡片 → AI 余额区「充值额度」展开充值面板 | `pp-bal-create`「生成充值订单」 | `balOrder`（kind=`credit`） | 核销后**余额入账**（`refreshUser`） |

模型（AI 调用额度）的购买在 Papilot 里就是**余额充值**——按用量从余额扣费，
没有单独的「模型商品」订单；因此「模型购买」的订单展示 = 充值订单展示。

### 2.2 触发条件矩阵

| 时机 | 是否弹窗 | 说明 |
|---|---|---|
| 下单成功（`createOrder` / `createCreditOrder` 返回合法订单） | ✅ **自动弹出一次** | 「下单验证通过」= 服务端校验参数/优惠券并落库成功 |
| 订单字段异常（缺 id / 金额不可读 / 金额为负） | ❌ 不弹 | 内联区显示「订单数据异常（原因），请重新生成」 |
| 轮询到状态变化（pending→claimed→fulfilled） | ❌ 不重弹 | 已打开的弹窗**原地更新**内容与按钮态 |
| 点内联区「查看付款单」 | ✅ 重开 | 自动弹出只发生一次；重开入口常驻（订单存在时） |
| 取消订单成功 | — 关闭弹窗 | 订单作废，弹窗无意义 |
| 登录/登出切换账号 | — 关闭弹窗 | 旧账号付款单不得残留 |
| 面板关闭 / 重启 Zotero | 弹窗随之销毁 | 弹窗是面板内 DOM，无独立生命周期；重启后不恢复（与内联订单区一致） |

## 3. 展示逻辑

### 3.1 弹窗结构（`OrderDlg`）

```
┌ 会员订单  [待支付]                              × ┐
│ 专业版 · 12 个月（按年）                          │
│ ¥269.42                                          │  ← 24px 等宽数字
│ ⚠ 请精确转账 ¥269.42（不能凑整）：末尾 42 分是本单专属对账尾数
│ 订单号   o-xxxxxx                                │
│ 订阅周期 按年 · 12 个月                           │
│ 折前价   ¥299.00 / 优惠 CP-XXXX −¥29.58          │  ← 有优惠码时出现
│ 收款方式 支付宝收款码                              │
│ 转账备注 扫码后备注订单号                          │
│ [二维码 148×148]                                  │
│ 核销通过后自动开通会员（无需手动领码）…             │
│ [我已完成支付] [刷新状态] [取消订单] [关闭]         │
└──────────────────────────────────────────────────┘
```

### 3.2 字段映射（服务端 `orderOut` → 弹窗）

| 弹窗字段 | 数据源 | 备注 |
|---|---|---|
| 标题 | `kind`：`plan`→会员订单，`credit`→充值订单 | 双流共用组件 |
| 状态徽标 | `status` → `MB_STATUS` + 色调（pending 警示/claimed 信息/fulfilled 成功/cancelled·expired 灰） | 状态即权限：按钮可用性由状态推导 |
| 订单内容 | 会员：`planName + months/perpetual + cycleName`；充值：`amountText → 到账 creditMicro（含赠送 bonusMicro）` | 充值文案与服务端 `creditText/bonusText` 同源 |
| 金额 | `amountText`（含唯一尾数） | 高亮大字；尾数提醒独立警示条 |
| 订单号 | `id` | 对账与客服凭据 |
| 折前/优惠 | `originalText` / `discountText` / `couponCode` | 仅 `discountCents>0` 时显示 |
| 收款方式/备注 | `pay.channel` / `pay.qrText` / `pay.note` | 与内联区完全一致（同一服务端字段） |
| 二维码 | `pay.qrImage` | 无图时只显示文字指引 |
| 到账说明 | 按 `kind` 固定文案 | 明确「核销后自动开通/入账」 |

### 3.3 状态与按钮联动

| status | 徽标 | 我已完成支付 | 取消订单 | 刷新状态 |
|---|---|---|---|---|
| `pending` 待支付 | 警示黄 | 可用 | 可用 | 可用 |
| `claimed` 待核销 | 信息蓝 | **禁用**（文案改「已提交，等待核销」） | 可用 | 可用 |
| `fulfilled` 已开通 | 成功绿 | 禁用 | 禁用 | 可用 |
| `cancelled`/`expired` | 灰 | 禁用 | 禁用 | 可用 |

## 4. 数据关联（与会员、模型购买体系的正确性）

1. **订单号即纽带**：弹窗展示的 `id` 与内联区、服务端订单、后台对账是同一个订单号；
   弹窗 `update()` 只接受**同 id** 的订单（防旧单覆盖新单）。
2. **动作单一真源**：弹窗按钮不复制业务逻辑，而是调用面板的
   `mbClaimCore / mbCancelCore / mbRefreshCore`（充值侧 `bal*`）——
   与内联按钮共用同一实现，杜绝「弹窗点了已支付、内联区状态没变」这类漂移。
3. **履约链路不变**：
   - 会员单 fulfilled → `mbRefreshCore` 内置 `A.refreshMembership()` + `renderAll()` →
     会员等级/到期时间即时刷新；
   - 充值单 fulfilled → `balRefreshCore` 内置 `A.refreshUser()` + `renderAll()` →
     余额三档（赠送/订阅/充值）即时刷新；
   - 弹窗只做**展示与触发**，不参与入账/开通判断（那些在服务端核销时完成）。
4. **轮询同源**：弹窗不新建定时器，沿用面板既有 6 秒轮询（10 分钟截止）；
   每次轮询结果经 `syncOrderDlg()` 写入弹窗。

## 5. 异常情况处理

| 异常 | 表现 | 处理 |
|---|---|---|
| 下单接口失败（网络/401/服务端 4xx·5xx） | 不弹窗 | 内联「✗ 具体原因」；按钮恢复可点（finally） |
| 订单数据异常（缺 id / 金额不可读 / 负金额） | 不弹窗 | 内联「✗ 订单数据异常（原因），请重新生成」；服务端订单若存在可在订单列表查看 |
| 弹窗构建失败（DOM/装配异常） | 不弹窗 | `show()` 全程 try-catch 返回 false；内联订单区照常渲染（订单信息不丢失） |
| 轮询/刷新失败 | 弹窗保留最后已知状态 | 弹窗内提示「✗ 查询失败」；6 秒后自动重试（silent 轮询不打扰） |
| 提交「我已完成支付」失败 | 弹窗内红色提示 | 按钮态由当前状态重置，可再次提交 |
| 订单过期/被取消 | 徽标转灰 | 停止轮询；「我已完成支付/取消」禁用；用户可关窗重新下单 |
| 重复下单 | 单例弹窗 | 新订单直接替换旧弹窗内容；创建按钮 disabled 防连点 |
| 弹窗打开时切换账号/登出 | 自动关闭 | 登录/登出路径显式 `OrderDlg.close()` |
| 设置面板关闭 | 弹窗随 DOM 销毁 | 无独立窗口/定时器/监听器泄漏（使用 `window.addEventListener("unload")` 既有清理点） |

## 6. 实现要点（为什么这样做）

1. **页面内模态，不新开窗口**：弹窗挂在 `#pp-dlg-root`（根级、折叠组之外），
   与面板轮询同源、随面板销毁；避免独立窗口的跨窗口引用、单例管理、主题复制。
2. **防折叠隐藏**：`#pp-dlg-root` 必须在所有 `.pp-fold` 分组之外——折叠组
   `display:none` 会连带隐藏 `position:fixed` 子节点（check-wiring §43.7 锁死）。
3. **防御式 DOM**：`show()/update()/close()` 全部 try-catch；按钮动作返回
   `{ok,error}` 而非抛错（与项目「异步渲染函数自己包 try」纪律一致）。
4. **测试可跑**：组件只用 `getElementById/createElementNS/appendChild/removeChild`，
   与现有迷你 DOM 测试桩完全兼容（K 段 30 项断言真跑面板脚本）。
