# Papilot 系统架构与性能审查报告

> 基线：插件 `0.54.0`（`manifest.json`）+ 服务端 `1.8.4`（`account-server.js` 头注释）
> 审查时间：2026-10-18
> 工作区状态：`git status` 有 4 个未提交改动（`launcher.ps1` / `start-server-hidden.vbs` / `account-server.js` / 启动 bat，均为「启动控制台卡死治理」在制品）。本报告**已把这批在制品纳入审查**，并单独标注。
> 方法：全量静态扫描（96 个模块对象、5.8 万行插件代码 + 3.6 千行服务端）+ 依赖矩阵计算 + 关键路径逐函数推演 + 实机启动日志 + 实际 pref/数据文件体积测量 + 四路并行深审（服务端并发、AI 链路、功能模块资源、配置构建）。

---

## 0. 结论摘要

**架构总体成立**：插件侧「单作用域全局对象 + 手工依赖序加载」在零打包器约束下是合理取舍；服务端零依赖、单进程、文件存储与「一个人维护的账号后台」规模匹配；启动实测 480ms（`papilot-boot.log`：`startup begin` → `init complete` 共 481ms，其中 90 个脚本加载 163ms），不存在启动性能问题。

**但有四类问题必须优先处理**：

| 级别 | 数量 | 代表问题 | 一句话影响 |
|---|---|---|---|
| P0 | 4 | pref 命名空间错用（11 处）、管理面 DNS rebinding、支付履约跨文件非原子、store 损坏静默重置 | 核心功能静默失效 / 管理面可被远程打 / 已付款未到账 |
| P1 | 12 | refPaneCache 587KB 读放大、每调用全量写盘、会话切换竞态、PDF 状态泄漏、更新通道无签名 | 卡顿、内存增长、数据串台、供应链风险 |
| P2 | 15 | pref 缺默认值、限速表无界、日志无轮转、脚本写死用户目录 | 可维护性与运维韧性 |

**最意外的发现**：设置面板「翻译 / 术语表 / PDF 对照」整组开关**从未真正生效**——写入用了 `Zotero.Prefs.set(key)` 而漏掉第三个参数 `true`，值被写进 `extensions.zotero.extensions.zotero.papilot.*` 双前缀孤儿键；读取端用的是正确键。实测 `prefs.js` 里只存在双前缀键、不存在正确键，术语表核心功能等于全程未生效，界面却提示「已保存（下次翻译即生效）」。

**分级标准**（本报告口径）：

| 级别 | 判定 |
|---|---|
| **P0** | 安全可被利用 / 资金不一致 / 数据丢失 / **核心功能静默失效**。必须在下一版前修复 |
| **P1** | 明显卡顿或内存增长、并发竞态导致错误结果、可用性缺口（可绕过的工作损失） |
| **P2** | 可维护性、运维韧性、边角正确性；不紧急但不能长期欠账 |

> 现状佐证：`python scripts/check-wiring.py` 当前 **1472 项通过 / 0 问题**，但 P0-1 的 11 处错误写入、P1-1 的 587KB 孤儿键全部漏检——说明现有静态守卫只覆盖「显式点名」的接线，缺少**命名空间级**的通用规则。

| 层 | 文件数 | 行数 | 说明 |

模块对象共 **96 个**，全部挂在同一作用域（`var Xxx = {...}`），由 `main.js` 的 `files[]` 手工排序加载。

### 1.3 依赖矩阵（脚本计算，`Xxx.` 形式引用）

| 方向 | Top | 含义 |
|---|---|---|
| 出度最高 | `menus.js` 49、`main.js` 39、`chat-float.js` 13 | `menus.js` 是**扇出中心**：任何功能改名/删除都要动它 |
| 入度最高 | `core/utils.js` 111、`ai/chat.js` 21、`ai/client.js` 21、`semantic-scholar.js` 9、`citation-column.js` 8 | `utils.js` 是单点，改它等于全量回归 |

依赖方向基本健康（core ← ai ← features ← panels），但**没有显式声明**：`files[]` 的顺序注释是唯一契约，加载失败只写 boot 日志、功能静默缺席。

### 1.4 四条主数据流

1. **AI 问答**：`chat-float` → `AIChat.buildMessages`（读条目/全文，16k 字截断）→ `AIClient.chatStream`（fetch + 手写 SSE）→ 官方网关 `POST /v1/chat/completions` → 上游 → 流式回传 → `MdLite.toHtml` 渲染 → `ChatSessions.save`（文件 + pref 尾部）。
2. **账号/计费**：`Account.restore`（2 落点 × 3 代会话副本）→ `/api/auth/me` 滑动续期 → 网关 `balance.precheck` → 上游 → `balance.consume`（三档余额）→ `countUsage`（**同步全量写 users.json**）→ 客户端 `_reportCost` 显示「本次消耗 / 剩余」。
3. **PDF 翻译**：`PdfText` 取 textLayer/blocks → 分类（caption/formula/junk）→ `TranslateSvc`（13 引擎、缓存键含术语指纹）→ `PdfInline` 按段落坐标注入 → 双栏窗口复用同内核；整篇翻译靠**逐页滚动触发 pdf.js 渲染**，串行推进。
4. **MCP 对外**：Zotero 本地 HTTP `/papilot/mcp` → 恒定时间令牌校验 → 只读工具直通、写工具要求 `allowWrite:true` → `AgentTools.execTool(skipConfirm)`。

### 1.5 存储分布

| 位置 | 内容 | 体积（实测） | 风险 |
|---|---|---|---|
| `prefs.js` | 196 默认键 + 运行期大 JSON | **709KB**，其中 Papilot 600KB | 单键 587KB（见 P1-1）、60s 心跳写 |
| Zotero 数据目录 | 聊天会话、S2 被引缓存、翻译缓存 | — | 明文（隐私面） |
| `server/data/*.json` | 用户/令牌/会员/订单/价格/通道 | users 38KB（6 用户）、membership 12KB | 全量重写（P1-4） |
| `server/data/*.log` | console/audit/alerts/guard | console 116KB，**无轮转** | 长期增长（P2-4） |

### 1.6 并发与资源模型

- **插件**：严格单线程。并发靠「每模块 busy 标志 + 代际计数」手写，**无统一调度器**；常驻定时器 12 个（60s 心跳 2、60s 调度 2、6s 轮询 2 个仅在设置面板打开时、30min 发现、其余为窗口内轮询）。
- **服务端**：单进程单事件循环；所有变更**同步** `writeFileSync + renameSync`；金额路径无锁（依赖单线程串行）；跨文件事务不存在。
- **可扩展性**：服务端状态全在内存，**无法水平扩展**（两个实例会互相覆盖 JSON）；插件侧新增功能需同步改 3 处（`files[]`、门面挂载、`destroy`）。

#### 并发点清单（实测）

| 并发点 | 上限/节流 | 取消方式 | 风险 |
|---|---|---|---|
| AI 流式问答（插件→网关） | 单会话 1 个在途（`s.busy`） | `AbortController`；但切条目/关窗口不触发（P1-6/P1-7） | 中途切换串台 |
| 网关→上游 | 每 IP 20 次/分钟；上游空闲 60s（`timeoutMs×5`） | **无**（客户端断开不取消，P1-2） | 白烧 token + 可能崩进程 |
| Agent 工具循环 | `aiAgentMaxSteps` 默认 5，每步一次 LLM + 工具 | 每轮流式句柄挂 `s.handle` | 一步慢则整轮慢；工具串行 |
| 翻译引擎 | 单次翻译 1 请求；回退链 3 档预算（`routeMs`/`totalMs`）；引擎冷却 | 无显式取消 | 回退链叠加延迟 |
| 整篇 PDF 翻译 | 页级**串行**，页内段落并发 2 | `state.stopped` | 31 页最坏 ~2 分钟（P1-8） |
| S2 请求（列/面板） | 批量 50/批、约 1 批/秒；面板 400ms 防抖（0.54） | 代际丢弃 | 翻页时配额消耗 |
| MCP 客户端 | 单请求同步等结果 | 无 | 长工具阻塞调用方 |
| 服务端写盘 | 单线程串行，每次全量 | — | O(用户数) 阻塞（P1-4） |
| 心跳/定时器 | 60s × 2 + 60s × 2 | `stop()`/`destroy()` 成对 | 窗口切换时可能丢句柄（P2-13） |

## 2. 架构评价

### 2.1 做得好、不建议改的部分

1. **零依赖 + 单一真源生成**：`tools/arxiv/src` → `chrome/…/arxiv-*` 由脚本生成，`preflight` 守同构。这是本仓库最值得保留的工程决策。
2. **失败隔离**：`loadSubScript` 逐文件 try/catch + `_diag` 落盘；启动不会因单模块崩掉；`papilot-boot.log` 是极好的可观测设计（本次审查 90% 的装配结论直接从它来）。
3. **服务端资金口径**：金额一律「分」，微元计量，`moneyStr` 不参与计算；`balance` 三档扣减顺序（越保值越晚扣）设计正确；`secretbox` 用 AES-256-GCM + 每次随机 IV，写法正确。
4. **幂等与撤销**：`fulfillByGateway` 状态机幂等、`reconcile` 默认 dryRun、元数据医生可撤销、`audit` 留痕。
5. **安全细节**：MCP 只绑 127.0.0.1 + 恒定时间比较；支付回调验签用 `timingSafeEqual`；上游 401 翻译成 502 避免用户「掉登录」——这些都是踩过坑才有的正确设计。
6. **健康自证**：服务端 200ms 事件循环心跳暴露 `lagMs`——比「端口在听」强得多（本报告 P1-9 正是要求把这条标准用到守护脚本）。

### 2.2 结构性问题

| 问题 | 证据 | 影响 |
|---|---|---|
| **全局作用域无隔离** | 96 个 `var Xxx` 同域；`main.js` `global Xxx, Yyy…` 注释列 130+ 标识符 | 拼写错误静默变全局；无法按模块测试/复用；`destroy` 漏一个就泄漏 |
| **装配清单是唯一依赖契约** | `main.js:52-210`，90 条带注释的顺序 | 新增模块漏加 = 运行期 `undefined`；顺序错 = 静默降级（有 3 个模块靠 `typeof` 兜底） |
| **巨石模块** | `chat-float 2250` / `prefs-account 2096` / `skill-packs 2029` / `cn-fetch 1983` / `translate 1937` | 单文件改动面大、评审困难；`translate.js` 同时承担注册表/缓存/术语/一致性校验 |
| **双路径实现漂移** | `chat-float.js` 有 100ms 节流（0.54 修复），`chat-window.js` 仍逐 token 全量渲染 | 同一个「AI 回答」两套渲染质量；修复只覆盖一半（P1-7） |
| **门面挂载重复** | `main.js:236/254` 两次 `this.menus`；`281/342` 两次 `this.commandTags` | 无害但说明门面是手工维护、无结构校验 |
| **无类型/无 lint** | 仓库无 ESLint/TS | P0-3 这类「少写一个 `true`」的 bug 只能靠人眼或实测发现 |
| **pref 命名空间四套并存** | `extensions.zotero.papilot.*`（规范）／`extensions.papilot.*`（3 模块）／双前缀（11 调用）／双重双前缀（ref-pane） | 见 P0-3、P1-1：功能失效 + 卸载残留 + 无法用 `check-wiring` 覆盖 |

## 3. 问题清单

> 编号规则：`P0/P1/P2 - 序号`。每条给出**位置（文件:行）→ 成因 → 触发 → 影响 → 修复**。
> 行号以当前工作区为准（含未提交改动）。

### 3.1 P0 —— 立即修复

#### P0-1｜pref 写入漏 `true` 参数，术语表/对照/翻译设置全部不生效

- **位置**：`chrome/content/prefs-translate.js:277, 305, 411, 866, 882, 888, 894, 909, 920, 927, 933`（共 11 处）
- **成因**：`Zotero.Prefs.set(key, value, global)` 的第三参数 `global` 缺省为「非全局」，Zotero 会自动补 `extensions.zotero.` 前缀。这些调用传入的是**完整键** `extensions.zotero.papilot.X`，于是实际落盘键变成：
  `extensions.zotero.extensions.zotero.papilot.X`（双前缀）。
  读取端 `prefs-translate.js:144/174/182/405`、`ai/translate.js:178`、`pdf-dual.js:126/161` 等都用 `Prefs.get` 或 `Zotero.Prefs.get(key, true)`，读的是**正确键**。
- **实证**：`%PROFILE%/prefs.js` 中存在 `extensions.zotero.extensions.zotero.papilot.translateGlossary`（703B）与 `…bilingualStructExtract`，**不存在** `extensions.zotero.papilot.translateGlossary` 等正确键。
- **影响（用户可见，且是静默的）**：
  - 设置 → 翻译：**术语表**（手输 / CSV 导入）、术语领域白名单、领域词包状态 → 保存提示「已保存（下次翻译即生效）」，实际 `TranslateSvc` 全程读到空表；
  - 设置 → PDF 对照：右栏模式、同步滚动、同步缩放、译文字号 → 改了不生效（除非从窗口内另有一条正确写入路径覆盖）；
  - 公式保护、结构化提取、双语上下文 → 开关无效；
  - 所有写入产生**孤儿键**：卸载不回滚、设置面板不显示、`check-wiring.py` 覆盖不到（它只比对 `Prefs.` 包装的键）。
  - **没有第二条写入路径兜底**：受影响控件（`pp-tr-glossary` / `pp-tr-bl-struct` / `pp-tr-bl-context` / `pp-tr-formula` / `pp-pd-rightmode` / `pp-pd-scale` / `pp-pd-sync` / `pp-pd-zoom`）在 `prefs.xhtml` 里**都没有 `preference=` 属性**，全靠 `prefs-translate.js` 的 JS 写入；`translate.js` 每次调用都重新解析术语表，因此**同一会话内也不生效**。
- **触发条件**：任何用户打开设置面板改这几项。
- **修复**：
  1. 这 11 处统一改为 `Prefs.set(...)`（内部已带 `global=true`）或 `Zotero.Prefs.set(key, v, true)`；
  2. 补一条**静态守卫**：`check-wiring.py` 增加断言——`Zotero.Prefs.set(` 的字符串首参若以 `extensions.` 开头，必须显式传 `true`；同时断言全仓只允许 `extensions.zotero.papilot.` 一种命名空间；
  3. 迁移：启动时把双前缀孤儿键的值搬回正确键（仅当正确键不存在），然后清理孤儿键；
  4. 补测试：用真实 `Zotero.Prefs` 桩断言「set 后 get 同一键能取回」，否则这类 bug 永远测不出（现有测试桩把它掩盖了）。

#### P0-2｜管理面只认「回环 socket」，可被 DNS rebinding 远程调用

- **位置**：`server/account-server.js:646-650`（`isLocalAdmin`）、`1975`（路由入口，**无 Host/Origin 校验**）
- **成因**：唯一判据是「`remoteAddress` 是回环 且 无 `CF-Connecting-IP`/`X-Forwarded-For`」。攻击者在浏览器里打开恶意页面，把自己的域名解析到 `127.0.0.1`（rebinding），页面 fetch `http://evil.example:8000/api/admin/...` → 请求 socket 来自回环、无代理头 → **判定为本机管理员**。
- **影响**：可读取全部用户/订单/设备 IP，修改自身为 Pro、改价、删用户、充值/调账、导出审计——即后台全部能力。属于「本地服务被浏览器当跳板」的经典面。
- **触发条件**：受害者访问恶意页面且后台在跑（默认常驻）。无需任何凭据。
- **修复**（三层，任一层都能阻断，建议全做）：
  1. **Host 白名单**：`isLocalAdmin` 追加 `req.headers.host` ∈ `127.0.0.1:PORT` / `localhost:PORT`；不匹配直接 403（Tunnel 场景 Host 是公网域名，本来就会被拒）；
  2. **Origin 校验**：带 `Origin`/`Sec-Fetch-Site` 的跨站请求一律拒（本机管理页同源，不受影响）；
  3. **管理令牌**：管理页首次加载下发一次性 token（存 sessionStorage），后续管理 API 校验 `X-PP-Admin`，彻底摆脱「IP 即身份」。

#### P0-3｜支付/充值履约跨两份 JSON 两次写，非原子；进程 fatal 退出放大窗口

- **位置**：`server/account-server.js:2539-2542`（回调）、`2488-2492`（主动查单）、`1907-1926`（`applyOrderFulfill`）、`165-177`（`uncaughtException`/`unhandledRejection` → `process.exit(1)`）
- **成因**：履约顺序是「改内存订单状态 → `membershipStore.save()` → `usersStore.save()`（余额入账）」。两次同步写之间若发生进程退出（未捕获异常、断电、磁盘满导致第二次写抛错被路由 catch 成 500），则：**订单已标记 `fulfilled`，余额未入账**。
- **影响**：用户付了钱、后台显示已履约、余额为 0；且因为订单状态已是 `fulfilled`，再次回调会走 `already:true` 直接返回成功，**永远不会自动补账**；对账只能靠人工比对流水。属于资金类 P0。
- **触发条件**：两次写之间的进程崩溃/异常/磁盘错误。概率低但不可逆，且 `process.exit(1)` 让「任何异步异常」都可能落在这个窗口。
- **修复**：
  1. **改变写序**：先 `usersStore.save()`（入账，带 `orderId` 幂等去重）再 `membershipStore.save()`（置履约）；最坏情况变成「余额到了、订单还 pending」，可由查单/对账重入幂等修复（宁可多给、不可少给）；
  2. **写前先落 journal**：`data/tx/<orderId>.json` 记录 `{orderId, creditMicro, stage}`，启动时扫描未完成事务补账；
  3. `uncaughtException` 的处理改为「先落盘 + 标记不健康 + 优雅退出」，并确保退出前不处于两写之间（用 `try/finally` 包住事务）；
  4. 补测试：mock `usersStore.save` 抛错，断言可通过重放回调补账。

#### P0-4｜store 损坏时静默回退默认值并**立刻覆盖**，会员/订单/价格全清空

- **位置**：`server/lib/store.js:17-33`（`_load` 损坏 → 备份 `.corrupt-*` → 返回 fallback）、`server/account-server.js:269-271`（`membershipStore.save()` **无条件**）、`276-291`（pricing 同样 `save()`）
- **成因**：`_load()` 的容错设计是「绝不因坏文件起不来」，但启动路径紧接着无条件 `save()`，把 fallback（`membership.newDoc()` 的空套餐/空订单/默认价格）写回正式文件。原文件只剩 `.corrupt-<ts>` 副本。
- **影响**：一次磁盘写坏/被截断 → 重启后**订单、激活码、优惠券、自定义价格表全部消失**，页面仍正常服务（用户下单按默认价、已购会员的 `membership.json` 侧记录丢失，虽然 `users.json` 里的 `user.membership` 还在，但订单/对账链断了）。运维若不看日志完全无感。
- **触发条件**：`membership.json`/`pricing.json` JSON 损坏（断电、杀进程写一半、手工编辑）。
- **修复**：
  1. `JsonStore` 增加 `loadFailed` 标志；`loadFailed=true` 时**禁止自动 save**，服务端进入「只读 + 显式告警」模式（`/api/health` 标红、写 alerts.log、启动横幅），并由管理员在后台「从快照/损坏副本恢复」；
  2. 启动时若发现 `.corrupt-*`，主动选最新快照做比对并提示差异条数；
  3. 写盘保持 tmp+rename（已有），但补 `fsync`（`fs.writeSync(fd)` 后 `fsyncSync`）以降低断电截断概率；
  4. 补测试：损坏文件启动 → 断言不覆盖原文件、health 报 `degraded`。

### 3.2 P1 —— 高优先（性能 / 一致性 / 可用性）

#### P1-1｜`refPaneCache` 587KB 孤儿键，且**每次读取都全量重写**

- **位置**：`chrome/content/scripts/panels/ref-pane.js:37`（`CACHE_PREF: "extensions.papilot.refPaneCache"`）、`119-136`（`_cacheReadAll`/`_cacheWriteAll`）、`138-147`（`_cacheGet`）
- **成因**：
  1. 键少写了 `zotero.`，而 `Zotero.Prefs.get/set` 又未传 `true` → 实际键 `extensions.zotero.extensions.papilot.refPaneCache`（实测 587KB，占 prefs.js 的 82%）；
  2. `_cacheGet()` 读完整个 map、刷新 `v.t`、再 `_cacheWriteAll(map)` —— **读操作触发全量 `JSON.stringify` + pref 写**。`Prefs.set` 会让 Zotero 重写整份 prefs.js。
- **影响**：每打开一次参考文献面板/切换一篇文献，就做一次「587KB 解析 + 587KB 序列化 + 700KB prefs.js 落盘」；实测本机 prefs.js 已 709KB，启动解析与每次写盘都被放大；SSD 写放大 + 主线程卡顿。
- **触发条件**：`RefPane` 面板渲染（每次选中条目）。
- **修复**：
  1. 键改为 `refPaneCache` + `Prefs.get/set`（或 `Zotero.Prefs.*(..., true)`）；
  2. **读不写**：LRU 时间戳只在 `_cacheSet` 时刷新，或改为内存内 LRU + 退出时落盘一次；
  3. 存储迁到数据目录文件（`IOUtils` + 1.5s 防抖），pref 只留 schema 版本——与 0.54 对 `chatSessions` 的改造同口径；
  4. 迁移：启动时读孤儿键 → 写新位置 → 删除孤儿键（可回收 587KB）。

#### P1-2｜网关不处理客户端断开：上游继续跑、可能写入已销毁响应、无取消

- **位置**：`server/account-server.js:1167-1382`（`gatewayChat`），全文件 **无** `req.on('close')` / `res.on('error')` / `aborted` 处理
- **成因**：手动转发只判 `res.writableEnded`，不判 `res.destroyed`；客户端 abort（插件 `stop()`、关窗口、断网）后：`upReq` 不会被 `destroy()`，上游继续生成到结束（最长 120s），期间 `res.write()` 可能落在已销毁的流上。
- **影响**：
  - 运营成本：用户点了「停止」，上游仍在烧 token，**该成本仍会计入用户余额**（`upRes.on('end')` 照常 `consume`）；
  - 可用性：向已销毁响应写数据在 Node 上可能触发未处理的 `'error'` → 命中 `uncaughtException` → **整个进程退出**（1 分钟空窗，所有在线用户掉线）；
  - 无背压取消：大量 abort 时上游连接堆积。
- **修复**：
  1. `res.on('close', () => { if (!res.writableEnded) upReq.destroy(); })`；
  2. `upRes`/`res` 都挂 `'error'` 处理器，写前判 `!res.destroyed`；
  3. 区分「客户端主动取消」与「上游失败」：取消时**不计费**（或按已产生 usage 计），并在日志记 `client_abort`；
  4. 补测试：起一个假上游，客户端发请求后立即 abort，断言上游 socket 被销毁、无 `uncaughtException`。

#### P1-3｜余额 precheck 无预留：单请求与并发都能大幅透支

- **位置**：`server/account-server.js:1241`（`balance.precheck` 仅判当前余额 > 0 / 高于阈值）、`1355-1362`（响应结束才 `consume`）
- **成因**：放行时不冻结额度，也不限制 `max_tokens`；`balance` 明确允许透支（注释：「拦截由请求前的 pre-check 负责」），于是单次请求成本可以远超余额。
- **影响**：`enforce=true` 时，余额 ¥0.01 的账号发一条 `max_tokens: 100000` 的长文请求，可产生数元成本；并发 20 条更甚。开启强制计费后这是直接的资金漏洞（当前默认 `enforce=false` 观察模式，风险被掩盖）。
- **修复**：
  1. precheck 时按「模型单价 × 预估 token（含 `max_tokens` 上限）」做**预留**（内存 `reserved` 字段），响应结束按实际结算、释放差额；
  2. 余额不足时把 `max_tokens` 夹到「余额可支付的上限」，或直接 402 并给出建议值；
  3. 并发保护：同一用户同时在途请求数上限（如 3）；
  4. 后台看板增加「透支金额」指标。

#### P1-4｜每次成功 AI 调用都同步全量重写 `users.json`

- **位置**：`server/account-server.js:877-880`（`countUsage` → `usersStore.save()`）、`store.js:35-39`（`writeFileSync` 全量 + `renameSync`）
- **成因**：用量、余额、令牌续期都挂在 `users.json` 这一个文档里，任何一次成功转发都 `JSON.stringify(整个 users)` 并同步写盘。
- **影响（实测外推）**：当前 6 用户时 38KB，单次写 ~1ms；按每用户 30 天按日用量 + `byModel` 估算约 6KB/人 → **1000 用户约 6MB，单次写 30–60ms 且阻塞事件循环**；并发 10 个 AI 请求 = 300–600ms 的接受队列停顿。这是服务端最主要的吞吐天花板，且随用户数线性恶化。
- **触发条件**：任何 AI 调用。
- **修复**：
  1. 用量/余额与账号静态信息**拆文件**（`usage/<userId>.json` 或按天分片），避免 O(全部用户) 写；
  2. 写入改异步（`fs.promises.writeFile` + rename）+ 单飞（在途写只保留最后一次），并保留 shutdown 强制刷盘；
  3. 中期：迁 SQLite（Node 22 内置 `node:sqlite`，仍零第三方依赖）——一次事务只写变更行；
  4. 观测：把 `lagMs` 接到告警（>500ms 连续 3 次）。

#### P1-5｜两处 60s 心跳全量写 pref；进度列每行读 pref、回填逐条写 pref

- **位置**：
  - `features/reading-stats.js:41-45`（`save` → `Prefs.set("readingStats", JSON)`）、`226-241`（60s tick 必写）
  - `features/reading-progress.js:58-61`、`200-241`（60s tick：`load → bumpPage → prune → save`）
  - `columns/progress-column.js:84-107`（`_minutesMap` 每行 `Prefs.get("readingStats")`）、`126-147`（`snapshot` 每行 `Prefs.get("readingProgress")` 并做整串比较）、`216`（每行再读 `progressBasis`）
  - `columns/progress-column.js:141-166`（回填：**每条条目** `ReadingProgress.save`）
- **成因**：把「按条目/按页」的增长型数据放进 pref；读路径没有内存级缓存失效机制，只能每次从 pref 取整串再比较。
- **影响**：
  - 阅读时每分钟 **2 次 700KB 级 prefs.js 重写**（Zotero 会序列化整份 prefs）+ 1 次 `redraw`；
  - 列表滚动/重绘时，每可见行 2–3 次 `Prefs.get`（跨 XPCOM + 字符串拷贝），大库时明显掉帧；
  - 首次打开含进度列的库：每个无记录条目触发一次 `getBestAttachment()` + 一次全量 pref 写，**N 条 = N 次写**。
- **修复**：
  1. 心跳改「内存累加 + 60s 防抖落盘一次」（现在就是 60s，但**未判断是否变化**——`bumpPage` 恒返回 `changed:true`，可改为「页未变则只在 5 分钟或切页时写」）；
  2. 存储迁到数据目录文件（同 P1-1 方案），pref 只留版本号；
  3. 列渲染改**订阅式缓存**：模块级 `Map` + 在 `save` 后自增 `version`，`lookup` 只读内存；`progressBasis` 等静态 pref 在 `_watchPrefs` 里缓存到变量；
  4. 回填批处理：收集 `_pendingRefresh` 后统一 `save` 一次（现在 refresh 批了，save 没批）。

#### P1-6｜切换会话条目不中断生成：旧文献的回答写进新文献的会话

- **位置**：`panels/chat-float.js:125-137`（`setSessionItem` 只清 history，**不 stop**）、`1814-1827`（`toggle` 可在 `busy` 时切条目）、`704-743`（`runSend` 结束后无条件 `s.history.push` + `_saveSession`）
- **成因**：`s` 是 `this.session` 的引用；切条目时同一对象被就地 reset（`item` 换、`history=[]`），在途请求的 `await` 返回后仍往同一对象 push，并调用 `_saveSession()`（此时 `itemID` 已是新条目）。
- **影响**：A 论文的提问与回答被写进 B 论文的会话存档；UI 上回答气泡落在旧窗口/旧位置，用户以为是 B 的回答。属于数据正确性问题（可被后续问答当作上下文污染）。
- **触发条件**：生成中按 Ctrl+Shift+K 或切换选中条目（很常见）。
- **修复**：引入代际 token：`runSend` 开始时记 `const genItemID = s.item && s.item.id`；每次 `await` 后与当前 `s.item.id` 比较，不一致则丢弃（不 push、不 save、`ui.onAbort()`）；或在 `setSessionItem` 里 `this.stop()` 并 `_flushRender()`。

#### P1-7｜分屏窗口逐 token 全量 Markdown 渲染；关闭窗口不中断请求

- **位置**：`chrome/content/chat-window.js:221-230`（`onDelta` 内 `mdLite.toHtml(acc)` + `innerHTML=` + `appendChild` + `scrollBottom()`）、`310-312`（`unload` 只 `_wins.delete`，**不 abort**）
- **成因**：0.54 的流式节流只加在 `panels/chat-float.js`（`_queueRender` 100ms），分屏窗口是**另一条渲染路径**，仍按 token 全量重解析。
- **影响**：长回答 O(n²) 主线程开销 + 强制 reflow（每 token 一次 scroll），分屏窗口明显掉帧；关闭窗口后请求继续跑（和 P1-2 叠加：上游白烧 token、仍计费）。
- **修复**：把 `ChatFloat._queueRender/_flushRender` 提为共用工具（或 `AIChat` 层统一 emit 节流），窗口复用；`unload` 里 `CF.stop()`；`onDone` 前 `flush`。

#### P1-8｜PDF 内联状态永不释放；整篇翻译串行等待

- **位置**：`features/pdf-inline.js:331`（`const states = new Map()`）、`964`（`states.set(reader, st)`）、`1115`（`stop()` 不清 map）；全文件无 `states.delete`；`1402-1440`（`translateAll` 逐页 `currentPageNumber` + `scrollTop` + 最多 24×160ms 等待）
- **成因**：Map 以 reader 对象为键，`stop()` 只停 UI/定时器，不解除引用；`translateAll` 依赖「滚动触发 pdf.js 渲染」。
- **影响**：
  - 每打开一篇 PDF 泄漏一份 state（含 DOM 引用、段落缓存、`pollTimer` 句柄），读 50 篇后内存与事件监听持续累积；reader 关闭时监听器仍挂在已销毁文档上；
  - 整篇翻译：31 页在最坏情况 ≈ 2 分钟纯等待，期间劫持用户滚动位置（`container.scrollTop`），且不可真正中断到当前页内的等待。
- **修复**：
  1. 在 `stop()`/reader `unload`/`destroy` 三处 `states.delete(reader)`，并显式 `removeEventListener`；
  2. 用 `WeakMap` 兜底（reader 被 GC 时自然释放）；
  3. 整篇翻译改「按页并发 2–3 + `IntersectionObserver` 驱动」或直接用 `pdf.js` 的 `getPage + getTextContent` 离屏取文（不依赖滚动），彻底去掉 3.84s 等待与滚动劫持。

#### P1-9｜守护脚本只看端口，与启动器的健康判定不一致

- **位置**：`scripts/guard-papilot.ps1:106`（`Test-Port 8000` 即认为健康）、`125`（等待 25s 后同样只 `Test-Port`）；对比 `launcher.ps1:3433`（明确区分「端口在听但 `/api/health` 不过」）
- **成因**：两套 watchdog 各写一套判据；guard 在 2026-10-16 重写时只解决了 tunnel 的 `/ready`，账号服务仍是 TCP 探测。
- **影响**：服务端「端口在听但事件循环卡死/半死」（同步写盘阻塞、死循环）时，guard 静默无操作，公网持续 502/超时；而启动器面板显示「服务异常」——两边结论相反，排障被误导。
- **修复**：guard 复用 `/api/health`（3s 超时）+ `lagMs` 阈值；连续 2 次失败才重启（避免误杀）；重启前落 `guard.log` 并带上 health 原文。启动器与 guard 抽一个共同探测函数（或 guard 直接调用 `launcher.ps1 -ProbeOnly`）。

#### P1-10｜服务端 O(n) 扫描与重复计算

- **位置**：`account-server.js:755-761`（`findUserByEmail/Id` 线性）、`membership.findOrder` 线性、`2374/2817/3148`（`reapOrders` **每个订单相关请求都全表扫并可能写盘**）、`2044-2046`（health 里 `backlogNow()` 调 3 次，每次都遍历订单）、`2026`（health 对全部用户 reduce `missingUsage`）、`2053-2054`（`audit.stats` 调 2 次，各读目录）
- **影响**：当前 6 用户/8 订单无感；订单到几千、用户到几千后，`/api/health`（被控制台每几秒轮询）本身成为 CPU 热点；`reapOrders` 让「查看订单列表」变成写操作。
- **修复**：启动时建 `Map<email,user>`、`Map<orderId,order>` 索引并在增删处维护；`reapOrders` 改为定时任务（1 次/小时）而非请求路径；health 里 `backlogNow()` 只算一次、`audit.stats` 合一；health 结果缓存 2s。

#### P1-11｜注册赠送 + 无验证码 + 邮件失败自动激活 可被批量套取额度

- **位置**：`account-server.js:2059-2097`（注册）、`2071-2075`（`grantSignup`）、`2084-2089`（发信失败 → `status='active'` 直接激活）、`240`（`REG_MAX=5`/IP/分钟）；`server/data/pp.env` 当前已配 `PP_RESEND_KEY`，故线上风险降低
- **成因**：防护只有「每 IP 每分钟 5 次」；无邮箱域名限制、无验证码、无风控；邮件通道故障时降级为直接激活（可用性优先的合理取舍，但同时放开了赠送）。
- **影响**：`signupGrantMicro` 默认 ¥6/账号，脚本换 IP + 一次性邮箱即可批量领取免费额度；额度可立即用于官方网关消费（注册赠送限定基础模型，但基础模型也在烧上游成本）。
- **修复**：注册赠送改为「邮箱验证通过后才发放」；同一邮箱域名/设备指纹限 1–2 个；邮件失败时保持 `pending` 而非激活（或改为不发额度）；监控「新账号 24h 内消费占比」。

#### P1-12｜更新通道无签名校验，`main` 分支即发布通道

- **位置**：`manifest.json`（`update_url` = `https://gitee.com/.../raw/main/papilot-update.json`）；`features/update-notice.js`（读同一清单）
- **成因**：Zotero 的第三方插件更新只校验 XPIs 的清单版本号，不校验发布者签名；清单与 xpi 都从仓库 `main` 分支直出。
- **影响**：任何获得仓库写权限的人（或一次误推）可向全部用户下发任意代码；`update_link` 也可被改成任意 URL。属于供应链风险，影响面 = 全部安装用户。

## 附录 G：P1-3 余额预留（2026-10-19，团队 SOP 交付）

**问题**：`precheck` 只读放行、扣费在响应结束，两个并发请求都能过检 → 一起扣成负数（生产 `enforce=true`）。

**方案（预留制）**：
- `balance.js`：`heldMicro` + `holds[{id,micro,at,highTier}]`（上限 8），`hold/settleHold/releaseHold/availableMicro`；`sweep()` 5 分钟回收异常占款；`ensure()` 按 holds 重算自愈；`viewOf()` 增 `heldMicro/availableMicro`（旧字段不变）。
- `gatewayChat()`：precheck 通过后按 `costOf(预估 in/out token) × 1.2` 预留（上限为可用额）；结束 `settleHold(实际成本)`；`holdClosed` 保证只走一次终态；客户端断开/上游 4xx/超时/异常一律 `releaseHold`。观察模式（`enforce=false`）不预留，保持「只记账不拦截」。
- 402 语义：`TOO_MANY_HOLDS`（并发 8 条）/ 预留被占（`INSUFFICIENT_BALANCE` 但 precheck 放行）/ precheck 拒绝（原文案一字不动）三路分流；透出 `hd.code` 便于客服判因（客户端只读 HTTP 402，零影响）。

**团队过程中修掉的 P0 级隐患**：`mod.request` 在预留之后**无 try/catch**——通道 apiKey 混入 `\n`/全角字符时同步抛 `ERR_INVALID_CHAR` → `unhandledRejection` → `process.exit(1)`，一条坏密钥杀整个后台且预留变僵尸。已加「构造请求 + 写 payload」与 `writeHead`（含 600+ 非法状态码）双保护，均回 502 并释放预留。

**验证**：
- `test/balance-hold.test.js` 105 项（含 `--probe-bad-key` 子进程回归：坏密钥 → 502 / exit 0 / held=0 / 无 consume）。
- `test/balance-hold-audit.test.js` 111 项（QA 独立编写）：断开、500/400/401、连接拒绝、超时、10 次串行、观察模式、脏数据自愈、非法 actual、上游 600、坏密钥 + 抢断、连续 5 次风暴后正常计费、8 条在飞第 9 条 `TOO_MANY_HOLDS` 且不破坏已有预留。
- 门禁：**79/79**；`check-wiring` 1495/0（19.17/19.18 已更新为 settleHold 口径）。
- 生产重启：1.8.5、`degraded=false`、users=6/orders=8、无残留 `heldMicro`、管理面 200/伪造 Host 403。

**已知取舍**：① 未配价模型 `costOf=0` ⇒ 不预留（实际扣费亦为 0，属运营补价流程）；② 8 条并发上限；③ holds 为单进程内存语义，多实例需分布式锁；④ 402 未接充值 CTA（`err.payment` 死标志，另行登记）。
