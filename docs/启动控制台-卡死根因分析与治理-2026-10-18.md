## 1. 结论（先看这段）

「卡死」不是后端挂了，而是**控制台自己的三个独立缺陷叠在一起**。任何一个单独存在都不会让人觉得"永久死锁"：

| 你看到的现象 | 真正的机制 | 证据（本次实测/代码） |
|---|---|---|
| 界面点不动、白屏残影 | **所有后端探测都在 UI 线程同步执行**，一次点击可冻结 1s，启停可冻结 6~40s | 点「运维与告警」1011/1014/1022/1025/1087ms；点「总览」10/11/11/7/45ms |
| 关不掉（X 没反应） | `FormClosing` 把 X **改成了"最小化到托盘"**，唯一真退出在托盘右键菜单 | `launcher.ps1:4018-4024`、`:3979-3987`；托盘图标默认藏在溢出区时等于"没有退出入口" |
| 再点 bat 也没反应 | 单实例锁只做"把已有窗口提前"，bat 只用 `tasklist` 判**进程存活**，不判**窗口是否响应** | `:82-105`、`启动Papilot后台.bat:43-57`；boot 日志 19:25 `duplicate launch: activated existing window` |

并且**当时后端确实不在**：19:30 检查 `:8000` 无监听、进程表里没有 `account-server.js`；而日志显示今天启动过 4 次（18:13 / 18:55 / 19:03 / 19:17），**没有一次关机/停止记录**，`server-stdout.log` 为 0 字节。也就是说：后端反复"无声消失"，控制台则因为上面的缺陷在"坏状态"下越卡越死。

> 一句话：**后端病了，控制台把自己也拖死了，而且不告诉你它在干什么。**

## 3. 卡死是怎么发生的

### 3.1 常规刷新：每 3 秒一拍，一拍 2~3 次同步探测

```text
$timer(3s).Tick  →  Update-All
                     ├ Update-StatusUI   → Get-HealthCached(6)   → HTTP 1s   ← 探测①
                     ├ Update-TunnelUI   → /ready（400ms 硬超时，已做得好）
                     ├ Update-ChannelUI  → Get-HealthCached(10)  → HTTP 1s   ← 探测②
                     ├ Update-BillingUI  → Get-HealthCached(10)  → HTTP 1s   ← 探测③（计费页）
                     │                     + /api/plans 4s + /api/admin/payment 4s
                     └ Update-OpsUI      → Get-HealthCached(10)  ← 探测③（运维页）
                                           + backups 4s + alerts 4s + audit 4s
```

关键缺陷在 `Get-HealthCached`（`:2887-2899`）：**成功才写 `healthAt`，失败不写**。
于是后端一旦不可用，缓存彻底失效 → 每拍必定重发 2~3 次探测，永不退避。
v1.8.1 的"UI 线程纪律"只做了**限制超时**（1s/400ms），没有把 IO 移出 UI 线程，所以它的作用是"把伤害从 5 秒压到 1 秒"，而不是"消除伤害"。

### 3.2 启停/重启：最坏 40 秒的完全冻结

`Do-RestartServer`（`:3780-3799`）：

```powershell
Stop-Server                                   # Get-NetTCPConnection 1.2s + CIM 0.3s
for ($i=0; $i -lt 20; $i++) {
  if ((Get-PortOwnerPid) -eq 0) { break }     # ← 每次 Get-NetTCPConnection = 1.2s
  Start-Sleep -Milliseconds 500               # ← 睡在 UI 线程上，消息泵停转
}
Start-Server                                  # 再 1.2s + 0.3s
Update-All                                    # 再 2~3s
```

→ **6.4s + 1.7s×N（N 最大 20）≈ 最坏 40 秒**，期间窗口不重绘、不响应点击、不响应关闭，且 `lblMsg` 只在**操作结束后**才更新，用户看不到任何"正在处理"。
这就是"点了重启后台 → 整个窗口像死了一样"的完整解释。

### 3.3 后端"半死"：把 1 秒超时变成 100% 占空比

Node 是单线程事件循环。一旦它被同步 IO / 长任务卡住，**内核仍然会接受 TCP 连接**（backlog），但没人处理请求：

```text
后端卡住 → 连接能建、响应不来 → 每次探测吃满 1s
        → 3 次/拍 × 1s = 3s ≈ 3s 的定时器间隔
        → UI 线程 100% 占空比 → 窗口彻底不响应（但进程 Responding=True，任务管理器看着"正常"）
```

本次已用假后端（只 accept 不应答）复现了这条链路：3 次探测 3068ms。**这类"半死"正是最难自证的状态**，因为端口探测（150ms TCP）是通的，看起来"服务在跑"。

### 3.4 为什么"再点一次"毫无反应

1. 第二次启动 → `Mutex.WaitOne(0)` 失败 → `FindWindow` 找到那个**卡住的**窗口 → `ShowWindow + SetForegroundWindow` → 退出。
2. 卡住的线程没有消息泵，`SetForegroundWindow` 被排队但永远不处理 → 屏幕毫无变化。
3. `.bat` 随后只做 `tasklist /FI "PID eq <pid>"` 判活（12 次轮询），进程活着 → 认为"启动成功" → **静默 exit 0**。
4. 于是用户看到的是：双击 → 什么都没有 → 再双击 → 还是没有。

## 4. 触发条件与优先级

### 4.1 排序（按"冻结时长 × 发生频率"）

| # | 触发场景 | 冻结时长 | 发生频率 | 备注 |
|---|---|---|---|---|
| 1 | 点「重启后台」/「停止后台」 | **6~40s** | 后端异常时必然 | 每次排障都会点，最容易被记成"卡死" |
| 2 | 后端"端口在听但不答" | 持续 ≈100% 占空比 | 偶发但一旦发生就是"永久" | 本次复现证实 |
| 3 | 切到「计费与会员」/「运维与告警」 | 1~12s | 每次切页 | 计费页 4s+4s；运维页 3×4s |
| 4 | 保存类对话框（套餐/优惠券/用户编辑） | 最长 **30s** | 低频 | `Invoke-AdminApi` 的 `TimeoutSec=30`（`:409`） |
| 5 | WMI/CIM 查询 | 0.3s ~ 无限 | 每 30/60s | 无超时上限，WMI 异常时可拖死整个进程 |
| 6 | 移动硬盘 IO（H: 上的 jsonl/dist） | 秒级 | 低频 | 本次未找到磁盘告警事件，非主因，仍是风险 |

### 4.2 判断依据（为什么这么排）

1. **冻结时长**：40s 的冻结在体感上已经等同"死机"，1s 只是"卡一下"；优先消灭秒级以上。
2. **是否阻断逃生通道**：X 被改成"最小化到托盘"、托盘图标默认隐藏 → 用户既不能关也不能退，这是"卡死"观感的主要来源，必须与真卡死分开修。
3. **修复成本与风险**：改关闭语义、改 bat 判活、加负缓存，都是**几十行、零依赖、可回滚**；改成后台采集要动刷新模型，收益大但需要真机验证。
4. **可观测性缺口**：现在发生任何一次卡死都**没有证据留下**（无慢操作日志、无 hang 日志、服务端无崩溃日志），所以第二优先级是"让下一次能定位"，否则永远只能猜。

### 4.3 建议的动手顺序

> **P0（当天，先止痛）→ P1（本周，治本 + 留证据）→ P2（规划）**

## 5. 排查思路（下次 5 分钟定位）

### Step 0：先分清三类"卡死"

| 类别 | 判据 | 处置 |
|---|---|---|
| A. 假死（最小化到托盘） | 进程在、窗口 `visible=False`、UI 响应 <50ms | 点托盘图标；**不是 bug，是设计**（需要改交互） |
| B. UI 线程阻塞 | 窗口可见、`WM_NULL` 往返 >200ms | 看 §5 Step 2 判定树 |
| C. 进程真没了 | PID 不存在 / 窗口找不到 | 删 `%TEMP%\papilot-launcher.pid`，看 boot/error 日志 |

### Step 1：一条命令取证

```bash
python scripts\diag\console-probe.py            # 全量：窗口/控件/UI延迟/端口/HTTP/日志尾部
python scripts\diag\console-probe.py --lag-seconds 20
```

它会直接给出三个关键结论：UI 线程是否在泵消息、`/api/health` 单次耗时、`8000` 的 TCP 建连耗时。
（后两个数字决定"一拍能不能跑完"。）

补充命令：

```powershell
Get-Process -Id <pid> | Select Id,Responding,CPU,StartTime      # Responding=True 不代表没卡
Get-NetTCPConnection -LocalPort 8000 -State Listen              # 注意：这条本身要 1.2s
Get-Content $env:TEMP\papilot-launcher-boot.log -Tail 20     # 上次走到哪一步
Get-Content server\data\server-console.log -Tail 30
```

### Step 2：判定树

```text
UI 延迟 >200ms ?
├─ 是 → 正在执行什么？
│        ├─ 刚点过 启动/停止/重启 → 等它跑完（最坏 40s），期间不要重复点
│        ├─ 停在计费/运维页 → /api/admin/* 的 4s 超时在排队
│        └─ 什么都没点 → 后端"半死"，探测占满拍子 → 直接停后端或者杀控制台
└─ 否 → 窗口 visible?
         ├─ 否 → 最小化到托盘（点托盘 → 右键 → 退出程序）
         └─ 是 → 有模态框？看控件列表里是否有 disabled 的兄弟窗口/对话框
```

### Step 3：恢复动作（不误伤后端）

```powershell

Remove-Item "$env:TEMP\papilot-launcher.pid" -Force
# 账号后台是 cmd 拉起的独立进程树，杀控制台不会停后端（可用 :8000 验证）
```

然后再双击 `启动Papilot后台.bat`。

## 6. 治理方案

### P0（当天，低风险，先止痛）

**P0-1 关闭语义：让 X 真的能关**

```powershell
# 方案 A（推荐）：X = 退出（带确认），把"最小化"做成显式按钮
$form.add_FormClosing({
  param($s, $e)
  if ($script:allowExit) { return }
  $e.Cancel = $true
  if ([System.Windows.Forms.MessageBox]::Show(
        '退出控制台？（账号后台与公网通道会继续运行）', '退出', 'YesNo', 'Question') -eq 'Yes') {
    Exit-App
  }
})
```
并在标题栏/状态栏写明："关闭窗口 = 退出控制台，不影响后台服务"。
若坚持托盘驻留，至少做到：**启动即 `$tray.Visible = $true`**（不要等最小化才显示），并在首次隐藏时用气泡明确提示退出路径。

**P0-2 单实例判活：从"进程活着"升级为"窗口能应答"**

```powershell
# bat 侧在 tasklist 之后补一次窗口响应探测（PS 一行）
$ok = [PpWin32]::SendMessageTimeout($hwnd, 0, 0, 0, 2, 300, [ref]$r) -ne [IntPtr]::Zero
```
不响应时输出明确提示 + 给出 `Stop-Process -Id <pid> -Force` 命令，而不是静默 exit 0。

**P0-3 负缓存 + 退避：一拍最多探一次，失败后 5 秒内不重试**

```powershell
function Get-HealthCached {
  param([int]$MaxAgeSec = 6)
  $now = Get-Date
  if ($script:health -and ($now - $script:healthAt).TotalSeconds -lt $MaxAgeSec) { return $script:health }
  if (-not $script:health -and ($now - $script:healthFailAt).TotalSeconds -lt 5) { return $null }  # ★
  try { $h = Invoke-UiApi 'GET' '/api/ping' $null 1; $script:health = $h; $script:healthAt = $now; return $h }
  catch { $script:health = $null; $script:healthFailAt = $now; return $null }                     # ★
}
```

**P0-4 把 tick 里的"重查询"全部拿掉**

| 现在 | 改成 | 原因 |
|---|---|---|
| `Get-NetTCPConnection` 取 PID | 150ms `Test-PortOpen` 判活；PID 由 `/api/ping` 返回 `process.pid` | 省 1.2s/次，且不再依赖 WMI |
| `Get-CimInstance` 每 30/60s | 只在"端口不通但怀疑进程还在"时查一次（用户点刷新/启动时） | 无超时上限 |
| `/api/health`（会遍历 users/orders、stat 审计文件） | 新增轻量 `/api/ping`（只回 `ok/pid/uptime/lagMs`）给 3s 高频探测；`/api/health` 降到 10~30s | 健康时约 1.4 万次/天，后端一不可用就退化为 8.6 万次/天，且每次都在累加服务端事件循环负担 |

**P0-5 重启流程去掉 20×(1.2s+500ms)**

```powershell
$deadline = (Get-Date).AddSeconds(8)
while ((Get-Date) -lt $deadline) {
  if (-not (Test-PortOpen $Port 150)) { break }
  [System.Windows.Forms.Application]::DoEvents()        # 或直接改成后台等待
  Start-Sleep -Milliseconds 150
}
```

### P1（本周，治本 + 留证据）

**P1-1 探测搬离 UI 线程（PS 5.1 的正确姿势）**
注意：`System.Threading.Timer` / `BackgroundWorker.DoWork` 里**没有 runspace**，PowerShell 脚本块会报 "no Runspace available"。必须显式建 runspace：

```powershell
$ps = [PowerShell]::Create()
$ps.Runspace = [runspacefactory]::CreateRunspace(); $ps.Runspace.Open()
$ps.AddScript({ while ($true) { ... 采集 ... ; $sync.snap = @{...}; Start-Sleep -Seconds 2 } })
$ps.BeginInvoke()     # UI 定时器只读 $sync.snap 渲染，零 IO
```
若不想引入 runspace，退而求其次：**保底 P0-3/P0-4**，把一拍压到 ≤200ms。

**P1-2 慢操作日志（没有它就无法复盘）**

```powershell
$sw = [Diagnostics.Stopwatch]::StartNew()
Update-All
if ($sw.ElapsedMilliseconds -gt 800) { 追加 "launcher-slow.log: 耗时/当前页/阶段" }
```
另加 UI 看门狗：后台线程每 1s `SendMessageTimeout(WM_NULL, 200ms)`，两次不应答就写 `launcher-hang.log`。

**P1-3 服务端自证"我卡了"**

- `/api/ping` 返回 `lagMs`（100ms `setInterval` 的实际漂移）：>500ms 就是事件循环被堵。
- 控制台把这个数字直接显示在状态灯旁 —— 今天的故障本来可以被这一行数字秒定位。
- `process.on('uncaughtException' | 'unhandledRejection')` → 写 `server-console.log` 后 `exit(1)`。

**P1-4 停止也要留痕**
`Stop-Process -Force` 走 `TerminateProcess`，服务端的 `SIGTERM` 处理器（`account-server.js:3545`）永远不会执行 → 日志里没有 `shutdown`。请在杀之前由控制台自己写一条停机记录，别让"谁停的"永远成谜。

**P1-5 修日志双轨的漏网之鱼**
`scripts\start-server-hidden.vbs:45-46` 把 stdout 重定向到 **`server-console.log`**，与 1.8.0 定下的"stdout 必须独立落 `server-stdout.log`"冲突（cmd 的 `>>` 会独占句柄，Node 的 `log()` 静默失败）。走 HKCU Run 启动时，日志会不明不白地丢。

### P2（规划）

- **统一启动入口**：现在 `HKCU\...\Run` 里有 `PapilotAccountServer` + `PapilotTunnel`，控制台里又有 `AutoStartServices`，两条路会同时拉起 → 竞态、重复进程。二选一。
- **后端 watchdog**：`PapilotGuard` 计划任务已不注册，服务挂了没人管。建议"心跳文件 + 连续 N 次 `/api/ping` 超时 → 重启 + 写审计"。
- **长操作进度**：启动/重启的 6~40s 里应有不确定进度条 + 禁用按钮，而不是白屏。

## 7. 防复现（守卫与纪律）

**给 `check-wiring.py` 加 4 条静态断言**（成本极低，防回潮）：

1. `Invoke-RestMethod|Invoke-WebRequest` 的 `TimeoutSec` 必须 ≤ 2s —— 白名单放行 `Do-TestSite`(8s)、`Invoke-AdminApi`(30s，且必须在对话框里)。
2. `Update-All` 可达调用链里**禁止**出现 `Get-NetTCPConnection` / `Get-CimInstance`。
3. `Get-HealthCached` 的 catch 分支必须给 `healthFailAt` 赋值（负缓存不能删）。
4. `启动Papilot后台.bat` 的探活必须包含窗口响应判断，不允许只 `tasklist`。

**纪律**：

- 任何"点一下要等 >300ms"的操作，必须有可见反馈（按钮禁用 + 文案），否则用户一定当它死了。
- 任何在 UI 线程出现的网络/进程/文件调用，都按"它会卡 30 秒"来设计。
- 关窗语义必须与用户预期一致：**能关就是退出，不能退就要在 3 秒内让用户看见"它在哪"**。
