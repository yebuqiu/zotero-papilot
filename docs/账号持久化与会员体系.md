## 一、故障复盘：「每次更新 xpi 后登录信息就丢失」

### 1.1 现象

用户登录后在设置面板看到「✓ 登录成功」，正常使用；一旦安装新版 xpi（Zotero 必然重启），  
打开设置面板又变回未登录，需要重新输入邮箱密码。

### 1.2 取证过程

| 证据        | 位置                                                                                                                                                                          | 说明                                                                    |
| --------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------- |
| 会话文件不存在   | `C:\Users\Administrator\Zotero\papilot-account.json` 缺失                                                                                                                  | 数据目录里只有 `papilot-account.log` / `papilot-boot.log`，没有会话文件       |
| 配置目录也没有   | `…\Profiles\swc79sqh.default\` 下无 `papilot-account.json`                                                                                                                 | 双落点全空                                                                 |
| 日志全是「找不到」 | `papilot-account.log` 20 行，全部 `restore: no session file at any path`                                                                                                     | 从未出现过一次 `session saved`                                               |
| 其它模块能写    | `papilot-easyscholar.json`、`papilot-s2-citations.json` 都在                                                                                                             | 数据目录可写，排除权限问题                                                         |
| 写法唯一不同    | 只有 account.js 用 `IOUtils.writeUTF8(p, t, {mode, tmpPath})`，其余模块都用无选项的 `IOUtils.writeUTF8(p, t)`                                                                             | 见 §1.3                                                                |
| API 语义    | Zotero 自带 `chrome/content/zotero/osfile.mjs`：`if (options.encoding == 'utf-8') return IOUtils.writeUTF8(path, bytes, options);`；`Archive.worker.mjs` 用 `{ mode: "append" }` | `options.mode` 是**字符串开关** `"append"/"create"/"overwrite"`，不是 UNIX 权限位 |

### 1.3 根因

0.14.0 引入账号系统时，`_save()` 写成了：

```js
await IOUtils.writeUTF8(file, body, { mode: 0o600, tmpPath: file + ".tmp" });
```

`0o600` 是数字（384），而该字段要求字符串枚举 → **该次写入不产出文件**。  
更致命的是紧随其后的 `catch`：

```js
} catch (e) {
  Zotero.debug("Papilot: account session save failed: " + e.message);   // 只进调试控制台
}
```

**异常被吞掉，`login()` 照常 resolve**，所以界面显示「登录成功」；而磁盘上什么都没有。  
下一次启动（对用户而言总是伴随 xpi 更新）`restore()` 自然找不到文件 → 掉登录。

`test/legacy-rootcause.probe.js` 用同一套 mock 加载历史版本代码，把这条链跑成断言：

```
$ node test/legacy-rootcause.probe.js a8daa3e   # 0.14.0 初版
根因取证（参照 a8daa3e）：7 项复现，0 项不符
  ✓ 全部复现：登录成功 ≠ 会话落盘，且失败不可见 → 更新 xpi 后必然掉登录

$ node test/legacy-rootcause.probe.js HEAD      # 0.22.0（用户当前运行的版本谱系）
根因取证（参照 HEAD）：7 项复现，0 项不符
  ✓ 全部复现（该版本已有诊断日志，会记 save FAILED，但写入本身仍未修）
```

### 1.4 为什么前三次修复都没解决

| 版本     | 修了什么                                     | 为什么不够                        |
| ------ | ---------------------------------------- | ---------------------------- |
| 0.15.1 | 卸载钩子不再删会话文件；令牌 TTL 7 天→30 天滑动续期          | 会话文件**从来就没被写出来过**，删不删都无关     |
| 0.20.0 | 403 不再误判为会话失效；401 先复核一次；双落点；加 `_diag` 日志 | 仍然没碰 §1.3 的写入本身；只是让失败「有日志可查」 |
| 0.20.0 | `restore()` 本地判过期不再删文件                   | 方向对，但文件不存在，无从谈起              |

**结论：症状的成因一直在写入侧，而不是清理侧。** 本版把写入侧彻底重做。

## 二、客户端会话持久化方案（v2 多代冗余仓库）

### 2.1 存储布局

```
<Zotero 数据目录>/           ← Zotero.DataDirectory.dir（本机 = C:\Users\Administrator\Zotero）
  papilot-account.json      第 0 代（最新）      ← 旧版单文件即此路径，天然兼容
  papilot-account.1.json    第 1 代
  papilot-account.2.json    第 2 代
  papilot-account.log       生命周期诊断日志（串行写、上限 400 行）
<Zotero 配置目录 ProfD>/       ← 互为兜底的第二落点
  papilot-account.json / .1.json / .2.json / .log
```

**最多 6 份会话副本。首次成功登录即写满 6 份**（没有旧代际时用新内容填充 gen1/gen2，  
见 `_rollDir(paths, fresh)`），所以「刚登录就出故障」的场景同样有 2 份以上可恢复。

### 2.2 文档结构（v2 信封）

```jsonc
{
  "schemaVersion": 2,          // 版本信封，v1 文档无此字段
  "app": "papilot",
  "token": "pp-…",             // 服务端仅存 sha256 散列
  "expiresAt": 1790000000000,  // 本地毫秒时间戳（与服务端 30 天滑动对齐）
  "user": { "email": "…", "name": "…", "plan": "Pro",
            "membership": { "plan": "Pro", "expiresAt": "…", "daysLeft": 88 } },
  "savedAt": 1787000000000,    // 代际排序依据（核心）
  "reason": "login"            // login / refresh / touch / redeem / membership-refresh
}
```

会员信息随会话一起落盘 → **离线也能正确显示等级与到期日**。

### 2.3 写入流程（`_writeDoc`）

对每个落点：

1. **代际滚动**（`_rollDir`）：先读完 gen0/gen1，再 `gen1 ← 旧 gen0`、`gen2 ← 旧 gen1`；  
   没有旧代际时用新内容填充（保证首次即有 3 代）。
2. **写第 0 代**（`_writeFile`）：先带 `tmpPath` 原子写（写一半崩溃不留半截文件），  
   失败回退**无选项直写**（本插件其余模块长期验证可用的形态）。
3. **回读校验**：写完全文读回比对，`写成功但内容不符`同样判失败，绝不谎报。
4. 全程 `_withTimeout` **硬超时 8s** —— 杜绝「IO 永不 resolve」把登录卡死且无日志。

结果写入 `Account.persistStatus = {attempted, ok, wrote, total, at, errors[]}`。

### 2.4 读取流程（`restore()`）

1. 收集**全部 6 个候选**（落点 × 代际），逐个 JSON 解析；解析失败的**保留现场不删**并记日志。
2. **按 `savedAt` 降序，最新者胜**（取代旧实现的「按路径顺序取第一个就 break」）。
3. 最新副本是 `revoked` 墓碑 → 保持登出（并把其余落点也写墓碑，防止复活）。
4. 否则装载会话；**本地判过期不再直接放弃**，交 `refreshUser()` 的服务端 401 定论  
   （首答 401 还会隔 900ms 复核一次）。

### 2.5 登出 / 会话失效 = 墓碑清除（`_wipe`）

关键点：**必须覆盖全部代际**。只删第 0 代的话，第 1/2 代里的旧令牌会在下次启动被读出来，  
产生「登出后重启又自动登录」。墓碑文档 `{revoked:true, savedAt, reason}` 同时做到：

- 令牌**物理清除**（磁盘上不再有任何有效令牌）；
- 留下「已登出」的证据，阻止另一落点的残留副本复活会话。

触发场景：用户点「退出登录」、`AIClient` 官方通道 401、`refreshUser` 连续两次 401。

### 2.6 故障与降级矩阵

| 故障             | 行为                                                                       |
| -------------- | ------------------------------------------------------------------------ |
| 单个落点写失败        | 另一落点照常写；`persistStatus.wrote = 1/2`；登录不受影响                               |
| 全部落点写失败        | 本次运行内仍可用（内存会话）；`persistStatus.ok = false`；**设置面板显示橙色告警条**说明「重启后需重新登录」及原因 |
| 第 0 代被删 / 损坏   | 从第 1 代自动恢复                                                               |
| 数据目录整体丢失       | 由 ProfD 落点兜底                                                             |
| 两落点不同步         | 按 `savedAt` 取最新，不再被旧副本遮蔽                                                 |
| 写操作挂起          | 8s 硬超时判定失败并回退，不留静默死锁                                                     |
| 服务端 401        | 复核一次，仍 401 才清会话（且走墓碑）                                                    |
| 服务端 403 / 网络异常 | **不清会话**（WAF/反代拦截不代表令牌失效）                                                |

## 三、跨版本迁移策略

### 3.1 客户端（会话文件）

| 起点                                         | 迁移动作                                                                                                                   | 幂等性                |
| ------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------- | ------------------ |
| 无任何文件（本机现状）                                | 首次登录直接按 v2 写满 2 落点 × 3 代                                                                                               | 天然幂等               |
| v1 单文件 `{token, expiresAt, savedAt, user}` | `restore()` 直接按兼容字段读取（无 `schemaVersion` 视为 v1）；会话装载后 `refreshUser` 触发的第一次保存把 gen0 升级为 v2，**旧内容原样滚入 gen1/gen2 作为可回滚备份** | 幂等：每次读取都容错，每次写入都滚动 |
| v2                                         | 无操作                                                                                                                    | —                  |
| 用户在旧代际里手动改过内容                              | 不适用（文件仅插件读写）                                                                                                           | —                  |

**回滚路径**：`papilot-account.1.json` / `.2.json` 保留了上两代原文，  
必要时把 `.1.json` 改名为 `.json` 即可回到上一次会话状态。

### 3.2 服务端（会员数据）

| 数据                           | 迁移动作                                                                                                                                                                      |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `users.json`（既有用户）           | **不迁移结构**。会员权威信息写在 `user.membership`，`user.plan` / `user.expiresAt` 作为兼容镜像同步维护；旧数据没有 `membership` 字段时，`membershipOf()` 会从 `plan`/`expiresAt` 现场合成视图，`source` 标记为 `legacy` |
| 既有 `Free/Pro/Team` 中的 `Team` | 新体系只保留 `Free`/`Pro`。存量 `Team` 用户在 `membershipOf` 中按 `user.plan` 原样展示，额度取不到配置时回落 Free 额度；管理端下拉不再提供 `Team`                                                                  |
| `membership.json`            | 首次启动用 `newDoc()` 落默认配置；`normalize()` 补齐缺失字段并把 v1 升为 v2（**幂等**，每次启动都安全调用）                                                                                                  |
| 每日额度口径变化（已废止） | 1.8.0 起**取消每日调用次数上限**（`plans[].dailyLimit` / `user.dailyLimit` 全部下线）：AI 调用统一从余额扣费，余额不足 402。旧数据里的 `dailyLimit` 字段由 `normalize()` 启动时清掉 |

### 3.3 插件升级时的数据边界（为什么不会再丢）

- 会话文件位于 **Zotero 数据目录 + 配置目录**，不在 xpi 内，升级 xpi 不会触碰。
- `bootstrap.js` 的 `uninstall` 钩子**明确不删**会话文件（更新/重装路径会触发 uninstall）。
- 即使某一份被外部清理（同步工具、清理软件、误删），仍有 5 份可恢复。
- 升级后启动日志（`papilot-boot.log`）新增一行会话仓库自检：  
  `account store: dirs=2 copies=6 newest=数据目录#0 savedAt=… loggedIn=true`  
  —— 以后再出现「掉登录」，**第一段启动日志就能给出结论**。

## 四、会员体系

### 4.1 等级与权益（配置化，后台可改）

| 等级           | AI 额度（余额） | 官方模型范围       | 价格（默认档位）                         |
| ------------ | -------- | ------------ | -------------------------------- |
| **Free** 免费版 | 注册赠送 ¥6（30 天，限基础模型） | 基础模型 + `auto` | 免费，登录即用                          |
| **Pro** 专业版  | 每月发放 ¥8（后台可配 0～1000 元，0=停止；不结转，全模型可用） | 全部（含推理档 / 长上下文） | 1 个月 ¥29 / 3 个月 ¥79 / 12 个月 ¥269 |

> 1.8.0 起不设每日调用次数上限：所有 AI 调用按真实成本从余额扣减（注册赠送 → 订阅额度 → 充值）。

- 所有额度、价格档位、权益文案、收款信息都存 `server/data/membership.json`，  
  通过 `PUT /api/admin/membership` 修改，**改完即刻生效，不需要重启服务端**。
- **官方模型按套餐分级见 §4.12**（服务端 1.4.9）。用户可用的模型范围由
  `channels.json.highTierModels`（哪些模型算高级）× `plans[].highTierModels`（哪个档能用高级）共同决定，
  并叠加「新用户全模型试用」。
- **自带 API Key（自有通道）始终不受任何限制** —— 那条链路不经过本服务端，
  既收不到钱也管不到；限制它只能拦住老实用户（详见 §4.12 的设计取舍）。
- ⚠️ **口径变更说明**：本节此前写的是「未购买 Pro 的用户**不受任何功能门禁限制**，只是额度更低」。
  1.4.9 起**官方模型范围成为付费差异**（这正是 Pro 卖点里「高级模型（推理档 / 长上下文）」的兑现），
  其余功能仍然无门禁。

### 4.2 购买流程（收款码 + 订单核销）

```
插件设置面板                     服务端                       管理员
─────────────                  ─────────                   ─────────
点「升级专业版」
选价格档位 ────────────────► POST /api/orders
                             创建订单(pending)
                             ← 订单号/金额/收款信息
展示订单号 + 收款码
扫码付款
点「我已完成支付」 ─────────► POST /api/orders/:id/claim
                             status: pending → claimed
（面板每 6s 轮询） ◄──────── GET /api/orders/:id
                                                    ► /admin 或启动管理器看到「待核销」
                                                    POST /api/admin/orders/:id/fulfill
                             开通会员 + 生成已用兑换码留档
面板轮询到 fulfilled ◄─────── order.status = fulfilled
自动刷新会员卡片
```

- 订单**绑定下单账号**，核销即自动开通，用户不需要再输任何码。
- 未支付订单 7 天后自动过期（`reapOrders` 惰性回收，列表接口顺带落盘）。
- 核销同时生成一枚**已使用**的兑换码留档，便于对账。

### 4.3 激活方式（两种并存）

| 方式        | 适用场景            | 入口                       |
| --------- | --------------- | ------------------------ |
| **订单核销**  | 插件内自助购买         | 设置面板 → 会员卡片 → 升级专业版      |
| **激活码兑换** | 线下售卖、赠送、补偿、渠道分成 | 设置面板 → 会员卡片 → 「有激活码？」输入框 |

激活码规则：

- 格式 `PP-XXXX-XXXX-XXXX`，字母表剔除易混字符（无 `0 O 1 I L`）。
- 兑换时**大小写与连字符都不敏感**（`pp xxxx xxxx xxxx` 同样识别）。
- 可绑定指定账号（`boundTo`），也可作为通用码；一经使用即绑定使用者。
- 支持 `expiresAt`（活动码有效期），已使用的码不可删除（保留对账记录）。

### 4.4 有效期管理

**续期 = `max(现在, 现有到期) + 时长`** —— 剩余时长不会被吞。

例：Pro 还剩 20 天 → 买 1 个月 → 新到期 = 今天 + 20 天 + 30 天 = 50 天后。

| 场景             | 行为                                                             |
| -------------- | -------------------------------------------------------------- |
| 到期未续费          | **不踢下线**，`plan` 有效值回落 Free、额度回落 100；插件会员卡片显示红色「已到期」            |
| 剩余 ≤ 7 天       | 会员卡片转警示色「仅剩 N 天 · … 到期」，提示续费                                   |
| 服务端 `daysLeft` | 由 `/api/auth/me` 与 `/api/membership` 下发，客户端同步落盘，离线可显示          |
| 管理员手改到期日       | 走 `syncMembershipFromLegacy`，**覆盖式**（以填写的日期为准，不叠加）—— 后台手改即最终裁决 |

### 4.5 价格表（服务端 1.4.1 新增：等级 × 计费周期 × 生效时段）

价格不再是一张「月数 → 价格」的平铺表，而是一个**价格条目**集合，每条 = 一个等级的某个计费周期在某段生效时间内的售价：

```jsonc
{
  "id": "pr-3f9a1c2b", "plan": "Pro",
  "cycle": "yearly",              // monthly / quarterly / halfyear / yearly / custom
  "months": 12, "price": 269,     // 该周期总价（一次付费覆盖 12 个月）
  "label": "按年 · 省 ¥79",
  "effectiveFrom": null,          // null = 立即生效
  "effectiveTo": null,            // null = 长期有效
  "enabled": true, "priority": 0, // 时段重叠时高者胜
  "note": ""
}
```

**三条关键规则**

1. **生效时段决定可见性**：生效中 → 可下单；`effectiveFrom` 在未来 → 客户端只看到「即将生效」预告、不可下单；
   已过期 → 完全不下发，只留在后台存档（所以可以「先把明年涨价的价格配好」）。
2. **允许时段重叠，按优先级决出唯一胜者**：`priority` 高者胜 → 起期晚者胜 → 新建者胜。
   因此「长期基础价 `priority 0` + 限时促销价 `priority 1`」可以共存：促销窗口内自动覆盖，
   窗口一过自动回到基础价，**不需要**把基础价切段（切段极易留下空档，让某个周期突然不可购买）。
   客户端每个周期只会拿到胜者那一条，不会出现两个价。
3. **下单取价只有一个口径**（`effectivePrice()`）：在该等级生效中的条目里精确匹配周期月数 →
   多条时取胜者；该等级有生效价但没有这个周期 → **明确报错**（不让用户买到后台没配的周期）；
   一条生效价都没有 → 退回「等级单月价 × 月数」兜底（兼容未配置价格表的老数据）。
   订单同时落 `priceItemId` / `cycle` / `unitPrice` / `priceSource` 四个字段，
   **日后改价不影响历史订单**，也能回答"这单为什么是 ¥19"。

**空档预警**：若某条价格设了 `effectiveTo`，而之后没有任何启用的价格接续，写入接口会返回
`warn`（不拦截，但后台会提示），避免悄悄把某个周期卖死。

> 兼容性：`priceOptions`（旧版平铺档位）降级为 **`priceItems` 的派生只读视图**，
> 每次写入后重算、只含**生效中的胜者**，因此已发布的插件版本继续正常显示价格。
> v2 文档首次加载时自动迁移为 v3（把旧的 `priceOptions` 转成价格条目，id 形如 `pr-migrated-pro-1`），幂等。

### 4.6 到期提醒与一键续费（插件 0.24.4）

面板会员卡上的**到期横幅**与**启动提示**共用同一套判定（`Account.renewalReminder()`）：

| 场景 | 表现 |
|---|---|
| 剩余 > 7 天 | 不打扰（只在卡片上显示"剩 N 天"） |
| 剩余 ≤ 7 天 | 卡片下方出现**可点横幅**「⏳ 仅剩 N 天（<日期> 到期）—— 点此续费，时长可叠加」 |
| 已到期 | 横幅转红并改文案「⚠ 会员已于 <日期> 到期，当前为免费版 —— 点此续费立即恢复」 |
| 剩余 ≤ 1 天或已过期 | 启动后额外用系统提示弹一次 |

两条防打扰规则：

- **同一到期周期只提示一次** —— pref `renewPromptShownFor` 记住 `expiresAt`；续费后 `expiresAt` 变化，
  下一周期到点会重新提醒，但同一个到期日绝不会重复弹。
- **主窗口还没就绪时不落标记**（直接留给下次），避免"没弹出来还把标记写掉、永久静音"。

点横幅 = 打开续费面板，并把**默认档位设为上次购买的周期**（`membership.history` 里最近一次的 `months`）——
买过 12 个月的用户续费时默认就选中"按年"，不用每次重新挑。

**免费用户不会被骚扰**：`expiresAt` 为空即无到期概念，横幅与提示都不触发。

### 4.7 用量趋势（服务端 1.4.3 / 插件 0.24.4）

`user.usage` 从「当日计数」扩展为「当日计数 + 近 30 天按日」：

```jsonc
"usage": { "date": "2026-10-03", "count": 5,          // 旧字段原样保留
           "daily": { "2026-10-01": 12, "2026-10-02": 7, "2026-10-03": 5 } }
```

- `daily` **只保留最近 30 天**（写入时顺手淘汰更早的键），键为本地时区的 `YYYY-MM-DD`（与 `today()` 同口径）。
- **旧数据无需迁移**：只有 `{date,count}` 的老账号由 `usageDays()` 现场兜底（那一天读 `count`）。
- 下发口径：`/api/auth/me` 与 `/api/membership` 的 `user.usage = { today, limit, last7, days[30] }`，
  `days` 缺口补 0 → 前端拿来就能画。
- 插件会员卡据此画**纯 CSS 迷你柱状图**（7 天）+「今日 N / 额度 · 近 7 天合计 M 次」；
  **老服务端没有趋势数据时整块隐藏**，不画空图。
- 后台：用户表新增「近 7 天」列，并有「导出用量 CSV」（带 BOM，含近 30 天按日明细）。

### 4.8 永久会员（服务端 1.4.5 / 插件 0.24.5）

会员多了一种**计费周期**：`perpetual`（永久）。实现上就一句话 —— **`months` 恒为 0 表示「不适用」**，
授予时把 `expiresAt` 置空（而不是设一个很远的未来）。

| 位置 | 表现 |
|---|---|
| 价格条目 | `{plan:'Pro', cycle:'perpetual', months:0, price:128, label:'永久'}` |
| 下单 | `POST /api/orders {plan:'Pro', cycle:'perpetual'}`（不带 months） |
| 会员 | `expiresAt: null`、`daysLeft: null`、`perpetual: true`；`plan` 恒为 Pro（**不会被判过期**） |
| 插件 | 档位卡显示「永久 · ¥128」（不显示折合月单价）；会员卡显示「永久有效（无需续费）」；到期提醒自然不触发 |
| 后台 | 价格表单选「永久」时月数自动置 0 并禁用；开通/续期弹窗有「永久会员（不设到期日）」勾选 |

三条容易踩的规则：

- **`months = 0` 不能走 `clampMonths`**（它会把 0 抬成 1）→ `sanitizePriceItem` / `effectivePrice` /
  `createOrder` 都**先判周期再决定是否 clamp**。永久取价必须命中价格条目，**不允许按单月价折算**（会算成 ¥0）。
- **永久不被月数续费降级**：`grantMembership` 里 `keepPerpetual = 本次买永久 || 当前已是永久`，
  已永久用户再买 3 个月仍然是永久（否则一次误操作就把用户的永久权益吃掉）。
- **`membershipOf().perpetual` 的判据是「等级非 Free 且无到期日」** —— Free 用户本来就没有到期日，不能算永久。

### 4.9 收款流水自动对账（服务端 1.4.5 / 插件 0.24.5）

**要解决的问题**：人工核销是运营瓶颈 —— 用户付了钱要等人点一下，夜里下单就干等。

**做法（零支付资质）**：下单时给每笔订单分配一个**同金额内唯一的小数尾数**：

```
Pro 永久 ¥128  →  订单 A 实付 ¥128.62
               →  订单 B 实付 ¥128.35
```

于是收款流水**按金额就能唯一确定订单**，既不需要用户在备注里写订单号，也不需要对接支付网关。

**尾数分配（`membership.assignTail`）**：范围 1..99 分；**只有 pending/claimed 的订单占用**，
核销或取消后尾数自动回收；随机起点 + 线性探测（尾数分散、不易被猜）；99 个用尽时**明确报错**，
而不是把两笔订单做成同一个金额（那会让对账无法区分）。

**匹配（`server/lib/reconcile.js`，纯函数、可单测）**：

| 情况 | 结果 |
|---|---|
| 金额精确相同 + 订单未完成 + 落在时间窗内 | `matched`（唯一命中） |
| 金额对不上（含多付/少付、只按整数付） | `unmatched`（**刻意不做模糊匹配**，防错） |
| 同一批流水里同一订单被匹配两次 | `duplicate`（不会核销两次） |
| 命中多笔（历史遗留的同价订单） | `ambiguous` → **不自动核销**，列出候选交人工 |
| 订单已是 fulfilled / cancelled | `unmatched`，并提示「已完成/已取消」 |

时间窗默认 30 天（`windowDays` 可调），并给两端时钟偏差留 10 分钟余量。

**接口与入口**：

- `POST /api/admin/reconcile` body `{text|entries, dryRun, windowDays}` —— **默认 `dryRun` 预览**，
  必须显式传 `dryRun:false` 才真核销；核销语义与管理员手动核销完全一致（叠加开通 + 留档一枚已用码），
  并写审计 `order.reconcile`。
- Web 管理页「订单 → 对账导入」、启动器「会员管理 → 订单 → 对账导入」：粘贴流水 → 预览 → 确认核销。
- CLI：`node scripts/reconcile.js payments.txt [--apply] [--window 30]`。
  **走 HTTP 接口而不是直接改 `server/data/*.json`** —— 运行中的服务端在内存里持有权威副本，
  直接改文件会被它下一次 `save()` 覆盖（甚至丢掉本次核销）。

流水格式（每行一条，时间与备注可空；容忍 `¥` 与全角逗号）：

```
128.62,2026-10-03 12:30,微信,4200001234
29.48
```

> 与「人工核销」的关系：两条路完全等价、可混用。对账只是把「人去点核销」换成「按金额自动点」，
> 所以它是**可选的加速器**而不是唯一通道 —— 以后接支付回调（建议 #6 第二步），也复用同一个核销入口。

### 4.10 优惠券 / 折扣码（服务端 1.4.6 / 插件 0.24.6）

**先说与激活码的分工** —— 这两件事很容易被混在一起，但语义完全不同：

| | 激活码 `codes` | 优惠券 `coupons` |
|---|---|---|
| 作用 | **直接发会员**（开通 / 叠加续期） | **只打折**，会员仍靠订单核销开通 |
| 是否走订单 | 否 | 是（下单 → 收款 → 核销，一步不少） |
| 是否涉及收款 | 否 | 是（把应付金额降下来） |
| 典型用途 | 赠送 / 补偿 / 线下售卖 | 促销 / 首发优惠 / 老用户回馈 |

**想免费送用激活码，想让人少掏点钱用优惠券。** 系统里做了硬隔离：折扣上限 **99%**，
折后至少留 **¥1**（`MIN_PAYABLE_CENTS`）—— 100% 减免一律拒绝，避免把优惠券用成「免费的会员发放器」。

**券的形态**（存在 `membership.json` 的 `coupons` 数组，与 orders 同一份文档）：

```jsonc
{ "id": "cp-3f8a1c2b4d", "code": "CP-4DX7-YKGC-FTD4",
  "type": "percent" | "amount",      // 按比例减免 / 固定金额减免
  "percent": 25, "amountCents": 0,   // percent 型用 percent；amount 型用 amountCents（分）
  "plans": [],                       // 适用等级（空 = 全场可购等级通用）
  "minAmountCents": 5000,            // 门槛：折前金额需 ≥ 此值（0 = 无门槛）
  "maxUses": 100, "perUser": 1,      // 可用总次数（0=不限）/ 每人限用（0=不限）
  "effectiveFrom": null, "effectiveTo": "2026-11-15T00:00:00.000Z",
  "enabled": true, "note": "国庆活动", "createdAt": "…", "createdBy": "admin",
  "uses": [ { "orderId": "o-…", "userId": "u-…", "email": "a@b.c",
              "at": "…", "discountCents": 6725, "state": "used" } ] }
```

#### ★ 三个刻意的设计决定（改动前先读这段）

**1）名额是「占用 → 核销消耗 / 取消释放」，而不是「下单即消耗」。**
用户点几下就能生成订单，如果下单即消耗，限量券会被瞬间耗光。
所以：下单 → `reserveUse`（`state:'reserved'`）；核销 → `consumeUseByOrder`（`'used'`）；
用户取消 / 管理员取消 / 订单超时回收 → `releaseUseByOrder`（`'released'`，不再计入额度）。
`usedCount()` 只统计**未释放**的占用，因此 `maxUses` 与 `perUser` 的口径都是「真实被占住的名额」。

**2）尾数必须在折后金额上分配。**
实付 = 折后价 + 唯一对账尾数（见 4.9）。若按折前价分配尾数，两张「折前同价、用了不同券」的订单
会落到同一批尾数上，「按金额唯一对账」立刻失效。所以 `createOrder` 的顺序是
**先算折扣 → 再 `assignTail(折后价)`**；订单字段拆成
`originalCents`（折前）/ `discountCents` / `baseCents`（折后）/ `tailCents` / `amountCents`（实付）。
`amount`（元）仅作旧 UI 兼容 —— **断言与对账一律用「分」**。

**3）下单后不再复核券的状态。**
券被停用、额度改小、过期，**都不影响已经下过的单**（那些单已在 `uses` 里占了名额）。
否则会出现「用户已付款、管理员停券、订单核销不了」—— 把钱卡在中间是最糟的结果。

#### 校验与报价

下单与「试算」共用同一个 `coupon.quote()` 口径（`POST /api/coupons/validate` 与 `POST /api/orders` 走同一段代码），
所以**试算价永远等于下单价**。校验顺序：码格式 → 存在 → 状态 → 等级范围 → 门槛 → 每人限用 → 折前金额 → 折扣额。

- 状态机五态：`active` 生效中 / `scheduled` 未生效（起期在未来）/ `expired` 已过期 /
  `disabled` 已停用 / `exhausted` 名额用尽；另有 `invalid`（数据被手改坏）。
  判据顺序：**停用 > 配置异常 > 未生效 > 已过期 > 用尽 > 生效中**。
- 金额字段**越界一律拒绝，不做静默夹取**（把 150% 悄悄变成 99% 比直接报错危险得多）。
- 批量生成前先拿一张试校验，参数非法就地报错 —— **不留半成品**（旧写法会先 push 几枚再报错）。
- 券码归一与激活码同规则：大小写、连字符都不敏感；字母表剔除 `0 O 1 I L`。

#### 管理侧的两条保护

- 已被使用/占用的券**不能删除**（`activeUses > 0` 直接拒绝）—— 那些占用挂在待核销订单上，
  删掉会让订单的折扣来源凭空消失、对账对不上。需要停发用**停用**（只影响新订单）。
- 审计记 `coupon.create` / `coupon.update` / `coupon.revoke`；`create` 只记配置与数量
  （批量生成不逐条落码值，否则审计日志就成了码本）。

### 4.11 登录设备与会话管理（服务端 1.4.7 / 插件 0.24.7）

**动机**：`tokens` 表此前只有 `{userId, expiresAt}` —— 同一账号可以从任意多台机器无限次登录，
服务端**完全无法区分「两台机器」和「一台机器」**。共享账号（一个人买 Pro 给整个课题组用）因此不可见，
用户也无从自查「我在几台机器上登录着」。

#### ★ 先纠正一个容易做错的语义

**「同时在线设备数」在现有模型里没有可实现的定义。** 令牌是 30 天滑动续期、靠请求续期，
用户关掉 Zotero **并不会"下线"**。能真正实现的只有两种判据：

1. **活跃设备数**：最近 N 天内有请求的令牌数（本版采用，语义诚实、可实现）
2. 并发在途请求数（需要额外计数，暂不做）

所以界面上写的是「**活跃设备 N 台（阈值 M 台 / 窗口 D 天）**」，而不是「在线设备」。

#### 记录了什么

令牌记录新增可选字段（**无需迁移**，老令牌首次读取时现场补齐）：

```jsonc
// users.json → tokens[<sha256>]
{ "userId": "u-…", "expiresAt": 1730000000000,
  "sid": "a1b2c3d4",          // 对外会话 id = 令牌散列前 8 位（不可反推令牌）
  "createdAt": "…", "createdIp": "203.0.113.45",
  "lastSeenAt": "…", "lastSeenIp": "…",
  "deviceId": "…uuid…",       // 插件上报（0.24.7 起）；缺失即视为"未识别设备"
  "deviceLabel": null, "platform": "Windows 11", "zoteroVersion": "10.0.5" }
```

写入点全是**既有钩子**，没有新增定时器：`issueToken()` 写设备与起始信息；
`touchToken()` / `touchTokenSoon()` 在续期的同时更新 `lastSeenAt`（网关高频路径复用既有的 30s 落盘节流，
**不因记录活跃时间而增加写盘频率**）。

#### 三条刻意的设计取舍

1. **只观测，不处罚。** 超阈值只写 `alerts.log` + 发管理员邮件 + 在后台标红；
   「踢设备」是**显式动作**，绝不自动踢下线、绝不自动降级。
   理由：同一人「台式 + 笔记本 + 实验室机器」很常见，而共享账号的损失远小于误封一个真实付费用户；
   自动处罚不可逆、客服成本高。**要处罚也必须是人工确认后的动作。**
2. **脱敏分层。** 用户看自己的设备 → **IP 打码**（`203.0.113.*`），且响应里**不含完整令牌散列**；
   只有仅本机直连的管理接口 `/api/admin/users/:id/sessions` 才返回完整 IP（出事时要能追）。
   原始 IP 只落在 `users.json`。审计沿用既有行为记录来源 IP（便于追查），但不记令牌。
3. **设备标识不是凭据。** `deviceId` 由插件本机生成、可伪造，**只用于展示与异常检测**，
   绝不参与鉴权。形状不合的上报（例如带路径分隔符）一律丢弃，不写进用户数据。

#### 踢出 = 删令牌（链路早已就绪）

`DELETE /api/sessions/:sid` 删掉该令牌 → 客户端下次请求吃 **401** → 走既有的墓碑清会话并提示重新登录。
**不需要任何新机制**。踢自己 = 登出（返回 `self: true`）。

两条一致性约束（都有回归测试守着）：

- **展示与撤销必须用同一个 sid 取值来源**（`sidOfRec` = 记录里的 `sid`，缺失才由令牌散列推导），
  否则会出现「界面看得见、却怎么都踢不掉」的设备。
- **踢出只处理仍然有效的令牌**：与设备列表口径一致，这样「已踢出 N 台」的提示不会跟用户数出来的台数对不上。

#### 插件侧（0.24.7）

- **本机生成一次 `installId`**（随机 UUID，存 pref）并随每个请求上报 `X-PP-Device` /
  `X-PP-Platform` / `X-PP-Zotero`。设备头在 `_request()` 里**统一注入**，不是每处手写 ——
  避免将来新增接口时漏传导致「设备识别时有时无」。
- **`installId` 不是凭据**（可伪造，只用于展示与异常检测）。它是**非敏感标识**，放 pref 与
  「令牌绝不进 pref」那条纪律不冲突（令牌是凭据，这个不是）。
- **不上报主机名**：本机拿不到可靠主机名（Zotero 10 的 Firefox 基座已移除 `Services.sysinfo`），
  所以**设备名由用户自己起**（`PUT /api/sessions/:sid {label}`，≤40 字符，空串 = 清除）。
  这既达到「认出是哪台机器」的目的，又符合最小必要原则。
- 设置面板新增「登录设备」块：显示活跃设备数/阈值/窗口、逐台显示设备名 · 平台 · 最近活动 · 打码 IP，
  可「重命名」「踢出」，以及「踢出其他设备」。当前设备标「（本机）」且**不给踢出入口**
  （要退出请用登出，避免误操作）。
- 老服务端没有该接口时**整块隐藏**，不报错占屏；异步失败也只在内部吞掉 ——
  `renderAll()` 是同步调用它的，若让异常逃逸会变成未捕获的 Promise 拒绝（Zotero 里是控制台噪音）。
- 提示框走既有的 `Services_promptConfirm` / 新增的 `Services_promptInput` 安全包装，
  **不用裸 `window.prompt`**（面板作用域没有 `Services`，裸调用在 Zotero 里不可靠）。

#### 与「改密 / 重置密码」的关系

改密与管理员重置密码**仍然一次吊销该账号全部设备**（既有语义不变）。
两者的分工：想**精确**踢一台用「踢出设备」；想**一刀切**（怀疑整体被盗）用重置密码。

### 4.12 套餐 AI 能力：官方模型分级与全模型试用（服务端 1.4.9 / 插件 0.24.8）

**要解决的问题**：Pro 卖点里一直写着「高级模型（推理档 / 长上下文）」，但**从未实现**——
`plans[].highTierModels` 这个字段存在、也下发给客户端了，全仓库却没有任何一处读它。
与此同时 `/v1/models` 返回的是**全局**上线清单，所以免费用户事实上能直接选用最贵的模型。

**三个概念（务必分清，改配置前先读）**

| 配置项 | 位置 | 管什么 | 留空/默认 |
|---|---|---|---|
| `publishedModels` | `channels.json` | **对外可见可调用的范围**（分批发布用） | 空 = 全部上线 |
| `highTierModels` | `channels.json` | 其中**哪些属于付费档**（是 `publishedModels` 的子集） | 空 = 不做分级，全部免费 |
| `plans[].highTierModels` | `membership.json` | **哪个等级能用高级模型** | Free `false` / Pro `true` |
| `ai.trialDays` | `membership.json` | 新用户「全模型试用」天数 | `7`（`0` = 关闭） |

**★ `auto` 恒定免费**，即使被误配进高级清单也不锁。它映射到活动通道的默认模型，
是**全体用户的兜底入口**——把它锁掉等于一次误配锁死所有免费用户。这条有专门断言守着。

**解析规则**（`highTierAccess()`）：

```
可用高级模型 ⇐ 套餐自带（plans[].highTierModels）
              ∨ 新用户试用中（now < user.createdAt + ai.trialDays 天）
              ∨ 否则不可用
```

**双层强制**

| 层 | 做什么 | 可信度 |
|---|---|---|
| 服务端 `/v1/*` | `/v1/models` 按套餐返回；`chat/completions` 显式调高级模型 → **403 + `code: MODEL_REQUIRES_PRO`** | ✅ 权威，改插件也绕不过 |
| 插件端面板 | 官方模型下拉只列可用模型，需升级的以 **🔒 灰显**列出；点它会被拦下并提示升级 | ⚠️ 仅体验/引导，可绕过 |

**为什么是「明确拒绝」而不是「静默换成便宜模型」**：静默降级会让用户以为自己在用所选模型，
比报错危险得多（与金额字段「越界一律拒绝、不做静默夹取」同一条纪律）。
403 文案同时给出**当前可用**与**升级后可用**两份清单，插件端据此提示。

**试用期取「注册时间 + 天数」现场计算** ⇒ **零迁移、无需落盘**；改 `ai.trialDays`
即对全体生效（缩短会立即结束进行中的试用，这是政策语义，不额外记账）。
`trialState()` 是纯函数，测试覆盖到毫秒边界（到点即结束，取 `<=`）。

**「过期不踢下线」的既有语义在这里同样成立**：试用结束或套餐过期只**收回模型**，
会话、额度与其它功能不受影响（`planEffective()` 回落 Free，高级模型跟着回落）。

**边界与降级**

- 老服务端（没有 `ai` 块）→ 插件端按 **`reason: "unknown"`＝不限制**处理，**不擅自锁用户**；
  下拉列表退回通道缓存，且**绝不缩小用户当前的选择**（否则会显示成别的模型，看着像配置被改）。
- 当前保存的模型若已被锁（试用结束 / 套餐到期回落）→ 面板**可见地**回落到 `auto` 并写明原因，
  同时写回配置。**不静默改配置**。
- 高级清单里若含有不在上线范围内的模型 → 保存时只提示、不阻断（允许先配分级再放开上线）。

**改配置**

- Web 管理页 → 模型通道 → 「**高级模型（需套餐）**」卡片：从上线清单里点选，保存/取消分级；
  会员管理 → 套餐额度与收款 → 「新用户全模型试用（天）」与「可用高级模型」勾选框。
- 启动器：通道窗体的「高级模型(需Pro)」行；会员管理 → 套餐与收款 页的同一组字段。
- 接口：`PUT /api/admin/channels/high-tier {models:[...]}`、`PUT /api/admin/membership {ai:{trialDays}, plans:{...}}`。

**隐私/成本提示**：分级只影响**官方网关**这条会产生上游费用的链路；
自带 Key 的通道不消耗本站成本，因此不做任何限制（见 §4.1 最后一条）。

## 六、数据存储方案

| 数据      | 位置                            | 格式                         | 生命周期                          |
| ------- | ----------------------------- | -------------------------- | ----------------------------- |
| 会话（客户端） | Zotero 数据目录 + ProfD，各 3 代     | JSON（schemaVersion 2）      | 30 天滑动；登出/401 走墓碑清除           |
| 账号（服务端） | `server/data/users.json`      | scrypt 密码散列 + 令牌 sha256 散列 + 锁定状态 | 长期；`server/data/` 已 gitignore |
| 会员（服务端） | `server/data/membership.json` | 套餐（含 `highTierModels` 开关）/ **价格表 priceItems** / 收款 / **`ai.trialDays`** / 订单 / 激活码 / **优惠券 coupons** | 长期；订单、已用码与券的使用记录为对账凭证，不清理 |
| 官方通道（服务端） | `server/data/channels.json` | 上游通道池 + `active` + `publishedModels` + **`highTierModels`** | 长期；**上游 API Key 只存服务端**，不进快照以外的任何地方 |
| 快照（服务端） | `server/data/backup/<时间戳>-<原因>/` | users / membership / channels 三份 JSON + `meta.json`（含各文件 sha256） | 最近 30 份 ∪ 最近 14 天每日锚点；**刻意不含 `pp.env`** |
| 登录设备（服务端） | `users.json` → `tokens[<sha256>]` 的可选字段 | 设备标识 / 平台 / 创建与最近活动时间 / 来源 IP | 随令牌（30 天滑动）；改密或踢出即删；**原始 IP 只存服务端** |
| 审计（服务端） | `server/data/audit.log`（+ `audit.log.1`） | JSONL：时间 / 动作 / 对象 / 前后值 / 来源 IP / 结果 | 追加写；超 2MB 轮转 1 份；**密钥与密码永不写入**；不进 git、不参与快照 |
| 运维状态（服务端） | `server/data/alerts.json` · `alerts.log` | 告警去重状态 / 追加式告警日志 | 长期追加；可安全清理（只影响去重记忆） |

**服务端快照（服务端 1.4.2）**：客户端会话仓库早有「2 落点 × 3 代」，服务端此前是**一份孤本**——现在
`server/lib/backup.js` 在**关键写操作之前**自动打一份现场快照（按原因节流，避免高频写刷爆磁盘），
并在服务启动时补一份每日快照。恢复走 `restore`：**先自动给当前现场打一份 `pre-restore` 快照**（恢复错了还能再滚回来），
再逐文件覆盖并**回读 sha256 校验**；校验不一致会明确报错而不是静默写坏数据。
快照目录在 `data/` 内、随 `data/` 一起被 gitignore。

`membership.json` 的 `schemaVersion` 演进：**v1**（无版本号）→ **v2**（套餐 + 平铺价格档位）→
**v3**（价格表 `priceItems`，`priceOptions` 降级为派生视图）。`normalize()` 每次启动都跑，
幂等且不丢数据；v2 → v3 的迁移只在 `priceItems` 为空时发生一次。


**密钥纪律**：任何令牌只出现在 `Authorization` 头，且服务端只存散列；
`server/data/` 不进 git；客户端令牌不进 prefs（回归测试 T11 断言）。

### 7.3 三种操作的语义差别（容易踩的地方）

| 操作 | 入口 | 语义 |
|---|---|---|
| **核销开通** | 订单表 | 订单已核销即**叠加**开通给下单账号，并留档一枚已用兑换码 |
| **开通/续期** | 用户行 | **叠加式**：`max(现在, 现有到期) + 时长`，剩余时长不吞 |
| **编辑** | 用户行 | **覆盖式**：到期日以管理员填写的为准 —— 后台手改即最终裁决 |
| 注册时选 Pro | 注册表单 | 先按 Free 建号，再用会员接口**叠加** N 个月（避免两套语义打架） |

> `Team` 档已下线（只保留 Free / Pro）。存量 `Team` 用户仍可正常登录，
> 显示与额度按 `membershipOf()` 的降级规则处理，管理端下拉不再提供该档。

### 7.4 审计日志（服务端 1.4.4）

**为什么**：核销、改价、删用户、回滚此前都没有留痕 —— 出问题只能翻 `server-console.log` 里
自然语言的 `log()` 行，既不好筛也不好导。现在**每个管理写操作**都落一条结构化记录：

```jsonc
{ "at": "2026-10-03T20:51:46.123Z", "action": "price.update", "target": "pr-cf587266ad48",
  "before": { "price": 399, "enabled": true },  "after": { "price": 369, "enabled": true },
  "ip": "127.0.0.1", "note": "", "ok": true }
```

**覆盖的 24 个写操作**：用户（新建 / 修改 / 重置密码 / 删除 / 解锁 / 开通续期）、
价格条目（增 / 改 / 删）、会员与收款配置、订单（核销 / 取消）、激活码（生成 / 作废）、
模型通道（增 / 改 / 删 / 切换 / 上线清单）、快照（打 / 删 / 回滚）、告警巡检。

三条硬约束：

- **密钥与密码永不写入**：落盘前统一 `redact()`，键名命中 `apiKey / token / password / salt / hash / authorization…`
  一律替换成 `***`；超长字符串截断并标注原长。**激活码也不记码值本身**（它就是凭据，只记数量与套餐）。
- **写审计失败绝不影响业务**：`auditLog()` 内部 try/catch，失败只在 console 留一行 —— 审计是留痕，不是前置条件。
- **不参与数据快照**：`audit.log` 不在 `backup.js` 的快照清单里 —— 回滚业务数据不该把日志也带回去。

入口三处（同一批接口）：Web 管理页「审计日志」标签页（筛选 + 导出 CSV）、
启动器「会员管理 → 审计日志」标签页、以及 `GET /api/admin/audit`。
