## 0. 一句话结论

v1 是「保存一条检索式 → 每天跑一次 arXiv → 自动入库」；v2 把它升级为
**「用你库里的研究领域推荐主题 → 一句话/AI 配置 → 试跑确认 → 定时多源检索 → 去重入库 + 速递」**。
关键取舍：**AI 只做翻译与解读，不做入库决定；确定性链路在 AI 不可用时仍然完整可用。**

## 1. 现状与问题（v1 的真实短板）

| # | 问题 | 代码证据 | 用户感受 |
|---|---|---|---|
| 1 | 只支持 arXiv | `SearchSubs.run()` 只走 `ArxivFetch.search` | 医学/社科库订阅等于不可用 |
| 2 | 配置门槛高 | 表单只有关键词、分类、时间三个输入 | 不知道 `cs.CL` 大小写、不知道多词是 AND |
| 3 | 无法试跑 | `run()` 直接入库、写记账、出笔记 | 建错了只能第二天发现，且已污染去重记账 |
| 4 | 管理能力薄 | 面板只有「立即运行/删除」 | 不能暂停、不能编辑、看不到上次结果 |
| 5 | 没有推荐 | 只能自己想到关键词 | 「我的领域该订阅什么」无从下手 |
| 6 | 只有每日一次 | `checkDue` 只认 `dailyTime` | 周更/双周更场景不适用 |

v2 的每一项都是针对上表的一条，而不是「加功能」。

## 2. 核心功能范围

### 2.1 P0：本次已实现

1. **订阅模型 v2**：来源、布尔模式、排除词、时间窗、频率（手动/每日/每周）、启停、AI 开关、运行历史。
2. **多源检索**：arXiv、OpenAlex、Crossref、Europe PMC、PubMed；单源失败不影响其它源（`bySource` + `partial`）。
3. **试跑预览**：`preview()` 只取数、打分、标注状态；**不写 pref、不入库、不记账、不出笔记**。
4. **智能推荐**：基于库内画像产出 3 类可解释主题（分类轨道 / 全局主题 / 近期关注），冷启动回退「研究者画像」文本。
5. **AI 三能力**：一句话建订阅、相关性复核、速递速览；全部可选、失败降级。
6. **管理闭环**：启用/暂停、编辑、立即运行、最近 5 次历史、上次状态。
7. **导入导出**：订阅配置 JSON 走剪贴板（不含 id/运行态），便于备份与课题组共享。
8. **推荐缓存**：库内画像分析结果本机缓存 12 小时，面板「重新分析我的库」强制刷新；订阅增删改自动失效。
9. **调度**：手动 / 每日 / 每周（ISO 1=周一），沿用 60s 轮询 + 启动即查 + 6 小时补跑窗口。
10. **与现有功能衔接**：文献发现窗口「存为订阅」、功能中心入口、arXiv 工具包单一真源。

### 2.2 0.58.0 已补齐（原 P1 四项）

- **反馈学习**：预览卡「收藏 / 忽略」写入 `searchSubsFeedback`；收藏会入库并计入 seen，忽略的条目不入库、不再进速递，只计入跳过数；反馈按词/作者折算成 ±3 分内的排序微调。
- **作者追踪**：订阅新增 `authors`（≤6）；arXiv `au:`、Europe PMC `AUTH:`、PubMed `[au]`、OpenAlex `raw_author_name.search`、Crossref `query.author` 全覆盖；推荐新增「作者轨道」。
- **系统通知**：订阅 `notify`（默认开）；非手动运行且有新增时弹 `Zotero.ProgressWindow`，失败静默。
- **OpenAlex 免费 Key**：`openAlexApiKey` 可选，进 `api_key` 参数；错误信息脱敏，密钥不进云同步。

### 2.2.1 仍未做

- 邮件 / Webhook 通知（当前只有系统通知 + 速递笔记）。
- 机构追踪（作者维度已覆盖，机构尚未）。
- Web of Science / Scopus / CNKI 等需授权或反爬的源（CNKI 已有实验性基础设施，但稳定性另论）。

### 2.3 明确不做（边界）

- **不做本地向量库**：零依赖是仓库约束；语义召回留到 P2（可接 embedding，但必须可离线降级）。
- **不做服务端代抓**：账号后台不碰用户的检索行为与库内容。
- **不做「AI 决定入库」**：AI 解析出的草稿强制 `autoImport: false`；是否入库始终是用户/确定性规则的决定。
- **不做无限历史**：seen 记账 LRU 1000，运行历史每订阅 5 条。
- **不做「定时器统一」**：不与 `Scheduler.JOBS` 合并（两条线生命周期不同；合并会把「订阅失败」和「晨报失败」耦合在一起）。

## 3. 订阅创建与管理的交互流程

### 3.1 四个创建入口

| 入口 | 用户动作 | 系统行为 | 何时落盘 |
|---|---|---|---|
| A. 推荐卡 | 点「预览」或「直接创建」 | `suggest()` → 卡片；预览走 `preview()` | 只有「创建」才 `add()` |
| B. 一句话 | 输入描述 → 「AI 解析」 | `aiParseQuery()` → 回填表单 → 自动试跑 | 解析不落盘；保存才落盘 |
| C. 手动表单 | 填条件 → 「试跑预览」→「保存订阅」 | `preview()` → `add()` | 保存时 |
| D. 文献发现 | 发现窗口点「存为订阅」 | `fromDiscovery()` → `add()`（默认每日 08:00、不自动入库） | 点击即落盘，但可在列表里改 |

**所有入口都共享同一条确认链**：条件可见 → 结果可见（预览）→ 才创建。唯一的例外是 D（用户已经在发现窗口看过结果）。

### 3.2 状态机

```
draft（表单/AI 草稿，不落盘）
  └─ preview（试跑，不落盘）
       └─ saved（落盘）
            ├─ enabled + daily/weekly → 到点 running → 回到 enabled
            ├─ paused（enabled=false）→ 只能「立即运行」
            └─ deleted（remove，含确认）
```

- `lastRun` 只表示「调度记账的日期」，`lastStatus/runLog` 表示「真实执行结果」——两者分开，避免「到点触发但网络失败」被误读为成功。
- 预览与正式运行使用同一套 `_search` / `_rank` / `_normEntry`，因此「预览看到的」与「运行时入库的」形状一致。

### 3.3 管理操作

| 操作 | 行为 | 失败反馈 |
|---|---|---|
| 启用/暂停 | `update(id,{enabled})` | 行内提示「状态保存失败」 |
| 编辑 | 表单回填，标题变「编辑订阅：…」，保存走 `update` | 名称/条件为空时拒绝并聚焦 |
| 立即运行 | `run(id,{trigger:"manual"})`，显示 `+N 新入库 / M 跳过 / K 失败` | `reason` 转中文（网络/空结果/模块未就绪） |
| 历史 | 展开最近 5 次（时间、计数、触发方式、失败原因） | 无记录时给空态文案 |
| 删除 | `Services.prompt.confirm` → `remove` | 不存在时提示「订阅可能已不存在」 |
| 导出 / 导入 | 配置 JSON 走剪贴板；导入重分配 id、跳过同名 | 坏 JSON / 空内容 / 写失败给明确文案 |

### 3.4 失败反馈（reason 词表）

`no_sub` 订阅不存在 · `no_query` 缺检索条件 · `no_arxiv` arXiv 模块未就绪 ·
`network` 网络/解析失败 · `empty` 无命中 · `busy` 上一次未结束 ·
`no_ai` AI 未配置 · `not_logged_in` 官方通道未登录 · `ai_failed` AI 调用失败 · `parse_failed` AI 输出不可解析。

UI 对 `not_logged_in` 与 `no_key` 给不同指引（沿用 `AIClient.status()` 的精确原因，不用一条笼统提示盖住）。

## 4. 推荐逻辑

### 4.1 画像（复用 Discovery，不另写一套）

`Discovery.buildProfile(items)`：

- 词元权重：标题 ×3、标签 ×3、期刊 ×2、摘要 ×1；
- 过滤：停用词 + 状态/管理类标签（`⛔ No DOI found`、`未读`）+ 「出现在超过 40% 文档」的泛词（下限 3 篇，避免小库画像被清空）；
- 中文按 bigram 切分，长度下限 ≥2（否则「抽动/障碍/中医」会被整体丢掉）；
- 另抽 arXiv 分类偏好（扫 `extra/url/archiveID/DOI`），Top 8。

### 4.2 三类候选

| 类型 | 生成方式 | 命名 | 为什么可解释 |
|---|---|---|---|
| 分类轨道 `cat` | 取库内出现最多的 1–2 个 arXiv 分类，对「属于该分类的子集」重新画像，取 Top 4 词 | `追踪 cs.LG` | 「库内 N 篇属于 cs.LG」 |
| 全局主题 `topic` | 全库画像 Top 4 词 | `词A / 词B` | 「全库高频主题词（已过滤泛词）」 |
| 近期关注 `recent` | 近 180 天入库条目的画像 Top 4 词 | `近半年关注：词A / 词B` | 「近 180 天新入库 N 篇」 |

排序分：`recent × 3 + coverage`（覆盖篇数用标题/标签/摘要做子串匹配，纯本地、零网络）。

### 4.3 去重与负反馈

- 与现有订阅关键词做 **Jaccard ≥ 0.5** → 不推荐（避免重复订阅）；
- 推荐之间 **Jaccard ≥ 0.6** → 只留分高的；
- 「忽略」写入 `searchSubsRecoDismissed`（LRU 100），之后不再出现；
- 分类轨道要求该分类子集 ≥2 篇，否则不出（避免 1 篇文献造出一个主题）。

### 4.4 冷启动

库里没有可分析条目时，读 `researcherProfile`（设置 → AI 与翻译 → 研究者画像）文本 →
分词取前 5 个 → 生成一条「研究方向：…」，并明确告知「库内条目还太少，导入后推荐会更准」。
**不会**在没有任何输入时编造主题。

### 4.5 为什么用词元而不是向量

- 可解释：每个推荐都能说清「哪些词、覆盖多少篇」；
- 零依赖、可离线、小库也稳定（向量模型对 <50 篇的库反而更差）；
- 成本可控：推荐不产生任何网络请求或 AI 费用。
P2 若接 embedding，只作为 `topic` 候选的补充排序，不替换可解释的理由字段。

## 5. AI 辅助的具体能力边界

| 能力 | 触发 | 输入 | 输出 | 校验 | 失败时 |
|---|---|---|---|---|---|
| 一句话建订阅 `aiParseQuery` | 用户点「AI 解析」 | 用户原话（可中文） | 严格 JSON：name/keywords/categories/sources/mode/exclude/maxAgeDays/freq/dailyTime/autoImport | 来源白名单、分类用 `ArxivCategories.checkAll` 过滤、频率/时间归一、关键词 2–8 个、**强制 `autoImport:false`** | 返回 `no_ai`/`not_logged_in`/`ai_failed`/`parse_failed`，不猜测、不建订阅 |
| 相关性复核 `aiRerank` | 订阅开启「AI 相关性复核」 | 订阅条件 + 前 12 条标题/摘要前 220 字 | `[{i,score:0-100,why:≤24字}]` | 只接受 1..N 的索引，分数夹紧 0–100；缺失条目保持原序 | 静默保持确定性排序，不阻断运行 |
| 速递速览 `aiDigest` | 订阅开启「AI 速递速览」且本次有新入库 | 条件 + 前 15 条标题/摘要前 120 字 | 3–5 条中文要点（≤1200 字） | 纯文本，作为笔记的「AI 速览」段 | 返回空串，笔记照常生成 |

**硬边界（写进代码与本文档）**：

1. **不自动创建**：解析结果只填表，`add()` 必须由用户点击。
2. **不自动入库**：AI 草稿强制 `autoImport:false`；即使表单里被改成 true，也只在「保存后正式运行」时生效。
3. **不擅自扩写分类**：AI 给的分类必须通过本地白名单；不确定就为空，不用「猜一个相近的」。
4. **不发库内正文**：只发命中的标题与摘要片段；不发送批注、笔记、全文。
5. **AI 输出是数据不是指令**：解析器只做 JSON 提取 + 字段校验，绝不执行模型返回的任何命令；提示词里明确要求「只输出 JSON」。
6. **成本上限**：复核 12 条/次、速览 15 条/次、解析 1 次/点击；没有「后台自动反复调用 AI」的路径。
7. **可完全关闭**：三个开关默认关（AI 解析是显式点击），关闭后 v2 的确定性链路（多源 + 预览 + 推荐 + 定时）全部可用。

## 6. 与现有检索功能的衔接

| 现有模块 | 复用方式 | 新接缝 |
|---|---|---|
| **文献发现** `features/discovery.js` | `buildProfile` / `tokenize` / `extractArxiv` / `knownIndex` 全部复用；不再复制分词与停用词表 | `Discovery` 窗口新增「存为订阅」→ `SearchSubs.fromDiscovery()` |
| **arXiv 工具包** `tools/arxiv` → `scripts/arxiv/*` | 查询构建、Atom 解析、去重、限速全部走生成物；订阅不手写 arXiv 语法 | `SubSources._arxiv()` 调 `ArxivFetch.search`，`arxivSpec()` 负责条件映射 |
| **库内检索** `features/lib-search.js` | 通过 Discovery 间接复用 `LibSearch.tokenize` | 无直接改动（避免把「库内问答」与「外部订阅」耦合） |
| **定时任务** `features/scheduler.js` | 时间语义完全一致（60s 轮询、启动即查、6h 补跑、先写 lastRun） | 独立 timer；新增 weekly 判定 `_isPlannedDay` |
| **笔记管线** `MdLite` / `Scheduler._saveNote` | 速递笔记同样落库根目录独立笔记 | 新增「来源」「AI 速览」段落 |
| **AI 通道** `ai/client.js` + `ai/channels.js` | `AIClient.chat` / `status()` / 官方通道计费 | 三个能力都先查 `status()`，再决定是否调用 |
| **功能中心** `hub.js` | 「检索与发现」组新增「检索订阅」入口 | 打开设置页（订阅卡） |
| **云同步** `features/cloud-sync.js` | 订阅是 pref，默认进入快照 | 多设备可用；并发编辑为 last-write-wins（已知限制） |
| **文献发现缓存** `discoveryResults` | 订阅草稿复用画像词与分类 | 不复制发现结果，只借条件 |

**为什么不把订阅放进 Discovery 窗口**：发现是「一次性浏览」，订阅是「长期后台任务」；两者共享画像与打分，但生命周期、失败语义、UI 密度都不同。放在设置页能让「定时/暂停/历史」这类管理操作有稳定位置。

## 7. 数据模型与迁移

### 7.1 存储

三个 pref（JSON 字符串）：

- `searchSubscriptions`：订阅数组，最新在前；
- `searchSubsSeen`：`fingerprint → {itemID?, at}`，LRU 1000；
- `searchSubsRecoDismissed`：被忽略的推荐 id，LRU 100；
- `subsMailto`：可选礼貌邮箱（OpenAlex/Crossref 配额）。

### 7.2 订阅对象

```json
{
  "id": "sub-m1abc2",
  "name": "稀疏注意力",
  "enabled": true,
  "sources": ["arxiv", "openalex"],
  "keywords": "sparse attention, long context",
  "categories": "cs.LG, cs.CL",
  "mode": "all",
  "exclude": "survey",
  "maxAgeDays": 14,
  "freq": "weekly",
  "dailyTime": "08:00",
  "weekdays": [1, 3],
  "max": 10,
  "autoImport": true,
  "aiRerank": false,
  "aiDigest": false,
  "seedProfile": false,
  "lastRun": "2026-10-19",
  "lastStatus": "2026-10-19 08:00 · +2 新入库 / 1 跳过",
  "runLog": [{ "at": "2026-10-19 08:00", "added": 2, "skipped": 1, "failed": 0, "trigger": "weekly", "reason": "" }],
  "createdAt": 1760000000000,
  "updatedAt": 1760000000000
}
```

### 7.3 v1 → v2 兼容

| v1 字段 | v2 处理 |
|---|---|
| 无 `sources` | 默认 `["arxiv"]` |
| 无 `enabled` | 默认 `true` |
| 无 `freq` | `dailyTime` 合法 → `daily`；否则 `manual` |
| 无 `mode` | `all`（与 v1 的 AND 语义一致） |
| 无 `weekdays` | 默认周一至周五 |
| 无 `runLog/lastStatus` | 空数组/空串 |

旧订阅不需要迁移脚本；`_normSub` 在每次读取时补齐。写入时保留新形状，因此升级后第一次编辑即完成迁移。

**`autoImport:false` 的记账语义**：只推送、不入库 → **不写 seen**。写了 seen 会让这批论文之后永远被当作「往期已见」，用户改成自动入库也再收不到（等于静默丢论文）。代价是它们会重复出现在速递里，可接受；已手动导入的条目仍会被 DOI 查重拦住。

## 8. 数据源、限速与召回

| 源 | 覆盖 | 鉴权 | 限速策略 | 布尔语义 |
|---|---|---|---|---|
| arXiv | 预印本（数理/CS/生医等） | 无 | `ArxivRateLimiter`：任意两次请求 ≥3s、单连接 | 原生 `AND/OR/ANDNOT` + `cat:` + 日期区间 |
| OpenAlex | 期刊/会议/预印本，带被引量、OA 链接 | 无（可选 `mailto` 进 polite pool） | 客户端 ≥400ms/次 | `search` 支持 AND/OR/引号；**本地二次过滤**兜底 |
| Crossref | DOI 元数据，全学科 | 无（可选 `mailto`） | ≥400ms/次 | 相关度检索；**本地二次过滤**兜底 |
| PubMed | 生物医学 | 无（可选 `mailto`/email） | ≥400ms/次（官方 3 req/s） | `[tiab]` + `AND/OR/NOT` |

补充规则：

- 非 arXiv 源**必须有关键词**：分类只对 arXiv 有意义，缺关键词时该源返回明确原因，而不是拉一堆无关结果。
- 本地过滤：`all` 要求全部词命中标题/摘要，`any` 任一，`phrase` 连续；**没有摘要时不误杀**（交给源的相关度排序）。
- 分页/条数：每个源最多取 `sub.max`（≤30），合并后跨源去重，再按 `_rank` 截断。
- 跨源去重优先级：DOI > arXiv ID（去版本）> 归一标题；重复条目做字段互补（PDF、被引量取大者）。

## 11. 已知限制与风险

1. **中文关键词**：OpenAlex/Crossref/PubMed 对中文命中率低；表单已提示「建议英文」，AI 解析会译成英文。未配置 AI 时用户需自己写英文。
2. **布尔语义不统一**：只有 arXiv/PubMed 原生布尔；OpenAlex/Crossref 依赖本地二次过滤，可能比源本身召回更严（宁可少，不可噪声）。
3. **arXiv 限速**：多条订阅同一分钟到点会串行（每条 ≥3s）；这是官方礼节，不做并发绕过。
4. **NCBI 可达性**：实测本机 `eutils.ncbi.nlm.nih.gov` 直接不可达（HTTP 000）。因此新增 Europe PMC 作为生物医学的主力源（同一批 PubMed 记录、单请求、带摘要）；PubMed 保留给网络可达的用户，失败时只在 bySource 里报错。
5. **PubMed 摘要缺失**：`esummary` 默认不带摘要，本地过滤对这类条目不误杀，但相关性排序会偏弱。
6. **AI 成本**：复核/速览走用户配置的通道；官方通道按现有计费规则扣额度。默认关闭是刻意的。
7. **云同步边界**：`searchSubsRecoCache`（本机画像缓存）与 `searchSubsSeen`（本机投递记账）已排除出云同步；订阅配置仍随云同步，并发编辑为 last-write-wins。
8. **推荐质量依赖库质量**：标签噪声大、库很小或跨领域过杂时，推荐会偏保守（宁可少推）。
9. **未做真正的「已读」状态**：seen 只用于去重，不在 UI 展示「未读速递」；P1 可加。
10. **OpenAlex 匿名额度**：官方提示无 API Key 时按 IP 共享每天 $0.10 的免费预算；额度耗尽只会让该源失败（`bySource` 可见），不影响其它源。需要稳定额度时可在 OpenAlex 申请免费 Key（当前未做 Key 输入框，属 P1）。

## 12. 后续演进建议（按投入产出排序）

1. **反馈闭环**（小）：收藏/忽略 → 关键词权重 ±；忽略的条目 id 参与 `_scoreEntry` 负分。
2. **作者追踪**（小）：库内 Top 作者 → 一类订阅；OpenAlex `author.id` / arXiv `au:` 都成熟。
3. **通知**（中）：系统通知 + 邮件；复用现有账号后台的邮件能力（若有）或用户 SMTP。
4. **语义召回**（大）：本地 embedding 或 OpenAlex `related_works`；必须保留词元链路作为降级。
