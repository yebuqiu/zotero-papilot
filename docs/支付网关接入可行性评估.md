# 支付网关接入可行性评估（复用「医疗工具平台」售卖站实现）

> 评估日期：2026-10-05
> 被评估对象：`E:\project\医疗工具平台\store\server\`（易支付/码支付接入 + 售卖站订单体系）
> 结论：**可用，且正好补上 Papilot「支付自动确认」这个唯一缺口。**

## 1. 结论

Papilot 当前充值/下单的最后一环是**人工核销**（用户点「我已完成支付」→ 管理员核销 → 自动入账）。
「医疗工具平台」的售卖站已经把这一段做完了，并且**已在生产真实跑通**（配置 `enabled: true`、
网关易支付 V1、密钥齐备、订单表有 2 笔 `paid`）。

它的三块资产可以搬到 Papilot：

| 资产 | 位置 | 价值 |
|---|---|---|
| 支付协议实现（下单/验签/查单/连接自检） | `store/server/pay.js`（356 行） | 纯 Node `crypto`，**零第三方依赖**，与 Papilot 的「服务端零依赖」约束完全兼容 |
| 敏感数据加密 | `store/server/crypto.js` | AES-256-GCM（`iv.tag.ct` base64）+ 主密钥落盘，同样零依赖 |
| **回调验签 → 幂等履约** 的完整顺序 | `store/server/api-public.js:1011-1032` | 支付自动化的核心，五重校验顺序可直接照搬 |

**真实使用的网关**：易支付 V1（`provider: epay`），网关 `https://www.ljlliu.cn`，
查单走该站的 `checkOrder` 变体（`pay.js` 里已单独适配）。**同一套商户号可复用到 Papilot**。

## 2. 可直接复用的部分（几乎逐行搬）

### 2.1 协议层（`pay.js`）

```
buildSignStr(params)          非空参数、剔除 sign/sign_type、键名 ASCII 升序、k=v 以 & 连接
buildSign / verifySign        V1 易支付 MD5；verifySign 用 timingSafeEqual（防时序侧信道）
rsaSign / rsaVerify           V2 SHA256WithRSA（crypto.sign/verify）
verifyNotify(cfg, query)      按 provider 分发到上面两者
toPrivateKey / toPublicKey    base64 裸 DER 与 PEM 双兼容（PKCS#8/PKCS#1 自动回退）
cleanKeyMaterial              粘贴密钥的空白清洗
createPayUrl                  V1 → {gw}/submit.php（GET 跳转）；V2 → {gw}/api/pay/submit
queryOrder                    主动查单：V1 api.php?act=order / checkOrder 变体；V2 POST api/pay/query（响应也验签）
testConnection                连接自检：V1 会真的构造一笔 0.01 元测试单验证「签名+必填字段+跳转入口」全链路
```

### 2.2 回调路由的五重校验（**这是最值得抄的部分**）

`api-public.js:1011` 的 `/api/pay/notify` 顺序：

```
① 按 IP 限速（60 次/10 分钟）
② 配置就绪检查
③ 验签（V1 MD5 / V2 RSA）
④ 商户号 pid 比对
⑤ trade_status === 'TRADE_SUCCESS'
⑥ 订单存在
⑦ 金额比对 toFixed(2) 相等 —— 防少付
⑧ fulfillOrder 幂等履约（UPDATE ... WHERE status='pending'，changes===0 即已被并发履约）
→ 响应固定 text/plain 的 'success' / 'fail'
```

两个设计细节值得单独学：

- **拒绝原因只进 stderr 日志，响应体恒为 `fail`** —— 不给探测者任何信息（`fail()` 的注释写明了这点）。
- **金额比对是防少付的关键** —— 只验签不够，必须比对实付金额与本地订单金额。

### 2.3 兜底与运维

- `/api/store/orders/:no/query`：**主动查单**，网关异步通知没到达时由用户在界面上手动触发（有限速）。
  支付回调丢包是常态，**没有这一段就不要上线**。
- 后台「连接测试」按钮 → `POST /api/admin/payment/test` → `testConnection()`，把"配了但没通"这类问题在启用前暴露。

## 3. Papilot 侧必须改造的部分

「医疗工具平台」与本仓库架构差异不小，不能整文件搬运：

| 维度 | 医疗工具平台 | Papilot | 改造方式 |
|---|---|---|---|
| 存储 | SQLite（`db.transaction`、`UPDATE ... WHERE status='pending'`） | JSON `JsonStore` + 快照回滚 | 用 **已存在的 `applyOrderFulfill(order, by)`** 作唯一履约入口；notify 里判 `status==='pending'` 后调用它。幂等靠"已 fulfilled 直接返回" |
| 订单状态机 | `pending → paid → closed` | `pending → claimed → fulfilled / cancelled / expired` | notify 命中即 `pending → fulfilled`（跳过 `claimed`）；`claimed` 仍留给人工核销路径 |
| HTTP 客户端 | 全局 `fetch`（Node 18+） | 头注释声明 ≥14，实跑 Node 22 | 建议改用**原生 `https` 模块**（与仓库既有 `mail.js`/网关转发一致）；或把最低版本明确提到 18 |
| 公网地址 | `baseUrl(req)` 读 `X-Forwarded-*` | 已有 `PP_PUBLIC_URL` + `mail.publicBaseUrl(req)` | notify_url 用 **`PP_PUBLIC_URL` 显式配置**，**不要按 Host 头推断**（公网请求的 Host 可被伪造，会把回调指向攻击者域名） |
| 密钥存放 | `config` 表 `payment.keyEnc`（AES-GCM） | `server/data/*.json`（已 gitignored） | 新增 `server/data/pay.json` + AES-GCM 加密字段；**绝不可进 `membership.json` 这类会被快照/导出带出去的文件** |
| 路由可达性 | 公开路由 | 管理面由 `isLocalAdmin()` 拦（公网 403） | notify 必须注册在 **admin 守卫之前**（与 `/api/auth/register`、`/v1/*` 同区），靠验签而非来源 IP 保护 |
| 金额 | 网关金额 = 标价 | **有唯一尾数**（人工对账用） | 可共存：网关收的就是含尾数的实付额，两边比对天然一致；想取消尾数需另做决定（见 §5.6） |

### 3.1 已发现的具体坑：订单号含连字符

Papilot 的订单号由 `membership.js:240` 生成：

```js
function rid(prefix, bytes) { return prefix + '-' + crypto.randomBytes(bytes).toString('hex'); }
// 生产实例：o-05ebc5e72c3b、o-9b2e724b0794
```

而易支付类网关的 `out_trade_no` **通常只接受字母数字**。带连字符会直接**拒单**。
改造方式：支付下单时另生成纯字母数字的 `outTradeNo`（如 `PP` + 时间戳 36 进制 + 随机），
在订单上新增字段保存，回调按它反查——**不要改 `id`**（`id` 已被插件端、管理页、对账脚本大量引用）。

## 5. 风险与必须由你决策的点

### 5.1 第三方聚合支付本身的风险（商业风险，非技术风险）
易支付/码支付属**非持牌第三方聚合支付**：费率、结算周期、金额上限均由上游决定，
存在上游跑路/冻结/风控导致资金受损的可能。这是"能不能用"之外的问题，需要你自己判断承受度。
（对比：官方微信/支付宝商户号需营业执照 + 主体资质。）

### 5.2 合规
Papilot 已在转售第三方模型 API 并面向公众提供生成式 AI 服务，本身就落在监管范围内
（算法备案等，见 `docs/AI计费与成本计量.md` §8.4）。**线上收款会进一步暴露经营主体问题**。
建议在做大之前把主体与备案的事确认清楚。

### 5.3 公网攻击面扩大
notify 是公开路由。必须做到：限速 + 验签 + pid 比对 + 金额比对 + **响应体不回显任何原因**
（照抄对方的 `fail()` 设计），拒绝原因只写本地日志。

### 5.4 回调丢包
CF 隧道抖动、网关重试策略都会导致通知丢失。**主动查单是必需项不是可选项**，
且订单要落 `outTradeNo / tradeNo / payChannel / paidAt` 四个字段以便对账与客服。

### 5.5 退款
网关侧退款与余额/权益回滚要设计清楚。Papilot 的余额模型下，
"已消费后再退款"很难处理——建议**只退未消费部分**，或退款一律退到 `paidMicro` 余额（不退回原路）。

### 5.6 尾数机制的去留（需要你决定）
现在金额带唯一尾数（如 ¥30.42）是为了**人工对账**。接入网关后：
- **保留**：网关收含尾数的实付额，人工兜底路径继续可用（改动最小，推荐先这样）；
- **取消**：金额取整更好看，但人工兜底（网关故障时）就失去匹配依据，需要同步改造对账脚本。
