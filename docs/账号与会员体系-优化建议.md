# Papilot 账号与会员体系 · 优化建议清单

> 面向：账号管理、会员体系、后台运维。
> 每条给出 **目标 / 实现思路 / 优先级 / 落地成本**，按优先级排序，可直接当排期表用。
> 优先级口径：**P0 = 不修迟早出事**（数据/资金/信任风险）；**P1 = 高价值且现在就能做**；
> **P2 = 有价值但要配套条件**；**P3 = 锦上添花**。
> 现状基线：账号（邮箱密码 + 30 天滑动令牌 + v2 多代会话仓库）、会员（Free/Pro、价格表 = 等级 × 计费周期 × 生效时段、
> 订单人工核销、激活码、后台两套 UI）已上线。

---

## 一、P0：现在就该补的三件

### 1. 数据备份与一键回滚 ✅
- **目标**：价格表、订单、激活码、用户会员一旦被误操作/写坏，能当场恢复，而不是靠记忆重配。
- **实现思路**：服务端每次 `membershipStore.save()` / `usersStore.save()` 前做滚动快照
  （`data/backup/membership-YYYYMMDD-HHmmss.json`，保留最近 N 份 + 每日 1 份），
  暴露 `GET /api/admin/backups`、`POST /api/admin/backups/restore`（仅本机、二次确认、恢复前再存一份现场）。
  插件端会话仓库已有 2 落点 × 3 代，服务端反而没有——这是目前最大的单点。
- **✅ 已实现（服务端 1.4.2）**：`server/lib/backup.js` + `GET|POST /api/admin/backups`、`POST /api/admin/backups/:id/restore`、`DELETE /api/admin/backups/:id`。
  关键写操作**之前**自动打快照（按 reason 节流 5 分钟，保住「一串改动开始前的状态」），启动时每日快照；
  保留 = 最近 30 份 ∪ 最近 14 天每日锚点；恢复需 `confirm:"RESTORE"`、**恢复前自动打 `pre-restore` 现场快照**（可反悔）、逐文件 sha256 校验。
  **刻意不备份 `pp.env`**（不复制密钥）。回归：`test/server-ops.test.js` A 组（含篡改即报错、节流、保留策略）。
- **优先级**：P0
- **成本**：小（半天）。纯服务端，不动插件。

### 2. 订单积压与核销超时告警 ✅
- **目标**：用户付了钱却没人核销，是最伤信任的故障；现在完全靠人主动点开后台看。
- **实现思路**：guard 每分钟巡检时顺带查 `/api/health`，若 `ordersAwaitingReview > 0` 且最老一条
  超过 N 分钟（默认 30），写 `data/alerts.log` 并（可选）发一封邮件到管理员邮箱；
  后台 KPI 卡对超时订单标红。已在 `/api/health` 暴露 `ordersAwaitingReview`，只差告警侧。
- **✅ 已实现（服务端 1.4.2）**：`server/lib/alerts.js` + 服务端后台任务每 5 分钟巡检（`/api/admin/alerts` 看状态、`POST /api/admin/alerts/check` 手动触发）。
  阈值 `PP_ALERT_BACKLOG_MIN`（默认 30）、重复提醒窗口 `PP_ALERT_REPEAT_H`（默认 6h，**最老订单换人立即再告警**）、收件人 `PP_ALERT_EMAIL`（未配则只写日志并在 UI 说明原因）。
  只统计已付款待核销（`claimed`），**未付款 `pending` 不计入**以免噪音；`/api/health` 新增 `backlogCount` / `backlogOldestMinutes` / `backlogOverdue`。
- **优先级**：P0
- **成本**：小（几小时）。复用现有 guard 与邮件能力。

### 3. 账号级登录风控 ✅
- **目标**：现在只有「每 IP 每分钟 10 次」的限速，换个 IP 就能无限撞某个账号的密码。
- **实现思路**：在 `users.json` 的 user 上加 `failCount` / `lockUntil` / `lastFailIp`：
  同一账号连续失败 5 次锁 15 分钟（阶梯递增），成功登录清零；锁定期间即使密码正确也返回
  「尝试过多，请 N 分钟后再试」。管理员后台可一键解锁。
- **✅ 已实现（服务端 1.4.2）**：`server/lib/lockout.js`。user 新增 `failCount` / `lockUntil` / `lastFailAt` / `lastFailIp`；
  **第 5 次起阶梯锁定 15 分钟 → 1 小时 → 6 小时 → 24 小时（封顶）**，锁定期内**密码正确也拒**（否则锁定形同虚设）；
  失败应答文案与「邮箱不存在」**完全一致**，不泄漏账号是否存在；成功登录清零；`POST /api/admin/users/:id/unlock` 一键解锁，用户列表显示锁定状态与剩余分钟。
- **优先级**：P0
- **成本**：小（半天）。纯服务端 + 后台加一个按钮。

## 二、P1：高价值，现在就能做

### 4. 插件端把新价格模型用起来 ✅
- **目标**：价格表已经能配「按月 / 按季 / 按年 + 折合月价 + 定时生效」，但插件端仍在读旧的
  `priceOptions`（只有「N 个月 ¥X」），用户看不到「折合 ¥22.42/月」「即将生效」这些关键决策信息。
- **实现思路**：`/api/plans` 已经同时返回 `priceItems`（生效中，含 cycle/cycleName/perMonth）与
  `upcoming`（未生效）。插件 `prefs-account.js` 的 `renderMbOptions()` 改为优先用 `priceItems`：
  档位卡显示「按年 · ¥269 · 折合 ¥22.42/月」，`upcoming` 用灰底标注「即将生效 · <日期>」且不可点。
  服务端零改动。
  **已在同一套接口里铺好，纯插件侧改动 → 需要发一版 xpi。**
- **✅ 已实现（插件 0.24.4）**：`account.js` 的 `plans()` 增返 `priceItems` / `upcoming` / `cycles`；
  `renderMbOptions()` 优先用价格表，档位卡显示「按季 · ¥79 · 折合 ¥26.33/月」（**单周期不显示多余的折合价**）；
  未生效价格以虚线灰底「即将生效 · 半年 ¥149 · 2026-11-11」出现且**不绑 click**（点不动=不可下单）；
  老服务端没有 `priceItems` 时自动回落旧 `priceOptions`，**向后兼容**。
- **优先级**：P1
- **成本**：小（插件里一个函数 + 少量样式）。

### 5. 会员到期提醒（插件端）✅
- **目标**：到期不踢下线是对的，但用户不知道自己要到期了，体验上像"偷偷降级"。
- **实现思路**：会员卡片已有 `daysLeft`。剩 ≤7 天时卡片转警示色 + 横幅「仅剩 N 天，点此续费」；
  剩 ≤1 天或已过期时用 `Services.prompt` 在启动后提示一次（每个到期周期只提示一次，
  用 pref 记 `renewPromptShownFor=<expiresAt>` 防打扰）。顺手把「续费」按钮的默认周期设为
  用户上次购买的周期（`membership.history` 里有）。
- **✅ 已实现（插件 0.24.4）**：会员卡剩余 ≤7 天出现**可点横幅**（已到期转红并改文案），点击直接打开续费面板；
  启动后若 ≤1 天或已过期，用系统提示弹一次 —— **同一到期周期只提示一次**（pref `renewPromptShownFor=<expiresAt>`；
  未登录或主窗口还没就绪时**不落标记**，留给下次，避免"弹不出来又永久静音"）；
  续费默认档位取 `membership.history` 里**最近一次购买的周期**（买过 12 个月就默认选中按年）。
- **优先级**：P1
- **成本**：小（插件侧）。

### 6. 接支付回调，用自动核销替代人工核销 ✅（第 1 步）
- **目标**：人工核销是当前运营瓶颈——用户付了钱要等人点一下，夜里下单就干等。
- **实现思路**：分两步走，不必一次到位：
  1）**收款码 + 备注金额核对**（现在就做）：下单时生成**带小数尾数的唯一金额**（如 ¥269.13），
     回调/对账脚本按「金额 + 时间窗」自动匹配订单 → 直接 `fulfill`。零支付资质，纯对账自动化。
  2）**接官方支付**：微信/支付宝当面付或 Stripe，`POST /api/pay/notify` 验签后按 `out_trade_no = orderId`
     核销；同时给订单加 `paidAt` / `channel` / `txnId` 字段与幂等保护（同一 txnId 只核销一次）。
- **✅ 已实现（第 1 步，服务端 1.4.5 / 插件 0.24.5）**：下单即分配**同金额内唯一的小数尾数**
  （1..99 分，随机起点 + 线性探测；终态回收；用尽明确报错而不是做成同金额），于是**收款流水按金额即可唯一匹配订单**；
  `server/lib/reconcile.js` 做纯匹配（**精确到分 + 时间窗 + 重复/歧义保护，刻意不做模糊匹配**），
  `POST /api/admin/reconcile`（**默认 dryRun 预览**，`dryRun:false` 才核销）+ Web 管理页与启动器的「对账导入」+ CLI `scripts/reconcile.js`；
  核销语义与人工核销完全一致并写审计 `order.reconcile`。
  **第 2 步（官方支付回调 / 真实商户号）未做**，需要支付资质，届时复用同一个核销入口即可。
- **优先级**：P1（第 1 步已完成）/ P2（第 2 步，需商户号）
- **成本**：第 1 步小；第 2 步中。

### 7. 把「发版前必跑清单」固化成一条命令 ✅
- **目标**：这次价格表上线过程中，测试真的抓到了两个 bug（局部更新漏字段、预览不联动）。
  但跑测试仍靠人记得住 5 个脚本路径。
- **实现思路**：加 `scripts/preflight.py`（或 `npm run preflight`）串起：
  `test/account-persistence.test.js` → `test/membership.test.js` → `test/price.test.js` →
  `test/legacy-rootcause.probe.js` → `scripts/check-wiring.py` → 全模块加载冒烟 →
  `build-xpi.py` 自检；任一失败即非零退出。发版流程文档里把它列为第 0 步。
- **✅ 已实现（服务端 1.4.2）**：`scripts/preflight.py`。一条命令跑：全部 JS `node --check`（81 个）→ 6 个测试套件
  （会话持久化 / 会员域 / 价格表 / 运维三件套 / 根因探针 / 全模块加载冒烟）→ 接线一致性扫描 → 后台真浏览器 E2E；
  另 `--with-build <ver>` 追加构建 xpi 自检。任一失败**非零退出并打印「哪一步失败 + 怎么单独复现」**。
  同时把原先散在 `E:/tmp/pp_test/` 的**全模块加载冒烟**与 **admin E2E** 收进仓库 `test/`（`test/smoke-load.test.js`、`test/admin-e2e.test.js`，
  后者缺 `playwright-core`/Chrome 时**优雅跳过**，保证无浏览器环境也能过门禁）。`--fast` 跳过 E2E 与构建（约 16s）。
- **优先级**：P1
- **成本**：小（半天）。
- **备注**：本项目长期是「多会话并发改同一棵树」，这条能显著减少"一个会话把另一个会话改坏"的概率。

### 8. 管理操作的审计日志与二次确认 ✅（审计部分）
- **目标**：现在核销、删除价格、改额度、删用户都没有留痕；误点「核销开通」会直接给错账号开会员。
- **实现思路**：服务端加 `data/audit.log`（JSONL：时间、操作、对象、前后值、来源 IP），
  由各管理路由统一写一条；关键破坏性操作（核销、删除用户、恢复备份）加「输入订单号后 4 位确认」。
  审计日志已在 `log()` 里有雏形，补齐结构化字段即可。
- **✅ 已实现（服务端 1.4.4）·审计部分**：`server/lib/audit.js`（JSONL 追加 + 2MB 轮转 + `redact()` 脱敏）
  + **24 个管理写操作**统一落一条（用户 / 价格 / 会员配置 / 订单 / 激活码 / 通道 / 快照 / 告警），
  `GET /api/admin/audit` 支持 `limit/action/target/ok/since/until` 筛选；Web 管理页与启动器各有一个「审计日志」入口（可导 CSV）。
  三条硬约束：**密钥与密码永不写入**（键名命中 apiKey/token/password/salt/hash… 一律 `***`；激活码不记码值）、
  **写审计失败不影响业务**、**不参与数据快照**（回滚不该把日志带回去）。
- **⏳ 未做（原建议的「严格二次确认」）**：保留为 P2。现状是**UI 层确认**（核销 / 删除用户 / 回滚均有 confirm 且带对象标识）
  + 回滚的**服务端强校验** `{"confirm":"RESTORE"}`；未做「输入订单号后 4 位」这类逐字校验 —— 它会改动
  启动器、Web 页与既有 E2E 的交互契约，收益（防手滑）已部分由 confirm 覆盖，留待有明确需求再做。
- **优先级**：P1（审计已完成）/ P2（严格二次确认）
- **成本**：小到中。

## 三、P2：有价值，需配套条件

### 9. 真正的自动续费订阅
- **目标**："按月/按季/按年"目前只是「一次买多久」，到期即停；订阅制能提高续费率。
- **实现思路**：依赖第 6 步的官方支付通道。新增 `subscriptions` 集合
  （`userId / plan / cycle / priceItemId / nextRenewAt / status / cancelAt`）+ 支付方
  「签约代扣」或「到期前 3 天账单」两种模式。到期前 N 天发提醒邮件，失败进入 3 天宽限期后降级。
  价格表的 `cycle` 字段就是为这一步预留的。
- **优先级**：P2（前置：支付通道）

### 10. 优惠券 / 折扣码 / 分群定价 ✅

**✅ 已实现（服务端 1.4.6 / 插件 0.24.6）** —— 但实现路径与原设想有几处重要偏离，记在这里：

- **与激活码的硬隔离**：原设想让 `coupons` 与 `codes` 并存但职责相近，容易混用。实际实现把它们定义成
  完全不同的东西：激活码**发会员**（免费、不走订单），优惠券**只打折**（走完整下单收款）。
  并加了硬约束：折扣上限 99%、折后至少留 ¥1 —— **100% 减免一律拒绝**，否则优惠券就成了第二个免费发放器。
- **名额语义做成「占用 → 消耗 / 释放」**，而不是原来的「下单即消耗」。用户点几下就能生成订单，
  下单即消耗会让限量券瞬间耗光。现在核销才 `used`，取消与超时回收都 `released` 且不计额度。
- **尾数必须在折后金额上分配**：实付 = 折后价 + 唯一对账尾数（#6 第一步的机制）。
  原来没考虑打折与对账的相互作用，实现时才发现在折前价上分尾数会让「按金额唯一对账」失效。
- **分群定价（audience / tags）本次未做**：它需要用户表加标签体系与后台标签管理，属独立一块，
  仍留在下面 P2 待办里。优惠券已能覆盖大部分「首单 5 折」「限时促销」的需求。
- 三条入口：Web 管理页「优惠券」标签页、启动器「会员管理 → 优惠券」标签页、
  以及 `GET|POST|PUT|DELETE /api/admin/coupons`。

- **原始设想（保留作对照）**：新增 `coupons`（码、类型=折扣额/折扣率、适用等级与周期、有效期、使用上限、每人限用）
  与 `POST /api/orders` 的 `coupon` 字段；订单记 `discount` 与 `originalAmount`。
  分群定价走价格表的 `audience` 字段（`all` / `student`），用户表加 `tags`。
- **优先级**：P2
- **成本**：中。

### 11. 用量可视化与导出 ✅
- **目标**：用户只看到「今日 12 / 3000」，不知道趋势，也不易判断是否该升级。
- **实现思路**：服务端把 `usage` 从「当日计数」升级为「近 30 天按日数组」（`usage.daily = {date: count}`，
  超 30 天滚动淘汰），插件端画一个迷你柱状图 + 近 7 天合计；后台用户详情页可导出 CSV。
- **✅ 已实现（服务端 1.4.3 / 插件 0.24.4）**：`usage` 增加 **`usage.daily`**（近 30 天按日滚动、超期自动淘汰；
  **旧的 `{date,count}` 结构现场兼容、无需数据迁移**），`usageDays()` 给缺口补 0 → 前端拿来就能画；
  `/api/auth/me` 与 `/api/membership` 下发 `usage{today,limit,last7,days[30]}`（`/api/membership` 同时带上 `user`）；
  插件会员卡新增**纯 CSS 迷你柱状图** + 「今日 N / 额度 · 近 7 天合计 M 次」，**老服务端没有趋势数据时整块隐藏**（不画空图）；
  Web 管理页用户表新增「近 7 天」列 + **导出用量 CSV**（带 BOM 便于 Excel 直开，含近 30 天按日明细）。
- **优先级**：P2

### 12. 额度包（一次性加油包）
- **目标**：偶尔跑大批量的用户不想升级整档会员。
- **实现思路**：**1.8.0 起已由充值档位直接满足**——`balance.rechargeOptions` 生成充值订单，
  核销后进 `paidMicro`（永不过期、全模型可用）。取消调用次数后不存在 `quotaBonus` / `dailyLimitOf()`，
  不要再按「+N 次」设计。
- **优先级**：P2
- **成本**：中（订单域要区分 kind）。

### 13. 会话/设备管理 ✅

**✅ 已实现（服务端 1.4.7）** —— 实施时对原设想做了三处修正，都值得记下来：

- **「同时在线设备数」这个提法本身就是错的**：令牌 30 天滑动续期、靠请求续期，关掉 Zotero
  并不会"下线"。所以改成 **活跃设备数**（最近 N 天有请求的令牌数），界面文案也相应写成
  「活跃设备 N 台（阈值 M 台 / 窗口 D 天）」。**判据要诚实，否则数字只会误导人。**
- **只观测不处罚**：超阈值只写 `alerts.log` + 发管理员邮件 + 后台标红，**不自动踢、不自动降级**。
  同一人「台式 + 笔记本 + 实验室机器」太常见，而共享账号的损失远小于误封一个真实付费用户。
  要处罚也必须是人工确认后的动作。原设想里没有明确这条边界，实际是这版最重要的决定。
- **脱敏分层**：用户看自己的设备 IP 打码、响应不含令牌散列；只有仅本机直连的管理接口才给完整 IP。
- **设备标识不是凭据**：`deviceId` 由插件本机生成、可伪造，只用于展示与异常检测。
  （原设想让它上报「主机名」，出于最小必要原则改为不上报主机名。）

- **原始设想（保留作对照）**：令牌表已按 user 分组，加 `deviceLabel`（插件首次登录时上报
  `Zotero.locale + 主机名 + 插件版本`）、`lastSeenAt`、`createdIp`；
  新增 `GET /api/sessions`、`DELETE /api/sessions/:id`（仅本人），插件设置面板列出并可踢出。
- **优先级**：P2

### 14. 离线宽限与网关熔断
- **目标**：账号服务抖动时，已登录用户不该立刻不可用；反之也要防止被薅。
- **实现思路**：插件端本地缓存「最近一次成功的额度校验」，网络不可用时按 30 次/小时的小额度放行，
  恢复后以服务端为准；服务端侧对单用户做令牌桶，上游 5xx 连续 N 次则短暂熔断该通道并让
  `/api/health` 体现状态（后台首页显示）。
- **优先级**：P2

## 四、P3：锦上添花

### 15. 发票 / 收据
- 目标：企业用户报销需要凭证。思路：订单核销后生成带编号的 PDF 收据（零依赖可手写极简 PDF），
  或直接提供「开具发票」申请入口转人工。**优先级 P3**。

### 16. 两因素认证（TOTP）
- 目标：给高价值账号加一层。思路：`user.totpSecret`（加密存储）+ 绑定二维码页面 +
  登录第二步；与第 3 步的锁定策略互补。**优先级 P3**（个人向工具，收益低于成本）。

### 17. 升级/降级按比例折算（proration）
- 目标：年付用户中途升档不亏。思路：剩余价值折算成天数补贴到新周期。
  **优先级 P3**——当前只有 Free/Pro 两档，没有升档路径，等出现第三档再做。

### 18. 会员等级 >= 3 档（Team / 机构版）
- 目标：面向实验室/课题组的多席位共享。思路：`plans` 已是配置化，加一档即可；
  真正的成本在「席位与共享额度」的数据模型（`seatGroup` 概念）。**优先级 P3**。

### 20. 套餐 AI 能力分级（官方模型范围 + 全模型试用）✅
- **目标**：让「Pro 才有的高级模型」真的存在。实施前发现：Pro 卖点里写着「高级模型（推理档 / 长上下文）」，
  而 `plans[].highTierModels` 字段**只定义、从未被消费**，`/v1/models` 又返回全局清单
  ⇒ 免费用户事实上能直接选最贵的模型。
- **做法**：`channels.json.highTierModels`（哪些算高级）× `plans[].highTierModels`（哪个档能用）
  + `membership.json.ai.trialDays`（新用户全模型试用）。服务端按套餐过滤 `/v1/models` 并对越权调用
  返回 **403（可编程识别的 code）**；插件端把需升级的模型 **🔒 灰显**给出升级引导。
- **三条设计取舍（值得记下来，别改回去）**：
  1. **`auto` 恒定免费** —— 它映射通道默认模型，是全体用户的兜底入口；一旦被误配进高级清单
     就会一次锁死所有免费用户。有专门断言守着。
  2. **自带 Key 的通道不做限制** —— 那条链路不经过本站，既不产生成本也管不到；
     限制它只能拦住老实用户，还会把「可接入自己的接口」这个卖点毁掉。
  3. **越权明确 403，不静默换成便宜模型** —— 静默降级会让用户以为在用所选模型，比报错危险。
- **优先级**：P1（直接支撑 Pro 的价值主张）｜**成本**：中｜**状态**：✅ 服务端 1.4.9 / 插件 0.24.8

**沿用这个框架还能顺手做的（未做，供决策）**：
- **永久会员独立额度** —— 上次定价建议已提：永久 = 一次性收入 + 永久成本，额度是唯一的成本阀门。
- **高峰优先通道** —— `GATEWAY_MAX` 目前所有套餐一样（每 IP 每分钟 20 次）；可按套餐分级。
- **长上下文 / `max_tokens` 分级** —— 与模型分级同源，可在同一处配置里加。
- **非 AI 功能分层** —— 标签治理/附件体检的批量上限与并发数、配置快照数量、PDF 对比页数上限。

### ★ 永久会员定价建议（2026-10-03，供决策；**未擅自改价**）

线上现价：永久 ¥128 / 按年 ¥69 / 按季 ¥19.9 / 按月 ¥9.9。

**问题**：¥128 只等于 **1.86 倍年费**（约 22 个月的年费价，折合 ¥5.75/月）。任何打算买满两年的用户
都会转而买永久 —— 年费档会长期失血，而永久档是**一次性收入 + 永久成本**（AI 网关按调用付费，
额度是每日 3000 次，这个成本永不停止）。

**建议价位：¥298**（≈ **4.3 倍年费** / 折合按月约 30 个月），区间参考：

| 价位 | 相当于 | 适用意图 |
|---|---|---|
| ¥198 | 2.9 倍年费 | 极限速销 / 冷启动期换取现金流，但会明显吃掉年费档 |
| **¥298（建议）** | **4.3 倍年费** | 常规软件买断惯例（3~5 倍年费），保住年费档的主力地位 |
| ¥398 | 5.8 倍年费 | 长期成本不确定、想更保守时；但转化会明显下降 |

**两个配套建议**（比单纯改数字更重要）：

1. **永久档给独立且更保守的每日额度**（例如 Pro 的一半）。永久 = 一次性收入 + 无限期成本，
   额度是唯一的成本阀门；现价 ¥128 配 3000 次/日，一个重度用户几个月就能把毛利吃平。
2. **永久档按「版本」而非「永远」界定**（买断当前主版本，后续大版本另计）。纯「永久 + 每日高额度」
   在 LLM 成本结构下有长期风险，写进条款能避免将来的纠纷。

改价入口：会员管理 → 价格与周期 → 编辑那条「永久」条目（**改价不影响已产生的历史订单**）。
